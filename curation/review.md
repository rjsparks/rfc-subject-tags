Other binary-to-text encodings a reader might associate with this area — uuencode, quoted-printable, Radix-64 — were considered and rejected: uuencode and quoted-printable are different technologies (rule 1), and "Radix-64" (OpenPGP's name for the armored base64 form) tokenises into "radix" and "64" under the stated splitting rules, so it could not be found as a single-token alias and is not important enough to warrant a multiword entry. "hexadecimal"/"hex" was rejected as generic vocabulary (rule 3): it occurs throughout the corpus in contexts unrelated to Base16 encoding.
- `beep` -- The desc already makes 'blocks', 'extensible' and 'exchange' findable as whole-word prefixes, so no expansion of the acronym is needed. BEEP has no version or variant names (the core is RFC 3080 with the TCP mapping in RFC 3081); profiles layered on it (e.g. SASL, TLS, SYSLOG-over-BEEP) are separate technologies with their own tags and are deliberately not listed.
- `benchmarking` -- "benchmark" is already reachable: the desc word "Benchmarking" starts with it. Terms like throughput, latency, frame loss, DUT and SUT are generic vocabulary or components of the methodology rather than other names for it (rules 2-3); throughput/latency measurement of live networks is also the sibling tag performance-measurement, not this one.
- `bfcp` -- The desc already contains "BFCP", "Binary", "Floor", "Control" and "Protocol" as indexed words, so both the acronym and the expanded name are findable today. "bfcpbis" is the working group name but readers do not use it for the technology itself, and it starts with "bfcp" only in the reverse direction that matters (typing "bfcp" would find the desc word anyway). Floor control components such as floor chair, floor request or BFCP over TLS/DTLS are sub-features (rule 2) or other tags. Related conferencing control protocols (XCON, CCMP, MSRP) are different technologies with their own tags or homes (rule 1/5).
- `bfd` -- The expansion "Bidirectional Forwarding Detection" is already in the desc word by word, so `bidirectional`, `forwarding` and `detection` are all redundant. Sub-features such as micro-BFD (BFD on LAG member links, RFC 7130), BFD echo mode and BFD authentication are components of the tag's subject (rule 2), not alternative names, and are left to full-text search. No predecessor or vendor name for BFD itself is in common RFC use.
- `bgp` -- BGP-4 (hyphenated, as in RFC 4271's title) is the same variant but the hyphen is a word separator in the index, so the searchable single-token form BGP4 is what is proposed. IDR was considered as a working-group alias but rejected: unlike SPRING->segment-routing, 'inter-domain routing' is a broader subject area (cf. routing-architecture, idpr) rather than a name readers use for the protocol itself. EGP is BGP's predecessor but is an existing tag id (rule 5) and a genuinely different protocol (rule 1). 'looking glass' appears in `match` but names an operational tool, not another name for BGP, so it is not an alias; it stays a match-only term. Children bgp-communities, bgp-flowspec, bmp, route-reflection and route-server already hold the sub-feature terms.
- `bgp-communities` -- BGP communities has only one name; the standard/extended/large variants are already words in the desc ("standard", "extended", "large", "BGP"), so no variant form needs rescuing. Deliberately not proposed: (a) the singular "community" — under the desc's prefix rule the indexed word "communities" is NOT matched by the query "community", so it would survive rule 4, but rule 3 names "community" outright as generic vocabulary and rules 1-3 outrank rule 4, so it stays out; (b) well-known community values such as NO_EXPORT, NO_ADVERTISE and NO_PEER, and extended-community types such as route target (RT) and route distinguisher (RD) — all instances or sub-features under rule 2 (RT/RD are also used chiefly in l3vpn/evpn contexts, whose own tags exist); (c) BGP-LS, BGP FlowSpec and other BGP features — different technologies with their own tags (bgp-flowspec) under rules 1 and 5. The IDR working group name is not a synonym for communities specifically; it would belong to bgp if anywhere.
- `bgp-flowspec` -- Only one candidate is genuinely a different name for this tag. Terms deliberately excluded: SAFI 133 / AFI-SAFI values, traffic filtering rules, rate-limit/redirect actions and flow-spec redirect communities are components or sub-features of the subject (rule 2) — redirect-to-VRF style communities belong to the sibling tag bgp-communities if anywhere. DDoS mitigation is the application area, and `ddos` is an existing tag id (rules 3 and 5); RTBH / remote-triggered black hole is a different filtering technique, not another name for BGP Flow Specification (rule 1). "FS" alone is too ambiguous to propose. If the search index also tokenises the tag id "bgp-flowspec" on the hyphen, "flowspec" would already be reachable and could be dropped as redundant; rule 4 as written tests only the desc, against which it is not reachable.
- `bgp-spf` -- The bare string 'SPF' is deliberately not proposed: `spf` is an existing tag id (Sender Policy Framework), so claiming it here would shadow a real tag; a reader typing SPF should keep landing on the email-authentication tag. 'BGP-LS' likewise is not claimed here -- it is a different technology (rule 1), recorded above as a missing tag candidate; if it is ever added, bgp-spf's desc reference to it would resolve there.
- `bgpsec` -- BGPsec has essentially one name, and the desc already indexes the words `bgpsec` and `bgp` plus `validation`, so a reader typing any of those lands here. Case variants (BGPSEC, BGPsec) are not separate index words. Deliberately rejected: `SIDR`, the working group, which the guidance already assigns to `rpki` and which produced both technologies, so claiming it here would be ambiguous at best; `S-BGP` and `soBGP`, which are distinct earlier secure-routing designs rather than other names for BGPsec (rule 1) and which appear in RFC text only as compared-against prior art, not substantial enough to propose as tags; `RPKI`, which is the sibling tag (rule 5); and components such as AS_PATH, router key, signature block and pCount (rule 2).
- `bier` -- BIER has exactly one name, and the desc spells out the expansion, so a reader typing BIER, Bit, Index, Explicit or Replication already lands here. Considered and rejected: 'BIER-TE' (Tree Engineering, RFC 9262) is an extension/variant mode of BIER rather than another name for it, and the hyphen means the query would not match the indexed word 'bier' anyway; 'BIFT' (Bit Index Forwarding Table) and 'BFR'/'BFIR'/'BFER' (bit-forwarding routers) are components of the architecture, rule 2; 'multicast' is the parent tag id, rule 5.
- `bmp` -- BMP has exactly one name, and both the acronym and its expansion are already reachable: the desc word `bmp` matches a query of `BMP`, and `BGP`/`Monitoring`/`Protocol` are each indexed as whole words. There are no superseded or variant names for this protocol (it has no versioned forms in common use, unlike OSPFv2 or IKEv2). Related terms such as `BMP station`, `route monitoring`, `Adj-RIB-In`, `stat reports` and `peer down` are components or generic vocabulary (rules 2 and 3), not other names for the protocol. Note that the string `BMP` is also the extension/name of the Windows bitmap image format and appears in RFC text (e.g. media-type and image registrations) and as 'Basic Multilingual Plane' in Unicode-related RFCs; those are different subjects entirely and are a matching concern for the `match` field, not something an alias could help with.
- `brotli` -- Brotli has a single name and the desc word `brotli` already covers prefix queries. The HTTP content-coding token `br` was considered and dropped under rule 4: the desc word `brotli` starts with `br`, so typing it alone already lands the reader here. Sibling algorithms (deflate, gzip, zstd) have their own tags, so rule 1 keeps them out.
- `brski` -- BRSKI has one name, and both it and the expansion words (bootstrapping, remote, secure, key, infrastructure) are already indexed from the desc. Rejected candidates: MASA, pledge, registrar and voucher are components/roles within BRSKI (rule 2), not other names for it; EST and est-coaps belong to the existing `est` tag (rule 5); ANIMA is the working group but its scope is the parent `autonomic-networking` (plus ACP/GRASP), not BRSKI specifically, so it is better placed there than here; 'zero-touch provisioning' names a broader concept that also covers SZTP/netconf-based bootstrapping, so it is a different (larger) subject rather than a variant name for BRSKI. Profile variants such as BRSKI-AE, BRSKI-PRM and constrained BRSKI all begin with 'brski', so the desc word already makes them findable by prefix match.
- `caldav` -- CalDAV has a single name, already the first word of the desc and therefore findable today. Plausible-looking candidates were all rejected: 'CalDAV Scheduling', 'iTIP'/'iMIP' and 'iSchedule' are separate scheduling protocols or sub-features rather than other names for CalDAV (rules 1-2); 'WebDAV' and 'iCalendar' are other technologies with their own tags, webdav and icalendar (rules 1 and 5); 'calendaring' and 'calendar access' are generic vocabulary and the parent tag id (rules 3 and 5).
- `calendaring` -- No aliases proposed. 'calendar', 'calendaring' and 'scheduling' are all already reachable as prefixes of the desc words 'Calendaring' and 'scheduling', so they are redundant under rule 4. iTIP, iMIP, vCalendar, VEVENT and VTODO are components or a predecessor of the iCalendar format itself, not other names for the calendaring topic; if any of them deserve search terms they belong on the existing `icalendar` child tag (rules 2 and 5 territory), not here. The working-group names calsch/calsify/calext were considered but rejected: unlike SPRING->segment-routing, readers do not use them as names for the technology, and calext/calsify appear mainly in process context rather than as terms someone would type to find calendaring specs.
- `captive-portal` -- 'captive' and 'portal' both already land on this tag via the desc, so neither is worth listing. 'Walled garden' was considered and dropped: it is multi-word, informal, and closer to generic vocabulary than a name for this technology. 'Hotspot' was dropped under rule 1/3 — it names the access network, not captive-portal detection, and would produce confidently wrong hits for Wi-Fi/wifi material.
- `capwap` -- CAPWAP has a single name, and both the acronym and its expansion (Control and Provisioning of Wireless Access Points) are already in the desc as whole words, so they are reachable by search. Its predecessor work (LWAPP, the Lightweight Access Point Protocol of RFC 5412, and the CAPWAP-related SLAPP/CTP proposals) are distinct protocols rather than other names for CAPWAP, so rule 1 keeps them out; LWAPP is arguably the closest candidate but it names a different, competing protocol that CAPWAP drew from rather than a former name of CAPWAP itself. Components such as WTP, AC and the binding-specific DTLS usage fall under rule 2, and generic terms like 'access point' or 'wireless' fall under rule 3 (and 'wireless' would in any case pull toward the sibling tag wifi).
- `carddav` -- CardDAV has exactly one name and no predecessor or variant forms; the desc already makes 'CardDAV' findable. The working group name 'vcarddav' was considered but rejected: it spans both the vCard format work and CardDAV, so it does not denote this tag specifically, and a reader typing it is at least as likely to want the parent 'vcard' tag. 'WebDAV' and 'vCard' are a different protocol and a different data format respectively (both have their own tags, webdav and vcard), so rule 1/5 excludes them; 'address book' is generic vocabulary already present in the desc.
- `cbor` -- CBOR has a single name; the desc already indexes both `cbor` and the expanded words `concise`/`binary`/`object`/`representation`, so a reader typing either the acronym or any word of the expansion lands here today. No superseded or vendor name exists. Related terms route elsewhere: CDDL is the existing child tag `cddl`; COSE, OSCORE and EDHOC are separate technologies with their own tags (`cose`, `oscore`, `edhoc`), not names for CBOR itself. `cbor-diag`/diagnostic notation and CBOR Sequences are sub-features (rule 2), and JSON is a different data format with its own tag (`json`).
- `cddl` -- CDDL has exactly one name, and the desc already contains both the acronym and the expansion, so typing "cddl", "concise", "data" or "definition" lands on the tag today. The full expansion "Concise Data Definition Language" is not needed in multiword for the same reason. Related terms are either the parent (CBOR, its own tag) or components/features of the language itself (e.g. sockets, groups, control operators), which are out of scope per rules 2 and 3. CDDL is also the acronym for the Common Development and Distribution License in unrelated licensing contexts, but that is not an alias concern here.
- `cdn` -- Components and sub-features of CDN work (surrogate, request routing, footprint, capacity advertisement, metadata) are excluded under rule 2, and generic words like content, delivery and distribution under rule 3 (the first two are already in the desc anyway).
- `cellular` -- `aliases` is empty on purpose: `cellular` is a category name with no genuine synonym of its own. GPRS was considered and dropped under rule 4 — the desc word is indexed as `gprs/lte/5g`, which starts with `gprs`, so typing GPRS already lands here; LTE and 5G do not benefit from that prefix and so remain in `covers`. `3GPP` likewise already matches the desc word `3gpp`. IMS/VoLTE were considered: IMS is a 3GPP service architecture whose RFC material is overwhelmingly SIP-related, so it belongs with `sip` (or a future tag of its own) rather than being claimed here. Radio-layer neighbours with their own tags — `wifi`, `wimax`, `lpwan` — are excluded under rule 1.
- `certificate-transparency` -- Rejected: SCT (Signed Certificate Timestamp), CTLog, log operator, monitor, auditor, Merkle tree — all components or sub-features of the subject (rule 2), or generic vocabulary. `trans` is the IETF working group name, but it is a generic English fragment that readers are unlikely to type for this technology and would collide badly with unrelated searches, so it is not proposed. `certificate transparency` itself is already reachable via the desc word `certificate` and is multi-word anyway.
- `cgn` -- CGN itself is already reachable: 'cgn' is an indexed word in the desc. 'Carrier' and 'grade' are likewise indexed separately since the hyphen splits the word. NAT444 was considered and rejected under rule 2 — it names one specific double-translation deployment architecture built with a CGN, not another name for CGN itself, and it sits alongside DS-Lite and NAT64 as an address-family-transition model rather than being synonymous with the tag; a reader typing it is served by full-text search. 'CGNAT' was considered but dropped for lack of confidence that it occurs in RFC text (RFCs consistently write CGN or LSN).
- `chacha20` -- Poly1305 is deliberately omitted: it is a whole word in the desc ('ChaCha20 and Poly1305'), so typing poly1305 already lands on this tag. 'ChaCha' alone is likewise redundant, since the indexed desc word 'chacha20' starts with that query. XChaCha20 was considered and dropped for lack of confident RFC-corpus occurrence. AES-GCM, GCM and other AEAD constructions are different technologies and belong to aes, not here.
- `character-sets` -- Unicode and UTF-8 are deliberately excluded: they are siblings with their own tags (`unicode`, `utf-8`), so rule 1/rule 5 governs. Named legacy sets whose names are hyphenated or underscored (ISO-8859-1, Latin-1, Shift_JIS, ISO-2022-JP) are omitted because the punctuation would be split on indexing, so no reader query for them can match as a single token; they would need the same search fix as `code page`. Generic vocabulary from this area (encoding, repertoire, transliteration, registration) is left to full-text search. `charset` is given in the singular; if the index does prefix matching as described, listing the plural `charsets` instead would additionally catch the singular query, which the vocabulary editors may prefer.
- `checksum` -- No aliases proposed: 'checksum' has one name and the desc word `checksum` already lands any reader typing it or any longer prefix-compatible query. Deliberately excluded: MD5, SHA and HMAC (cryptographic integrity, and `md5`, `sha`, `hmac` exist as tags — rule 5 and rule 1); ICV, MIC and MAC (integrity artefacts belonging to `ipsec`/`security`, and generic vocabulary); FCS and UDP-Lite coverage (`udp-lite` is its own tag); 'hash' and 'integrity' (generic vocabulary, rule 3). Note the plural 'checksums' is not findable today given prefix-directional matching, but a plural is not a variant name, so it is left to a search fix rather than listed as an alias.
- `cidr` -- 'classless' and 'aggregation' are both already whole words in the desc, so 'classless', 'classless inter-domain routing' and 'aggregation' are redundant. Considered VLSM (variable-length subnet masking) and rejected it under rule 1: it is subnetting inside a single network number, a related but distinct technique from classless inter-domain routing, so a confident hit on this tag would be wrong; full-text search already serves it. The working group name CIDRD is recorded in `groups` and readers do not use it as a name for the technology, so it is not proposed.
- `clnp` -- Deliberately excluded: IS-IS, ES-IS, IDRP, CLNP address/NSAP terms — IS-IS has its own tag (`is-is`) and the others are different OSI protocols or components, not other names for CLNP (rules 1 and 2). `connectionless` and `Connectionless Network Protocol` are already reachable via the desc. TUBA is the one judgement call: it names a specific proposal to run TCP/UDP over CLNP rather than CLNP itself, so if the reviewers consider it a distinct technology it should be dropped from here and pointed at `ipng` instead.
- `cmp` -- CRMF (Certificate Request Message Format, RFC 4211) is the message format CMP carries, not a synonym for it, so it is excluded under rule 2; if it warrants search coverage it belongs with `pki`/`x509` rather than here. `CMPv3` (the pvno 3 introduced by RFC 9480) would be a legitimate version-form alias by the same reasoning as CMPv2, but I am less confident the literal string appears in RFC text, so I have left it out rather than risk a corpus rejection — worth adding if a corpus check finds it.
- `cms` -- S/MIME and CMC/certificate-management terms were considered and rejected: s-mime is already a child tag (rule 5), and CMC is a separate protocol built on CMS rather than another name for it. Content types such as SignedData, EnvelopedData and AuthEnvelopedData are components of the syntax (rule 2), not alternative names. 'PKCS' alone was not proposed because it names the whole PKCS family, most of which belongs elsewhere (pki, x509).
- `coap` -- Considered and rejected: `CoRE` (the working group name) — although the SPRING precedent allows a WG name, `core` is an extremely common generic English word and would produce noisy/misleading lookups, and the WG's scope is broader than CoAP alone (link-format, resource directory). `constrained application protocol` is already findable word by word in the desc, so no multiword entry is needed. Block-wise transfer, Observe, CoMI and the Resource Directory are components or separate specs, not other names for CoAP. `oscore` is already a child tag; DTLS/`dtls` is a separate existing tag. LwM2M is a different (OMA) protocol layered on CoAP, not an alias, and has too little RFC presence to propose as a tag.
- `codecs` -- Singular 'codec' is already reachable: the desc word 'codec' is matched by the query 'codec'. I did not propose generic terms like 'vocoder', 'encoder' or 'compression' (the latter is also an existing tag id). GSM's speech codec (GSM 06.10) is referenced in RTP payload RFCs, but 'GSM' is better left to the cellular tag's covers as the instructions indicate. AV1 and EVS were considered and dropped for low confidence of appearing in published RFC text; if the corpus check shows otherwise they would both belong in covers here. Opus, VP8, VP9, H.264, AMR, FFV1 and Matroska are excluded because they are existing child tags (rule 5).
- `codel` -- CoDel has one name. 'Controlled Delay' is already in the desc as separate indexed words ('controlled', 'delay'), and it is multi-word anyway. FQ-CoDel (fair-queuing CoDel) was considered: it is a distinct algorithm combining CoDel with DRR fair queuing rather than another name for CoDel, so under rule 1/2 it is not an alias; it is close enough that a reader typing 'fq-codel' would likely still want this tag, but the search tokeniser splits on '-', so 'fq' and 'codel' index separately and 'codel' already lands here. No missing-tag candidate proposed for fq-codel since it is well within the aqm/codel scope. Sibling 'pie' is a different AQM algorithm and stays out. Note the single entry in aliases above is arguably redundant under rule 4 (case-insensitive prefix match on the id itself) and should be dropped by the reviewer if id matching is case-insensitive; the correct answer for this tag is an empty aliases list.
- `compression` -- 'compress'/'compressed' already reach this tag by prefix on the desc word 'compression', so no alias is needed for them. This is a category tag whose concrete instances mostly already have children (deflate, gzip, brotli, zstd), so the covers list holds only the formats with no tag of their own. 'zlib' (RFC 1950) is deliberately not listed here: it is the wrapper format around DEFLATE and its right home is the existing `deflate` tag, where it would be a reasonable alias. Header/payload compression terms (SigComp, ROHC, IPComp) belong to their own existing tags, not here.
- `conex` -- ConEx has exactly one name. The tag id `conex` and the desc words `ConEx`, `Congestion` and `Exposure` are all already indexed, so the expanded form is reachable today. The related mechanisms a reader might confuse it with (ECN, PCN, AQM) are distinct technologies with their own sibling tags, so none qualify under rule 1.
- `conferencing` -- Nothing else survives. Queries `conference`/`conferencing` already land here by prefix on the desc word `conferencing`, so they are redundant under rule 4. XCON (the centralized-conferencing WG's usual name) is another tag's id, so it is excluded by rule 5 — the child tag `xcon` is its correct home. CCMP, MCU, focus, and mixer are components/instances of the conferencing architecture (rule 2). MEDIACTRL is a media-server control WG rather than another name for conferencing, and PERC is conference media security whose natural homes are `srtp`/`multicast-security` — both fall under rule 1. `videoconferencing` and `audioconferencing` were considered and dropped as sub-forms of the subject (rule 2) rather than alternative names for it. Not a category tag, so no `covers`.
- `congestion-control` -- No aliases: 'congestion control' has no superseded or variant name, and both 'congestion' and 'avoidance' are already indexed words of the desc. Mechanism names such as slow start, AIMD, fast retransmit and RTO are sub-features (rule 2) and already live in `match`. CUBIC, LEDBAT, ECN, AQM, PCN and ConEx are existing sibling/child tags, so rule 5/rule 1 keeps them out of both lists. DCTCP overlaps data-center-networking and ecn; if it ever gets a tag, drop it from covers here.
- `content-negotiation` -- Considered and rejected: TCN / Transparent Content Negotiation (RFC 2295) — it names one specific HTTP mechanism rather than the subject as a whole, so rule 2 applies; if it were judged substantial it would be a tag candidate, not an alias. Accept, Accept-Language, Accept-Encoding, q-values and variant/Alternates headers are protocol components (rule 2). "media feature" and "content negotiation" themselves are already reachable: the desc words "Media", "feature", "content" and "negotiation" are indexed individually. "srv"-style shorthand and "varies"/"variant" are generic vocabulary (rule 3).
- `cookies` -- The tag has one name, and the desc already makes it findable: typing `cookie` matches the desc word `cookies` (prefix match), and `state` and `management` are separately indexed there, so `HTTP state management` needs no alias. Considered and rejected: `Set-Cookie` and `Cookie` as header names — these are the wire mechanism carrying the state, i.e. a component of the subject (rule 2), and `Cookie` is in any case reachable via the desc; `session` — generic vocabulary and also a different concept (server-side sessions), rule 3; `RFC 6265` / `Netscape cookies` — document and vendor-history references, not variant names a reader would type into tag lookup. `cookies` names a single technology, not a category, so it has no `covers`.
- `cops` -- Rejected: PDP, PEP, PIB, PRID (components/sub-structures of COPS, rule 2). RAP is the working group name but is a common English word and appears in RFC text in unrelated senses, so it is too ambiguous to be a safe alias. COPS-RSVP was considered as another variant form but is rarely written as a standalone name and readers typing it are generally served by `rsvp`.
- `cose` -- COSE has essentially one name. 'CBOR' alone is already reachable: the desc word '(cbor' indexes as 'cbor' and a query of 'cbor' matches it, so it would be redundant even if it were a name for this tag rather than the underlying data format. COSE_Key, COSE_Sign1, COSE_Encrypt and the algorithm registry entries are components/sub-features (rule 2). OSCORE and EDHOC use COSE but have their own tags (rule 5 / rule 1). JOSE is the JSON-based sibling family, a different technology with its own tag.
- `cpl` -- CPL has one name. The expansion "Call Processing Language" is multi-word and its words already appear in the desc as separately indexed tokens (call, processing, language), so a reader typing any of them already lands here; nothing to add. Related SIP call-control mechanisms such as SIP servlets or the SIP CGI interface are different technologies, not other names for CPL, so they are not aliases. CPL is a single technology, not a category, so it has no covers.
- `cryptography` -- "crypto", "cryptographic" and "cryptography" are already reachable through the desc word "Cryptography"/"cryptographic" (prefix match), so they are redundant. PKCS appears in `match` but is explicitly not an alias here - it is a standards family whose home is pki/cms/rsa. "encryption"/"cipher"/"ciphersuite" are generic area vocabulary (rule 3) and full-text search already finds them. Algorithm names that have or fall under existing tags were excluded by rule 1/rule 6: SHA-family -> sha, ECDSA/ECDH/P-256 -> elliptic-curve, Ed25519 -> eddsa, X25519 -> curve25519, 3DES -> des (note: "3DES" is a good alias candidate for the `des` tag, since the desc word "des" does not make "3DES" findable), Kyber/ML-KEM/Dilithium -> post-quantum, Poly1305 -> chacha20, bcrypt/scrypt/PBKDF2 -> password-hashing, HKDF -> key-management or hmac.

CUBIC's predecessor BIC/BIC-TCP is likewise a distinct algorithm rather than a variant name for CUBIC, and it is too thin on its own to warrant a tag. HyStart/HyStart++ is a slow-start component used with CUBIC, excluded by rule 2.

- `dane` -- DANE has no superseded or variant name; it is a single acronym coined in the WG of the same name (groups: dane), so the WG name adds nothing. The expansion 'DNS-Based Authentication of Named Entities' is present in the desc and multi-word anyway; a reader typing 'DNS-Based' matches the desc word 'dns-based' already. Related RR types SMIMEA and OPENPGPKEY are sub-features of the DANE framework (rule 2), not other names for it; readers seeking those are better served by full-text search, and S/MIME material has its own tag (s-mime). DANE deployment for SMTP/HTTPS belongs to smtp/http plus dane, not to an alias here.
- `data-center-networking` -- Deliberately excluded: VXLAN, NVGRE, EVPN, TRILL and overlay-networks are existing tag ids (rule 5) and are separate technologies rather than other names for this tag. 'NVO3' was considered and dropped — it names the network-virtualization-overlay work, which belongs with overlay-networks, not another name for data centre routing/address resolution. - `data-formats` -- No aliases proposed: 'data formats' has no superseded, versioned or vendor name. 'serialization'/'serialisation', 'encoding format', 'wire format' and 'interchange format' were considered and rejected under rule 3 as generic vocabulary describing the area (and 'interchange format' is multi-word and already the province of full-text search); 'format', 'encoding' and 'representation' are all reachable today as prefixes of the desc words 'formats', 'encodings', 'representations'. Encoding-rule names such as BER, DER, PER and XER are components of asn1 and belong there, not here; base32 and base16 belong with the existing base64 tag; protobuf, MessagePack and similar non-IETF serializations were left out for lack of confident RFC-text presence. Children (xml, json, cbor, asn1, sgml, markdown, base64, compression, ...) already cover the main instances, so covers is deliberately limited to the two formats with real RFC standing and no tag.
- `date-time-formats` -- Deliberately excluded: 'timestamp'/'timestamps' (already reachable — the desc word 'timestamps' starts with either query) and '3339' (the desc's '(RFC 3339)' splits on punctuation, so the bare number already lands here; 'RFC3339' as one token is rare in real RFC text and was dropped rather than risk a corpus rejection). 'UTC', 'GMT', 'offset' and 'leap second' are time-scale or generic vocabulary, not other names for this tag; queries about zone identifiers and zone data belong to the existing `time-zones` tag, and queries about clock synchronisation to `ntp`/`ptp`/`time-synchronization`. No `covers` list: this tag names one thing (the Internet timestamp format), not a category of formats.
- `dccp` -- DCCP has a single name; the acronym and its full expansion (Datagram Congestion Control Protocol) are both already in the desc and findable word-by-word. Related terms are excluded by the rules: CCID (Congestion Control Identifier), DCCP-UDP encapsulation, TFRC and ack vectors are components or sub-features of DCCP (rule 2); TFRC also relates to the existing `congestion-control` tag rather than being another name for DCCP. Sibling transports (tcp, udp, sctp, quic) all have their own tags (rules 1 and 5). No category behaviour here, so no `covers`.
- `ddos` -- Nothing else survived. 'DOTS' is the child tag id `dots` (rule 5). Mitigation mechanisms and attack techniques -- RTBH/blackholing, amplification, reflection, flooding, scrubbing, rate-limiting -- are components or generic vocabulary (rules 2 and 3) and belong to full-text search. 'botnet' is a different (if related) subject, not another name for DDoS. 'denial', 'service', 'mitigation' and 'signalling' are all already whole words in the desc and are reachable as prefixes today.
- `decnet` -- DECnet has essentially one name, and it is already the first word of the desc, so typing DECnet (or any prefix such as DEC) lands on the tag today. Considered and rejected: 'DNA' (Digital Network Architecture) — the formal architecture name, but far too ambiguous as a bare query and would produce a confidently wrong hit for readers meaning something else; 'DECnet Phase IV' / 'DECnet/OSI' — variant names, but multi-word or vanishingly rare as a typed query, and both begin with 'DECnet' so a reader typing the first token already arrives here; 'LAT', 'MOP', 'NSP', 'DDCMP' — these are separate protocols within or alongside the DECnet stack, i.e. components or different technologies (rules 1-2), not other names for DECnet itself, and none look substantial enough in the RFC corpus to warrant their own tag. The sibling tags appletalk and ipx cover the neighbouring legacy protocol families; nothing here belongs to them.
- `deflate` -- DEFLATE has essentially one name. `zlib` is the only other name in scope and it is already a whole word in the desc ("DEFLATE and zlib"), so typing zlib lands on this tag today — redundant under rule 4. `inflate` is the decompression operation rather than another name for the format (rule 2/3), and `zip`/`PKZIP` name a different thing (an archive container that merely uses DEFLATE), so neither qualifies. RFC-number strings such as 1951/1950 are not name variants. Related compression formats (gzip, brotli, zstd) are siblings with their own tags and are excluded by rules 1 and 5.
- `des` -- 'DES-EDE3', 'des-cbc', 'des-ede3-cbc' and similar are keying/mode names for the same cipher rather than alternative names for it, and they are hyphenated so they would not survive whole-word search; left out. 'DEA' (Data Encryption Algorithm) is a genuine alternate name for DES but is a rare, highly ambiguous three-letter string in RFC text, so I did not propose it. Related historic ciphers (DESX, IDEA, RC2, Skipjack, Blowfish) are different technologies and are excluded by rule 1; none seemed substantial enough in the RFC series to propose as new tags. Typing 'triple' already reaches this tag via the desc word, so no multiword entry is needed.
- `detnet` -- The tag name itself ('DetNet') and 'deterministic' are already whole words in the desc, so both are reachable by search today; nothing else denotes the same subject. Candidates considered and rejected: 'bounded latency', 'zero congestion loss' and 'time-sensitive' are generic descriptive vocabulary (rule 3) and multi-word besides. 'RAW' (Reliable and Available Wireless, the second working group feeding this tag) was considered: it is arguably a WG-name route to this subject, but it is a common English word and would make every reader typing 'raw' land here, so I am not claiming it; if the maintainers want WG-name coverage it would be better handled by a separate WG-name search index than by an alias. 'PREOF', 'PRF', 'PEF', 'POF' are DetNet sub-mechanisms (components, rule 2). 'TSN' is routed to missing_tag_candidates rather than claimed here.
- `dhcp` -- "dhc" (the working group name) is already reachable because the desc word "dhcp" starts with it, so it is redundant. Components and options (e.g. relay agent, option 82, PXE) are sub-features, not alternate names. RARP is a different protocol and belongs in neither list.
- `dhcpv6` -- DHCPv6 has exactly one name, and the desc already indexes the word `dhcpv6`, so typing it lands correctly today. Variants readers might type are all disqualified: `DHCP` is another tag's id (rule 5) and is the parent anyway; `DHCPv6-PD`, prefix delegation, DUID, IA_NA and relay-agent terms are sub-features of the protocol (rule 2); `SLAAC` names a different address-configuration mechanism with its own tag (rule 1). Nothing survives.
- `diameter` -- Diameter has exactly one name and the desc word `diameter` already makes it findable. RADIUS and TACACS are different protocols with their own tags (rules 1 and 5), not aliases, even though Diameter is RADIUS's successor. `DIME` is the working group name and does appear in RFC text, but it is used to denote the WG/mailing list rather than as a name for the protocol itself, so I did not propose it; if the maintainers judge that readers do type DIME expecting the protocol, it would be the only plausible candidate here. Components and extensions such as Diameter applications, AVPs, CER/CEA, or Diameter-SIP are sub-features (rule 2) and belong to full-text search.
- `diffserv` -- Considered and rejected: DSCP (Differentiated Services Code Point) — it is the marking field defined by Diffserv, i.e. a component/sub-feature of the tag's subject, directly parallel to the rule-2 examples SID/SRH -> segment-routing, so it stays out even though it appears in `match` and is not reachable from the desc. Same reasoning excludes PHB, AF/EF code point names, and the DS field. IP precedence / ToS is the predecessor field, not another name for Diffserv. `diffserv` and `differentiated` are already indexed from the desc, and the tag names a single technology, so there is no `covers` list.
- `directory-services` -- The desc word 'Directory' already makes 'directory' and 'directories' findable, so no single-word variant of the tag's own name survives rule 4. Candidates I rejected: DAP, DSP, DISP, DOP (X.500 component protocols -> belong with the existing x500 tag, rule 2); LDUP, DSML (LDAP-specific, -> ldap tag, rules 1/2); WHOIS++, CCSO/ph, Solid/NIC name services (different technologies, and whois already has its own tag, rule 1); 'nameservice'/'lookup'/'yellow pages' (generic vocabulary or a different sense, rule 3). Children ldap and x500 cover the concrete instances, so this tag is not a category needing a covers list.
- `dkim` -- DKIM has essentially one name. The predecessor/expansion name "DomainKeys" (Yahoo's DomainKeys, RFC 4870) is the one obvious candidate, but the desc "DKIM (DomainKeys Identified Mail)" indexes the word `domainkeys` (the parenthesis is punctuation and splits), so typing DomainKeys already lands the reader here under rule 4 — redundant. ADSP (Author Domain Signing Practices, RFC 5617) is a separate signing-practices protocol layered on DKIM rather than another name for it (rule 2/1), and its natural home is the sibling tag `dmarc`/`email-authentication` area rather than an alias here. DCRUP appears in `groups` but is a crypto-update WG name, not a name readers use for the technology itself, so it does not meet the SPRING->segment-routing bar. DKIM2 is currently draft-stage work with no RFC text, so it is not proposed.
- `dmarc` -- DMARC has exactly one name, and the desc already indexes 'dmarc' plus the expansion words. Sibling mechanisms SPF, DKIM and ARC are different technologies with their own tags (rule 1/5). Components and related artifacts such as RUA, RUF, aggregate/failure reports, p=reject and the Public Suffix List are sub-features or generic vocabulary, not alternative names for DMARC. 'ADSP' (Author Domain Signing Practices, RFC 5617) is a predecessor policy mechanism but is properly a DKIM-adjacent protocol of its own rather than an earlier name for DMARC, so it is not listed here.
- `dns` -- No genuine synonyms exist for this tag. 'Domain Name System' is already reachable: the desc indexes 'domain', 'name' and 'system' as separate words, and 'dns' itself is the first word of the desc. Terms in `match` were considered and rejected: IN-ADDR is a component (the reverse-mapping zone), 'resource record', 'name server'/'nameserver' and 'resolver' are generic vocabulary (and 'resource', 'records', 'server', 'resolver' are in the desc anyway), and SRV RR is a record type, with SRV-based discovery better served by the existing `dns-sd`/`service-discovery` tags. Implementation names such as BIND or Unbound are software products, not names for the protocol, and would be a poor search landing anyway. Variant forms a reader might type (mDNS, DoH, DoT, DNSSEC, DNS64, EDNS) all have their own tags -- mdns, doh, dot, dnssec, dns64, edns -- so rule 5 bars them here.
- `dns-privacy` -- ODoH / Oblivious DoH terms belong to the existing oblivious-dns child tag, not here. Discovery mechanisms from the ADD group (DDR, DNR, SVCB-based resolver discovery) are separate mechanisms rather than other names for encrypted DNS transport, so they are not proposed as aliases; the group id 'add' is also too generic and collides with an ordinary English word. QNAME minimisation and EDNS Client Subnet privacy work are sub-features/related mechanisms, not alternative names for this tag.
- `dns-sd` -- Bonjour and Zeroconf are deliberately not claimed here: the vocabulary already has `service-discovery` (the guidance assigns Bonjour/Zeroconf to it) and `mdns`, the sibling that covers the other half of the Apple stack. `SRV`/`PTR`/`TXT` record types and `Discovery Proxy` are components or record formats, not other names for DNS-SD, so they are left to full-text search.
- `dns-update` -- RFC 2136's protocol name 'DNS UPDATE' is already reachable: the desc word 'dns' matches a 'dns' query and 'updates' matches an 'update' query, and the full two-word string cannot be searched anyway. TSIG and SIG(0) were considered and rejected under rule 2/1 — they are separate transaction-authentication mechanisms used with (but not synonymous with) dynamic update, and they also serve zone transfer; if they warrant coverage it is under dnssec or a future DNS transaction-security tag, not here. 'dyndns' was dropped as a vendor service name with doubtful corpus presence.
- `dns64` -- DNS64 has exactly one name and it is the tag id, already findable via both the id and the desc. Related terms all belong elsewhere: NAT64 is its own tag (`nat64`), 464XLAT is `464xlat`, and the general translation area is `ipv6-transition` — listing any of them here would violate rules 1 and 5. 'Address synthesis' and 'synthetic AAAA' are generic vocabulary plus already reachable via the desc word `synthesis`, and they are multi-word besides. No `covers` because the tag names a single technology, not a category.
- `dnssec` -- DNSSEC has essentially one name, and both it and the expansion "DNS Security Extensions" are already indexed word-for-word in the desc, so a reader typing either lands here today. The obvious candidate terms are all record types or sub-features of the mechanism rather than other names for it -- NSEC, NSEC3, NSEC5, RRSIG, DNSKEY, DS, CDS/CDNSKEY, trust anchor -- and fall under rule 2 (NSEC and NSEC3 are additionally reachable from the desc word `nsec/nsec3`, which a query of `nsec` or `nsec3` matches as a prefix). Validation-side terms such as DNSSEC validator or signer are generic vocabulary (rule 3). DANE, RPKI and dns-privacy are separate technologies with their own tags (rules 1 and 5). I considered `dnssec-bis` / `DNSSECbis`, used in the RFC 403x era for the reissued specification, but it is a document-set label rather than a name for the technology and its corpus presence is thin, so I am not proposing it.
- `docsis` -- CMTS, BPI/BPI+ and QAM/HFC were considered and rejected as components or plant vocabulary rather than other names for DOCSIS (rules 2 and 3). CableLabs was rejected as the name of the standards organisation, not of the technology. DVB-C-style cable broadcast belongs to the existing `dvb` tag, not here.
- `doh` -- The tag has exactly one name, and both of its forms are already reachable: the desc indexes `dns`, `over`, `https` and `doh` (from "(DoH)"), so typing either "DoH" or "HTTPS" lands here today. The hyphenated spelling "DNS-over-HTTPS" is common in RFC text but splits on the hyphens under the indexer and cannot be entered as a single query, so it adds nothing. Sibling terms are routed elsewhere on purpose: DoT/DNS-over-TLS belongs to `dot`, Oblivious DoH/ODoH to `oblivious-dns`, and DNS-over-QUIC to `dns-privacy` (or a future tag), none of them to `doh`. Transport and component terms such as HTTP/2, HTTP/3, resolver and DoH server are rule-1/rule-2 exclusions.
- `domain-registration` -- No genuine variant names for this tag. The obvious candidates all fail: 'registry', 'registrar' and 'registration' are already whole words in the desc, so typing them lands the reader here today (rule 4). 'NIC' appears in `match` and is historically tied to domain registration (InterNIC), but it is badly ambiguous in RFC text (network interface card, Network Information Center generally) and names an organization/service rather than this subject, so it would produce confidently wrong hits. 'ICANN' is likewise an organization, not another name for domain registration; readers typing it are better served by full-text search or by `internet-governance`. 'EPP', 'RDAP' and 'WHOIS' are the tag's own children and exist as tags (rule 5). 'TLD', 'gTLD' and 'ccTLD' name parts of the DNS name space rather than registration operations, and belong to `dns`/`special-use-domain-names` territory, not here.
- `dot` -- DNS over TLS has essentially one name. The abbreviation DoT is already indexed as the whole word `dot` from the desc's "(DoT)" (and is the tag id itself), so it is redundant under rule 4. Hyphenated spellings (DNS-over-TLS) split on the hyphen into dns/over/tls, all already in the desc. Port 853 is an instance detail, not a name. DPRIVE is the working group name but covers DNS privacy generally, not DoT specifically, so it belongs on the parent tag `dns-privacy` rather than here; DoH and Oblivious DNS are different transports with their own tags (`doh`, `oblivious-dns`) and are excluded by rule 1.
- `dots` -- DOTS has exactly one name, and both the acronym and the expansion's words (ddos, open, threat, signaling) are already indexed from the desc, so any obvious query already lands here. The protocol's internal parts (signal channel, data channel, DOTS gateway, telemetry) are components or generic vocabulary and are excluded by rules 2-3; 'telemetry' is in any case another tag's id. 'DDoS' itself belongs to the parent tag ddos, not here.
- `drip` -- "drone" itself is already reachable: the desc word "Drone" starts with the query, so it needs no alias. "RID" was considered and dropped -- in DRIP text it names a sub-feature (Broadcast RID / Network RID) rather than the protocol, so rule 2 applies; the multiword "Remote ID" form is listed above instead. "UTM" (UAS Traffic Management) was rejected as a distinct system that DRIP interfaces with rather than another name for it, and it collides with unrelated uses of the acronym.
- `ds-lite` -- DS-Lite has exactly one name, given in full in the desc: the desc words `ds`, `lite`, `dual`, `stack` already make `DS`, `Lite`, `Dual` and `Stack` prefix-matchable, and the tag id `ds-lite` covers the hyphenated form, so nothing is left to add. Deliberately excluded: AFTR and B4 (the carrier-side and CPE-side elements of a DS-Lite deployment) are components of the tag's subject, not other names for it, so rule 2 rejects them despite being frequent and distinctive in RFC 6333 text. Lightweight 4over6 / lw4o6 (RFC 7596) and Public 4over6 are separate softwire mechanisms derived from DS-Lite, not synonyms for it — rule 1 keeps them out; if a reader searching lw4o6 should land somewhere, the existing sibling `softwire` is the honest home, not here. `dslite` (unhyphenated) was considered as a spelling variant but dropped: I am not confident it occurs in real RFC text, which consistently writes DS-Lite or Dual-Stack Lite.
- `dsl` -- The variants (ADSL/VDSL/SHDSL/HDSL) are versions of one access technology rather than separate technologies, so they belong in `aliases`, not `covers`; the tag names a single technology and has no category scope to enumerate. DSLAM was considered and rejected under rule 2 as a component/device of the subject (and 'dslam' is already prefix-reachable from a 'dsl' query anyway). ANCP is the child tag `ancp` and is not claimed here. Numbered spellings ADSL2/VDSL2 were left out as redundant: a reader typing 'adsl' or 'vdsl' is served by the base aliases, and the numbered forms are rare as standalone queries.
- `dsr` -- DSR has one name. Both the acronym and the expansion are in the desc as whole words (`dsr`, `dynamic`, `source`, `routing`), so every form a reader would type already lands here. The MANET-era variant labels (DSR-flow, DSR MIB) are sub-features, not other names, and generic terms like 'source routing' describe the area rather than name the protocol — 'source routing' would also be wrong to claim here since it covers IPv4/IPv6 header source routing and segment-routing, which are different technologies with their own homes.
- `dtls` -- DTLS has exactly one name, and both the acronym and the expansion words (datagram, transport, layer, security) are already indexed from the desc, so a reader typing any of them lands here today. Version forms (DTLS 1.2, DTLS 1.3) are prefixed by the indexed word 'dtls' and need nothing extra. The DICE working group name was considered and rejected: DICE stands for 'DTLS In Constrained Environments' and names a profiling effort, not the protocol, so readers do not use it as a name for DTLS itself. DTLS-SRTP and connection ID (CID) are components/profiles, not other names for DTLS; DTLS-SRTP work is better served by the existing srtp tag. Plain 'TLS' belongs to the parent tag tls and is another tag's id besides.
- `dtn` -- Plain 'DTN' and 'bundle' are already findable from the desc, so they are redundant. 'BP' alone was rejected as too ambiguous an abbreviation to be a safe search landing. 'DTNRG' (the IRTF research group) was considered but left out as low-value; the group name is not commonly used as a name for the technology itself in the way SPRING is. Convergence-layer bindings (TCPCL, UDPCL) are components, and the underlying transports already have the tcp and udp tags.
- `dvb` -- DVB itself needs no alias: it is the tag id. MPEG and the words digital/video/broadcasting are already reachable in the desc, so only the punctuation-broken forms are proposed. Deliberately excluded: MPE and GSE (sub-features/encapsulations within MPEG-2 TS and DVB-S2, rule 2); TS, transport stream, broadcast (generic vocabulary, rule 3); MPEG-4/H.264-style codec names (different technology, and `h264` exists, rule 1/5). DVB-RCS and DVB-S overlap the `satellite` tag's territory; if the curators prefer, DVB-RCS could be carried on `satellite` as well — aliases may belong to more than one tag. The VBI entry is the one judgement call here: `dvb` is marked kind=technology, which normally means no `covers` at all, but the ipvbi group assignment makes this tag the de facto home for VBI RFCs; drop it if the curators would rather keep `covers` strictly for category tags.
- `e-commerce` -- "payment" is already a whole word in the desc and would land the reader here today, so it is redundant despite appearing in `match`. "airline" (also in `match`) is generic vocabulary for an application domain rather than a name for this subject, so it belongs to full-text search. SET (Secure Electronic Transaction) was considered as a `covers` entry but rejected: the token is a common English word and would generate confident wrong hits far more often than right ones. EDI and IOTP are existing tag ids (rule 5) and are not claimed here; a reader wanting either should land on those tags.
- `eai` -- 'i18n' is the abbreviation readers would type for the general subject and belongs to the existing `internationalization` tag, not here. 'UTF8' / 'UTF-8' is deliberately omitted: the `utf-8` tag exists (rule 5) and the encoding is a different thing from address internationalization. Components and neighbouring mechanisms such as EAI downgrade, the ALT-ADDRESS parameter, IMAP's UTF8=ACCEPT and the internationalized message header extension (RFC 6532) are sub-features, not other names for the tag, so none are claimed.
- `eap` -- EAP has exactly one name, and it is the first word of the desc, so a reader typing EAP or extensible already lands here. Considered and rejected: (a) EAP method names -- EAP-TLS, EAP-TTLS, PEAP, EAP-FAST, EAP-SIM, EAP-AKA, EAP-pwd, EAP-PSK, EAP-NOOB -- these are sub-protocols/instances within EAP, so rule 2 applies; the tag is a single technology (kind: technology) rather than a category standing in for unrelated things, so it takes no `covers` list, and full-text search already finds these names well. (b) 802.1X and EAPOL -- port-based network access control and the LAN encapsulation are different technologies that merely carry EAP, so rule 1 applies; neither looks substantial enough here to propose as its own tag without wider review. (c) EMU and the eap WG name -- EMU (EAP Method Update) is a working-group name readers are unlikely to type meaning the protocol itself, unlike SPRING->segment-routing, and `eap` as a WG name is already the tag id. (d) Generic terms such as authentication, supplicant and authenticator belong to full-text search, and `authentication` is another tag's id (rule 5).
- `ebpf` -- Considered and rejected: `cBPF` (classic BPF) — a genuine variant name, but I am not confident the spelling appears in RFC text, so it is not worth a rejection. `XDP` (eXpress Data Path) is a hook/attachment point for eBPF programs, not another name for the instruction set, so rule 2 excludes it. `Berkeley Packet Filter` needs no multiword entry: the desc already indexes `berkeley`, `packet` and `filter` as separate words.
- `ecmp` -- 'ECMP' and 'multipath' are already reachable through the desc, so no alias is needed for them; 'equal-cost' splits on the hyphen but 'equal' and 'cost' both index, so typing either lands here. 'load balancing'/'load-balancing' is generic vocabulary (rule 3) and left to full-text search. LACP was considered and rejected as a component of link aggregation rather than another name for this tag's subject. UCMP (unequal-cost multipath) was considered for covers but is a different forwarding behaviour discussed mainly inside routing protocol specs (BGP link bandwidth, RIFT); if it is wanted, it fits better as a term for a future link-aggregation/load-balancing vocabulary review than as a name for this tag.
- `ecn` -- ECN has essentially one name, and the expansion is already in the desc as separate indexed words (explicit, congestion, notification), so no alias is needed for it. Codepoint and mechanism names such as CE, ECT, ECT(0)/ECT(1) and ECN-nonce are components of the scheme, not other names for it (rule 2). AQM, PCN and ConEx are existing sibling tags and must not be shadowed (rule 5). ECN is a single technology, not a category, so it has no covers list.
- `eddsa` -- Ed25519 is treated as a variant name rather than a `covers` instance because EdDSA names one algorithm with two defined parameter sets, not a category of distinct technologies. Ed25519 may legitimately also be searched toward the sibling `curve25519` tag, since edwards25519 and X25519/Curve25519 are the signature and key-agreement faces of the same curve family; if `curve25519` is scoped to the curve itself rather than to X25519 key exchange, listing Ed25519 there as well would be reasonable. Sub-modes PureEdDSA and HashEdDSA (Ed25519ph, Ed25519ctx, Ed448ph) are excluded as sub-features under rule 2.
- `edhoc` -- EDHOC has essentially one name. Related terms were deliberately excluded: COSE, OSCORE and ACE are separate technologies/existing tags (oscore, cose, ace) and would be confidently wrong hits; 'Diffie-Hellman', 'key exchange' and 'lightweight' are generic vocabulary; EAD (External Authorization Data) and cipher suite identifiers are sub-features. Note that if a term-level check shows 'LAKE' is dominated in the corpus by unrelated uses, drop it — it is the only candidate here with any ambiguity risk.
- `edi` -- Deliberately excluded: AS1, AS2 and AS3 (the EDIINT Applicability Statements for EDI over SMTP, HTTP and FTP). They are specific transport profiles within this tag's subject rather than other names for EDI, so rule 2 puts them out of aliases; they are also each a single small RFC, so I do not think they warrant their own tags. If the taxonomy later decides that instance-level transport profiles should be searchable, they would be candidates for covers. Also excluded: generic vocabulary such as 'trade', 'business documents' and 'e-business' (rule 3), and 'e-commerce', which is already another tag id (rule 5) and is the right home for readers searching commerce terms. Note that the covers entries above assume edi reads as a category over EDI syntax standards; if it is judged a single technology (its kind is 'technology'), EDIFACT and X12 should be dropped rather than moved to aliases.
- `edns` -- Deliberately excluded: OPT / OPT RR, the pseudo-RR that carries EDNS data, and specific options such as ECS (EDNS Client Subnet), COOKIE, NSID, padding and chain query — all components or sub-features of the tag's subject (rule 2). Plain "EDNS" needs no alias entry since the desc already contains it as a whole word.
- `egp` -- EGP has exactly one name, and the desc already indexes the words `egp`, `exterior`, `gateway`, `protocol`, `inter-domain` and `routing`, so every term a reader would plausibly type for this tag already lands here. Related historic protocols (GGP, Gateway-to-Gateway Protocol; HELLO) are different technologies, not other names for EGP, so rule 1 keeps them out; neither looks substantial enough in the corpus to propose as a tag. `autonomous confederations` appears in `match` but names a specific RFC 975 extension concept rather than an alternative name for EGP, and is multi-word besides. BGP, the protocol that superseded EGP, has its own tag (`bgp`), so rule 5 applies.
- `eigrp` -- The expansion "Enhanced Interior Gateway Routing Protocol" is already in the desc and each of its words is independently searchable (enhanced, interior, gateway, routing, protocol), so no multiword entry is needed. DUAL (Diffusing Update Algorithm) and the EIGRP packet/TLV types are components of the protocol, not other names for it, so they are excluded under rule 2. IGRP is the one borderline call: it is strictly a distinct, earlier protocol, but it is the same vendor's superseded predecessor in the same lineage and is the term readers use when looking for this family, which is the SSL->tls pattern; if the taxonomy prefers strict rule 1 here, drop it rather than creating an `igrp` tag, as the standalone protocol has essentially no RFC-series coverage of its own.
- `elliptic-curve` -- Named curves are deliberately excluded. `curve25519` is already a child tag, and specific NIST curve identifiers (P-256, secp256r1, prime256v1, P-384, brainpoolP256r1) are instances of an instance — plausible `covers` material only if the taxonomy later decides curve names should be searchable; flagged here rather than claimed. ECC is very occasionally "error-correcting code" in RFC text; the cryptographic sense dominates by a wide margin, and error-correction readers are served by `fec`. ECIES and ECMQV were considered and dropped as too thin in the corpus to earn an entry. `eddsa` and `curve25519` need nothing here since they are tags in their own right.
- `email` -- `mail` and `electronic` are already whole words in the desc and so are redundant as aliases. Child technologies (smtp, imap, pop3, jmap, message-format, eai, sieve, spam, mailing-lists, vpim) all have their own tag ids, so rules 1/5 keep them out of both lists; likewise `x400`, `netnews` and `uucp` are sibling tags, not other names for email. Components and generic vocabulary such as mailbox, MTA, MUA, mail gateway, RFC822 and webmail are left to full-text search or to the more specific tags (RFC822-style header syntax belongs under `message-format`). No `covers`: every instance this category stands over already has a tag.
- `email-authentication` -- Nothing else survived. SPF, DKIM, DMARC and ARC are all existing tag ids (rule 5) and are children here anyway. DomainKeys is the predecessor name of DKIM and belongs on the `dkim` tag, not here; ADSP, Authentication-Results, DomainKeys Identified Mail signature headers and PRA are components/sub-features (rule 2). "spoofing" and "authentication" are already reachable through the desc, which indexes "anti" and "spoofing" separately. - `firmware-update` -- Deliberately excluded: 'manifest' (reachable already — the desc word 'manifests' starts with it, and it is also a component rather than another name); 'OTA' alone (generic and ambiguous across unrelated over-the-air contexts); 'TEEP'/'RATS'/'attestation' (different technologies with their own homes — teep and remote-attestation are existing tags); 'software update' (generic multi-word vocabulary already served by full-text search, and its distinctive half is in the match rule, not a variant name).

ALC and LCT are underlying/sibling protocols, not synonyms, so they are recorded as missing tag candidates rather than aliases. The tag names a single technology, so it has no covers list.

Its predecessor in the sense of 'what it replaces' is IMAP, but that is a different protocol with its own tag (rule 1 and rule 5), so it is not an alias. Sub-parts and extensions of JMAP (Core, JMAP for Mail, JMAP for Calendars, JMAP for Contacts, WebSocket transport) are components or instances (rule 2) and where they have a better home it is an existing tag such as calendaring or websocket. The working group name is also 'jmap', so it adds nothing.
- `jose` -- JOSE has no genuine synonyms or predecessor names; the tag name is the working group name and the technology name. JWS, JWE and JWK are sub-specifications (rule 2) and are in any case already whole words in the desc, so they are reachable today. JWA (JSON Web Algorithms) is likewise a component of the family, not another name for it, so it is not proposed. JWT has its own tag (rule 5) and readers typing it should land there. 'JavaScript' is already indexed from the desc expansion.
- `json` -- JSON has exactly one name; "JavaScript Object Notation" is the only common expansion and it is already reachable word-by-word from the desc (javascript / object / notation), besides being multi-word. Candidates considered and rejected: I-JSON (RFC 7493) is a restricted profile, not another name for JSON, and its hyphenated form would not survive tokenisation anyway; JSON Schema, JSON Patch, JSON Pointer and JSON Merge Patch are JSON-based formats but each is a multi-token name whose first token is JSON, so a reader typing any of them already lands here via the tag name itself — adding them buys nothing; JSON-LD is a distinct W3C linked-data serialisation and barely appears in the RFC series. The two JSON-based formats substantial enough to matter already have their own tags (jsonpath, geojson), and CBOR/JOSE/JWT are separate technologies with separate tags, so rule 1 keeps them out. No `covers` entries: although the desc mentions "JSON-based formats", the tag primarily names one concrete technology, and the instances that would populate a category list either have tags already or are prefixed with the tag name.
- `jsonpath` -- JSONPath has a single name with no established synonym or predecessor. The desc word `jsonpath` already makes the tag findable for `json` (prefix match) and `jsonpath`. Related query languages such as JSON Pointer, JMESPath, XPath and JSONata are different technologies (rule 1) and would be confidently wrong hits; none appeared substantial enough in the RFC series to propose as a separate tag here, though JSON Pointer (RFC 6901) sits under the `json` parent if the vocabulary is ever extended.
- `jwt` -- The desc already contains "JWT" and "JSON", "Web", "Token", so both the acronym and the expansion are findable today. Related terms are either components or different technologies: JWS, JWE and JWK are separate JOSE constructs belonging under the existing `jose` tag, not other names for JWT; `jwt` profiles such as PoP or DPoP are sub-features. No superseded or vendor name for JWT exists in RFC text.
- `kerberos` -- Deliberately excluded: KDC, TGT, TGS, AS-REQ, PKINIT, PA-DATA are components or sub-features of Kerberos (rule 2). GSS-API and SPNEGO are a different technology with their own home — the existing `gssapi` tag (rules 1 and 5). KINK (Kerberized Internet Negotiation of Keys) is a distinct key-management protocol, not another name for Kerberos, even though the kink WG is listed in this tag's groups; it is small enough that it does not obviously merit its own tag, so it is left to full-text search rather than claimed here. `krb` alone was considered and dropped: it is not confidently attested as a standalone whole word in RFC text (it appears mainly as a prefix in message-type names like KRB_AP_REQ), and an unattested term would only earn a rejection.
- `key-management` -- No genuine synonyms exist for the phrase 'key management' itself, so aliases is essentially empty apart from the WG name KEYPROV. Deliberately excluded: IKE, EDHOC, PAKE, OTP, CMP, EST, ACME and SPKI are all sibling or existing tags (rule 1/5). GDOI and GSAKMP are group key management and belong under the existing multicast-security tag, not here. Component vocabulary such as KDF, key wrap, rekeying, key escrow, key agreement and key derivation is either generic (rule 3) or already reachable via the desc/full-text search. SACRED (the other listed group) was left out: 'Securely Available Credentials' is a credential-storage effort whose name a reader is unlikely to type expecting this tag, and the bare word is too ambiguous to be a safe search term.
- `l1vpn` -- 'L1VPN' itself and 'Layer', 'Virtual', 'Private', 'Network' are already indexed from the desc, so no variant of the spelled-out name is needed. 'GVPN' (Generalized VPN, the BGP/GMPLS-based provisioning of these services) was considered and left out: it names a specific GMPLS/BGP mechanism rather than the L1VPN service itself, so it reads as a component/adjacent technology rather than another name for this tag; if it turns out to be frequent in the corpus it would be better handled under gmpls or vpn. Sibling terms L2VPN/L3VPN/VPLS/EVPN are different technologies with their own tags (rules 1 and 5).
- `l2tp` -- L2F (Layer Two Forwarding, RFC 2341) and PPTP are predecessor/sibling protocols that fed into L2TP's design, but they are different protocols rather than other names for it, so rule 1 keeps them out of `aliases`. `l2tp` names a single technology, so it has no `covers`. Terms like `tunneling`, `tunnel` and `layer` are generic vocabulary and/or already reachable through the desc.
- `l2vpn` -- Nothing qualifies as a true synonym. The obvious sibling names VPLS and EVPN are existing tag ids (rule 5) and are different services anyway, so they stay out of both lists. L2SM was considered as a working-group-name alias (the tag's groups include l2sm) but rejected: L2SM names the L2VPN Service Model YANG work, a data model rather than another name for L2VPN services, so it is a different thing under rule 1; if the YANG service models warrant coverage, that belongs with yang/l3sm-style modelling work rather than here. Pseudowire and Martini-encapsulation terms belong to the existing pseudowire tag, and Ethernet-over-MPLS transport terms to mpls/pseudowire.
- `l3vpn` -- Rejected: 'VRF', 'RT'/'route-target', 'RD'/'route-distinguisher' and 'VPN-IPv4' are components of the L3VPN construction, not other names for it (rule 2). 'MPLS' and 'BGP' are other tags (rule 5) and are separate technologies here anyway. 'VPN' is the parent tag id (rule 5). Sibling terms (VPLS, EVPN, L2VPN, MVPN, L1VPN) all have their own tags. L3NM (L3VPN Network Model, RFC 9182) is a plausible further alias of the same character as L3SM, but it names a specific YANG model rather than the technology, so I left it out; if L3SM is accepted, L3NM is worth a second look. As a single technology tag, l3vpn has no covers list.
- `language-tags` -- Deliberately excluded: 'locale' (CLDR/POSIX locale identifiers are a related but distinct concept, rule 1, and would give a confidently wrong hit); 'ISO 639', 'ISO 3166', 'IANA Language Subtag Registry' (sub-registries and code sources feeding language tags, i.e. components, rule 2, and multi-word besides); 'Accept-Language' (an HTTP header that carries language ranges — an instance/usage, rule 2, and better served by full-text search); 'language range' and 'language negotiation' (already in `match`, generic/multi-word, and 'language' in the desc is directly searchable). 'LTRU' (the working group) was considered under the SPRING precedent but dropped: it names a short-lived registry-update WG rather than the technology, and readers do not use it as a name for language tags. Terms about picking content by language could also plausibly interest readers of `content-negotiation`.
- `ldap` -- DAP (the X.500 Directory Access Protocol) is deliberately excluded: it is a different protocol and belongs to the existing `x500` tag, not here. LDIF, DSE, RootDSE and the LDAP schema/control/extension names are components or sub-features of the protocol (rule 2) and are left to full-text search. Working group names (ldapbis, ldapext, ldup, asid, schema) are not used by readers as names for the technology itself, so none are proposed.
- `ldp` -- TDP (Cisco's Tag Distribution Protocol, the pre-standard predecessor described in RFC 2105) is arguably a predecessor name for LDP, but it appears only rarely in RFC text and the acronym is ambiguous, so I have not proposed it. 'Label Distribution Protocol' is already in the desc word by word and needs no alias. Sub-features such as LSP, FEC and label bindings are components and belong to full-text search (note that 'fec' is also an existing tag for a different subject).
- `ledbat` -- Considered and rejected: `uTP`/`µTP` (BitTorrent's Micro Transport Protocol) — it is a distinct transport protocol that *uses* LEDBAT rather than another name for LEDBAT, so rule 1 applies; it is also thinly attested in RFC text. Expansion words ("Low", "Extra", "Delay", "Background", "Transport") are already in the desc and are generic vocabulary besides. "background transport" would be multi-word and generic, so not listed.
- `link-layer` -- Nearly everything a reader might associate with this tag is either a specific medium that already has its own child tag (ethernet, wifi, ppp, atm, sonet, ...) or a sublayer/component of the data link layer -- MAC and LLC are sublayers, so rule 2 excludes them (MAC is also ambiguous with message authentication code). Specific link protocols without tags, such as HDLC or LLDP, are different technologies rather than other names for 'link layer'; they were not added to covers because this tag's role is general link-layer topics with per-medium children, and putting them here would produce confident but wrong hits. 'Link layer' in the IETF/TCP-IP-model sense and the OSI 'data link layer' sense are treated as the same tag, which the desc already states.
- `lisp` -- LISP has only one name; the expansion "Locator/ID Separation Protocol" is already in the desc, and the indexed word `locator/id` makes a query of `locator` (or `locator/id`) land here, while `separation` and `protocol` are also whole desc words. No predecessor or variant name qualifies: LISP grew out of the IRTF RRG work but was never called RRG, and LISP-MN/LISP-SEC/LISP-DDT are sub-features or extensions, not other names for the protocol (rule 2). EID, RLOC, MS/MR, map-server, map-resolver, map-request/map-reply and ALT are likewise components of LISP, not synonyms -- and `map` is an existing tag (the softwire MAP-E/MAP-T technology), so nothing map-shaped may be claimed here under rule 5. Related-but-different overlay/identifier-locator technologies (ILNP, HIP, shim6, NVO3/VXLAN, NHRP) all have their own tags and fall under rule 1. Note the collision with the Lisp programming language, which occasionally appears in RFC text (e.g. early ARPANET/applications documents); that is a reason to add no further loose aliases here, not a reason to change the tag.
- `lmap` -- LMAP has exactly one name, and it is both the protocol/framework name and the working group name, so the WG-name case adds nothing. The expansion is fully reachable today: the desc indexes 'large', 'scale' (the hyphen splits the word), 'measurement', 'broadband', 'performance' and 'platforms', so a reader typing 'broadband' or 'measurement' already lands here. Candidates considered and rejected: the LMAP architecture's own components -- Measurement Agent/MA, Controller, Collector, Report Protocol, Control Protocol, Measurement Task -- are sub-features of the tag's subject (rule 2) and are mostly generic vocabulary besides (rule 3). 'MBA'/'Measuring Broadband America' and 'SamKnows' name specific national measurement programmes and vendor deployments rather than the LMAP framework, so they are different things, not other names for it. Sibling active-measurement protocols OWAMP, TWAMP and STAMP each have their own tag (rule 1/rule 5), as does ipfix, which LMAP reports can use for transport; 'ippm' is the neighbouring WG for metrics definitions and belongs with performance-measurement, not here.
- `lost` -- LoST has exactly one name, and the desc already makes 'LoST', 'Location', 'Service' and 'Translation' findable as whole words. The expanded hyphenated form 'Location-to-Service' is not a distinct name a reader would type in place of 'LoST', and its component words are already indexed from the desc. 'ECRIT' (the working group that produced LoST) covers emergency call routing broadly rather than this one protocol, so if it is wanted as a working-group alias it belongs on the parent tag emergency-services, not here. Related terms such as LoST sync, service URN, mapping and service boundary are sub-features or generic vocabulary (service URNs are covered by the existing urn tag), so none qualify.
- `lpd` -- Nothing else qualifies. 'print'/'printing' is generic vocabulary and 'printer' is already a desc word. IPP is a different printing protocol with its own tag (`ipp`), so it must not be aliased here. LPRng and CUPS are implementations/vendor stacks rather than names for this protocol and are unlikely to be reliably present in RFC text.
- `lpwan` -- lpwan is a category tag: its instances (LoRaWAN, Sigfox, NB-IoT, Wi-SUN) are different technologies, not other names for LPWAN, so they go in `covers`, not `aliases`. No genuine synonym for the tag name itself was found — "LPWAN" is already a desc word, and the expansion words (low, power, wide, area, network) are all indexed from the desc too. SCHC is excluded as an existing child tag (rule 5). NB-IoT and LTE-M are 3GPP technologies that also relate to the `cellular` tag; LTE-M was left out for lack of confidence in its corpus frequency.
- `ltans` -- LTANS has exactly one name, and the desc already makes it findable by 'ltans', 'long-term', 'archive' and 'notary'. ERS / Evidence Record Syntax (RFC 4998, 6283) and LTAP are deliverables of the LTANS work rather than other names for it, so they are components under rule 2; the ERS body of work is small enough that it does not seem to warrant a separate tag, and readers searching for it fall through to full-text search today.
- `madcap` -- No aliases proposed. MADCAP has exactly one name. 'MALLOC' is the obvious candidate but it appears as a whole word in the desc, so typing it already lands the reader here (rule 4). AAP (Multicast Address Allocation Protocol) was considered and rejected: it was an unpublished draft of the MALLOC architecture with little or no published RFC text, and the three-letter string would in any case be a poor search term. Sibling multicast tags (pim, igmp, mld, msdp, ssm) are different technologies and belong nowhere here.
- `mailing-lists` -- The desc words "Mailing", "list" and "management" already make mailing, mailinglist-style prefixes, list and listserv-adjacent queries partly reachable -- but only prefix-wise: typing "list" hits the desc word "list", while "listserv" does not, since "list" does not start with "listserv". Hence LISTSERV survives as a genuine alias. Other list software names (Majordomo, Mailman, listproc) were considered and dropped: they are product names whose presence in actual RFC text I am not confident enough about to risk a corpus rejection. List header fields (List-Id, List-Unsubscribe, List-Post) are components of the tag's subject, not other names for it (rule 2), and message-header machinery generally belongs under the sibling tag `message-format`. DMARC/ARC interaction with mailing lists is a frequent RFC topic but those are different technologies with their own tags (`dmarc`, `arc`), so they belong in neither list.
- `manet` -- Nothing qualifies as an alias: the tag's only other name, "mobile ad hoc network", is already word-for-word in the desc, so "mobile", "ad" and "hoc" all land a reader here today. Version/variant names of the child protocols (OLSRv2, AODVv2, DYMO) belong to `olsr` and `aodv`, not here. VANET and vehicular ad hoc networking belong to the existing `vehicular-networking` tag. The `autoconf` working group name is deliberately left out: it is badly ambiguous (GNU autoconf, generic autoconfiguration, and the `slaac` tag's subject) and would produce confident wrong hits. Generic terms like "mesh", "wireless mesh" and "packet radio" are either other technologies or full-text-search vocabulary.
- `map` -- MAP-E and MAP-T are the two variant forms the tag explicitly names, not separate technologies, so they are aliases rather than `covers`. Deliberately excluded: BMR/FMR/DMR (mapping rules) and PSID/port-set ID are components of MAP, not other names for it; 'mapping' and 'address' are already indexed words of the desc. 4rd (IPv4 Residual Deployment, RFC 7600) is a related but distinct softwire mechanism, so it is not an alias here; if it is judged worth a vocabulary entry it would be its own tag under ipv6-transition, but I did not see enough corpus weight to propose one.
- `markdown` -- The tag's only name is 'Markdown', already reachable from the desc word `markdown` (and `markdown` also prefix-matches nothing shorter that readers would need). Variant flavour names (CommonMark, GFM, Markdown Extensions per RFC 7764) denote the same text format family, not different technologies, so they are aliases rather than covers. 'text/markdown' is a media type registration detail, and `media-types` is the tag for that concept, so it is not claimed here.
- `masque` -- MASQUE has exactly one name and the tag's own id is already the acronym readers type; the expansion words (Multiplexed, Application, Substrate, QUIC, Encryption) are all in the desc and individually findable, so no abbreviation alias is needed. CONNECT-UDP and CONNECT-IP were considered and rejected under rule 2: they are the HTTP methods/sub-protocols defined within MASQUE, not other names for it. The working group name is 'masque', identical to the tag id, so it adds nothing. Related proxying terms a reader might type (proxy, tunnel, VPN) are either generic vocabulary (rule 3) or belong to existing tags such as `vpn` and `tunneling` (rule 5).
- `matroska` -- Matroska is a single technology, so it has no covers list. EBML is in the tag's `match` but is a component/underlying layer rather than another name for Matroska, so it is recorded as a missing tag candidate instead of an alias. Sibling codec tags (opus, vp8, vp9, ffv1) are payloads carried in Matroska, not names for it, and each already has its own tag, so none belong here.
- `md5` -- MD2 needs no entry: the desc word `md2/md4` starts with `md2`, so a reader typing MD2 already reaches this tag. The tag name itself is the only name MD5 has; `message digest` and `Message Digest 5` are already reachable via the desc words `message`/`digest`/`digests`. MD4 and MD2 are deliberately folded into this tag by the desc and are historical enough that neither looks worth its own tag, so nothing is queued under missing_tag_candidates. Sibling digests (SHA-1, SHA-2) stay out under rule 1 — `sha` exists; HMAC-MD5 constructions belong to the existing `hmac` tag.
- `mdns` -- mDNS has essentially one name, and both words a reader would type (`mDNS`, `Multicast`) are already indexed whole-word from the desc "mDNS (Multicast DNS)", so nothing survives rule 4. Vendor/umbrella names were considered and rejected: `Bonjour` and `Rendezvous` (its earlier Apple name) denote Apple's combined mDNS+DNS-SD stack rather than the mDNS protocol itself, and `Zeroconf` names the broader zero-configuration networking effort (address autoconfiguration plus name resolution plus service discovery) — per the guidance's own example these belong on `service-discovery`, and `dns-sd` is the other natural home; both are existing tags, so listing them here would also hijack traffic that should reach them. `LLMNR` (RFC 4795) is a different protocol that competed with mDNS for link-local name resolution, so rule 1 excludes it; it is thin enough (one Informational RFC) that I would not propose a tag for it either, but it is worth a `match`/note on whichever name-resolution tag the editors prefer. Component terms such as `.local`, `unicast response` or `probing/conflict resolution` are rule-2/rule-3 material and stay with full-text search — note that `special-use-domain-names` already covers the `.local` reservation angle.
- `media-types` -- This tag has essentially one name, and the words a reader would type are already indexed from the desc: 'media', 'mime', 'type' (which prefix-matches 'types'), 'registry' and 'registrations' all appear as whole words in 'Media (MIME) type registrations and registry rules'. MIME itself is excluded twice over: it is reachable in the desc and it is another tag's id (the parent `mime`), so listing it would shadow a real tag. 'Content-Type' and 'MIME-type' were considered and dropped: the hyphen splits them into 'content'/'type' and 'mime'/'type' at index time, so neither is findable as a single token, and 'Content-Type' names an HTTP header field rather than the media type registry itself. The WG names in `groups` (mediaman, justfont) were considered under the working-group rule and dropped — unlike SPRING for segment-routing, readers do not use 'mediaman' as a name for media types, and it is unlikely to survive a corpus check. 'Dublin Core' appears in `match` but is not another name for media types; it is a separate metadata element set that currently has no tag and is being swept in by the match rule. It is also multi-word, so it could not be searched today even if claimed. I have deliberately not proposed it as a missing tag candidate here since the question is about the `match` field's scope rather than about aliases for this tag, but it is worth a look in the next vocabulary review.
- `megaco` -- The only real alternative name for Megaco is the ITU-T designation H.248, and that is already reachable: the desc contains "H.248", which indexes as the whole word `h.248` (the `.` stays inside the word), so a reader typing H.248 (or H.2, H.24) lands on this tag today. The dotless form H248 would not be reachable, but I am not confident it occurs in real RFC text — Megaco/H.248 documents consistently write the dotted form — so I am not proposing it rather than risk a corpus rejection. "Media Gateway Control" is both generic vocabulary and already in the desc, and it is multi-word. MGCP is a different protocol with its own sibling tag (`mgcp`), and "gateway control protocol" as a bare phrase is generic. No category behaviour here: megaco names one protocol, so it has no `covers`.
- `message-format` -- Rejected: 'header', 'headers', 'mail header', 'message header' as generic vocabulary already reachable via the desc word 'headers' and belonging to full-text search. Rejected 'MDN' and 'DSN' as components/sub-features (rule 2); DSN's better home is smtp if it ever gets an alias. 'email' and 'mime' are other existing tag ids and are excluded by rule 5. No covers list: this tag names a single specification lineage, not a category.
- `messaging` -- The tag is a broad category whose major instances all already have their own tags (email, mime, instant-messaging, x400, fax, paging, netnews, edi, uucp), so rule 1/rule 6 keep them out of both lists. No genuine synonym exists for 'messaging' itself: 'message', 'message systems' and 'store-and-forward' are generic vocabulary (rule 3) and are in any case already whole-word reachable from the desc. 'IM' and 'chat' belong to the existing instant-messaging tag, not here. SMS is proposed in covers only; I did not add it to missing_tag_candidates because RFC-series coverage of SMS is thin (mainly URI scheme and transport bindings) and probably does not justify a tag.
- `mgcp` -- Megaco/H.248 is a distinct successor protocol with its own tag (`megaco`), so H.248 and Megaco are deliberately not listed here. 'MGC' / 'media gateway controller' is generic vocabulary plus a component role, not another name for the protocol. The PacketCable NCS profile was considered but is a profile/instance of MGCP rather than a variant name for it, and its corpus presence is thin.
- `mib` -- Deliberately excluded: MIB-II / MIB-2 (a reader would type them, but the hyphen is a word separator on both sides of the index, so they cannot be made findable until search handles punctuation — worth revisiting with the multiword fix). Also excluded as components of the tag's subject rather than other names for it: textual convention/TC, OID, object identifier, conformance statement, MODULE-IDENTITY, ifTable/ifStack (the last already handled by `match`). ASN.1 is skipped under rule 5 — `asn1` is an existing tag. Note that the plural `MIBs` is not findable today either, since prefix matching is directional and the indexed word is `mib`; that looks like a stemming gap in the search rather than something the aliases field should paper over, so I have not claimed it here.
- `mime` -- MIME has essentially one name, and the desc already indexes both `mime` and `multipurpose`, so a reader typing either lands here today. Rejected candidates: `quoted-printable`, `multipart`, `content-transfer-encoding`, `MIME-Version`, `content-type` are components or sub-features of MIME body structure (rule 2) or generic vocabulary (rule 3), not other names for it; `base64` and `s-mime` are existing tag ids (rule 5); `media-types` is the existing child tag and is where Content-Type/subtype registration questions belong; `ODA` (Office Document Architecture, from the match expression) is a different, competing document technology (rule 1) and is too marginal in the corpus to be worth its own tag; `MHTML` names the MIME-encapsulated aggregate HTML document format (a distinct format with its own working group), not a synonym for MIME, so it is out under rule 1.
- `mld` -- IGMP is the IPv4 counterpart, a different protocol with its own tag (`igmp`), so it is excluded under rules 1 and 5 even though the two are specified together in several RFCs. `magma` is the working group id and is not used by readers as a name for the protocol itself. "MLD snooping" and "Listener Report" are sub-features/message types (rule 2). The plain expansion "Multicast Listener Discovery" is already reachable word-by-word through the desc.
- `mls` -- MLS has only one name; the tag id, the working group name and the expansion in the desc all coincide, and 'Messaging Layer Security' is already indexed word by word in the desc so no spelled-out form is needed. TreeKEM, MLSPlaintext/MLSCiphertext, the ratchet tree and the Delivery Service are components or sub-features of MLS (rule 2), not other names for it. Signal/Double Ratchet, OTR and Sender Keys are different group-messaging technologies (rule 1), not aliases; the generic term 'end-to-end encryption' is area vocabulary (rule 3). 'messaging' and 'instant-messaging' are existing tag ids (rule 5).
- `mobike` -- MOBIKE has a single name; the tag id already matches what a reader would type. Expansions like "IKEv2 Mobility and Multihoming" are multi-word and their component words (mobility, multihoming, IKEv2) are either generic vocabulary or point at other tags (`ike`, `multihoming`, `ip-mobility`), so none qualify as aliases here. RFC 4555's companion protocol-design document is still just MOBIKE, so there is no predecessor or variant name to record.
- `mobile-ipv4` -- Deliberately excluded: home agent, foreign agent, care-of address, registration extensions and DSMIPv4 (dual-stack Mobile IPv4) as components or sub-features of the tag's subject (rule 2). The bare acronym 'MIP' is left out because it is used for both Mobile IPv4 and Mobile IPv6 in RFC text and would be an ambiguous hit; if it is ever wanted it should be considered jointly with the sibling mobile-ipv6 tag.
- `mobile-ipv6` -- Deliberately excluded: HMIPv6 (Hierarchical Mobile IPv6) and FMIPv6 (Fast Handovers for Mobile IPv6) are extensions/variant protocols from the mipshop work rather than other names for Mobile IPv6 itself, so rule 1/2 keeps them out; they are also not substantial enough on current evidence to propose as tags. 'MIP' alone was excluded as ambiguous between this tag and the sibling mobile-ipv4. The group names 'mext' and 'mipshop' were excluded because readers use them as WG names for the mobility work generally, not as names for this protocol; 'mip6' is the exception since it doubles as the protocol abbreviation. Note that 'NEMO' and 'PMIPv6' terms belong to the existing sibling tags nemo and pmipv6, not here.
- `mospf` -- MOSPF has exactly one name. 'OSPF' is excluded by rule 5 (it is an existing tag id) and would in any case be a different protocol. Sibling multicast routing protocols such as DVMRP or CBT are different technologies, not aliases, and belong under the 'multicast' parent rather than here.
- `mpls` -- MPLS has one name, and the desc already indexes `mpls`, `multiprotocol`, `label` and `switching`, so the expansion and its parts are reachable today. Predecessor proposals sometimes associated with MPLS (Cisco Tag Switching, Ipsilon IFMP/IP Switching, Toshiba CSR, IBM ARIS) are distinct pre-standard technologies rather than other names for MPLS, so rule 1 excludes them; none looks substantial enough for its own tag either. Components and sub-features (LSP, LSR, LER, FEC label stack, MPLS-TE, entropy label) are rule-2 exclusions; note that `fec` already exists as a tag id (forward error correction) and `traffic-engineering`, `rsvp-te`, `sr-mpls`, `mpls-tp`, `ldp`, `gmpls` and `pseudowire` cover the neighbouring ground.
- `mpls-tp` -- The desc "MPLS-TP (MPLS Transport Profile)" indexes as the words mpls, tp, mpls, transport, profile, so the tag id itself carries the MPLS-TP query. Deliberately excluded: TP alone (generic/ambiguous fragment); PWE3, pseudowire, LSP, LSR, G-ACh, GAL, BFD, OAM (components or separate technologies — pseudowire, bfd, oam and gmpls all have their own tags, rule 1/2/5); PTN and OTN (different transport technologies, not other names for MPLS-TP). Caveat on T-MPLS: if the search index splits on hyphens the same way it splits the desc, the stored alias would index as "t" and "mpls" and the hyphenated query would not land — worth checking against the indexer, since the same concern applies to the tag id mpls-tp.
- `mptcp` -- The tag has one name. Both words a reader would type -- `MPTCP` and `multipath` -- are whole words in the desc "Multipath TCP (MPTCP)" and already land on this tag by prefix match. No superseded or version-variant name is in real use (RFC 6824/8684 use only "Multipath TCP"/"MPTCP"); the hyphenated "MP-TCP" is not RFC-corpus vocabulary and would be a rejection. Sub-features such as MP_CAPABLE, MP_JOIN, ADD_ADDR and subflow are components (rule 2), and the plain-TCP and tcpcrypt siblings are separate tags (rules 1 and 5).
- `mrcp` -- ASR, TTS and SIV (speech recognition, text-to-speech, speaker verification) are the media resource types MRCP controls, i.e. sub-features/other technologies, not other names for MRCP — rules 1 and 2 keep them out of both lists, and they are not substantial enough as RFC-series subjects to propose as tags. MRCP is a single protocol rather than a category, so it has no `covers`.
- `msdp` -- MSDP has a single name; the expansion (Multicast Source Discovery Protocol) is already word-indexed in the desc. Related terms such as SA (Source-Active) messages and the MSDP mesh group are components of the protocol (rule 2), and PIM-SM, anycast-RP and SSM are separate technologies with their own tags (pim, anycast, ssm) under rules 1 and 5.
- `msrp` -- Nothing else qualifies. The full expansion (Message Session Relay Protocol) is already word-searchable in the desc. 'MSRP relay' and 'relay' are components/generic vocabulary. CPIM and SIMPLE are related but distinct: `simple` already exists as its own tag, and CPIM is a separate message format, not another name for MSRP.
- `mud` -- MUD (RFC 8520) has exactly one name. Both the acronym and the expansion are already words in the desc — typing `MUD`, `manufacturer`, `usage` or `description` lands on this tag today, so nothing survives rule 4. Candidates considered and rejected: `mudfile`/`MUD file`, `MUD URL`, `MUD manager`, `MUD controller` are components or roles within the architecture (rule 2); `ACL` and `YANG` are different technologies with their own homes (`yang` is an existing tag id, rule 5). No superseded or vendor name exists for this technology.
- `multicast` -- IGMP, MLD, PIM, MSDP, MOSPF, SSM, AMT, BIER and MADCAP are all existing tags (children here), so none of them may be listed under rule 5 — they are the right destinations for those queries. Anycast and broadcast are separate things and are deliberately excluded; anycast already has its own tag. The morphological variant 'multicasting' was considered and dropped: it is a grammatical form rather than a distinct name, and adding grammatical inflections is not what the field is for. Group-address, RP, rendezvous point, group membership and similar terms are components or generic vocabulary (rules 2 and 3) and are left to full-text search. If ASM is judged too fine-grained to display as scope, dropping it costs only the ASM query, which would then fall through to full-text search correctly.
- `multicast-security` -- The tag reads as a category (an area of key management and source authentication work) rather than a single technology, so the named MSEC protocols are proposed under covers, not aliases. MIKEY was deliberately left out of both lists: it is key management for SRTP as much as for multicast groups, so if it is not given its own tag the better home may be `srtp`. Components and sub-features of the area (rekeying, GSA, group controller/key server, GCKS) were excluded as component or generic vocabulary.
- `multihoming` -- The hyphenated form "multi-homing" appears in older RFC text, but the search splits it on the hyphen into "multi" and "homing" and never splits a query, so it cannot usefully be listed as a single-token alias; it would need the same search fix as multiword entries. The inflection "multihomed" was considered and dropped: it is a form of the tag's own name rather than a variant name, and adding grammatical inflections is not what this field is for. SHIM6 is deliberately omitted -- it is an existing tag id (and this tag's child), so listing it would shadow a real tag. NPTv6 and similar prefix-translation mechanisms are different technologies, not other names for multihoming.
- `mvpn` -- The tag has essentially one name: MVPN, which is the id itself, and its expansion "Multicast VPN" is already the first words of the desc (`multicast`, `vpn` both index and both match prefix queries). Candidates considered and rejected: MCAST-VPN (the BGP SAFI/address-family name from RFC 6514 — it names the address family rather than the technology, and as a hyphenated string it tokenizes to `mcast`/`vpn` so it could not be found today anyway; `mcast` alone is just an abbreviation of generic `multicast`); PMSI, I-PMSI, S-PMSI, MI-PMSI, MDT, Default MDT (components/sub-features of MVPN, rule 2); NG-MVPN and "Rosen MVPN" (vendor/informal labels for particular MVPN designs, multi-token and not the tag's subject as a whole — `Rosen` alone is a surname and would be a poor search key); PIM, mLDP, BIER, RSVP-TE P2MP (different technologies used to build the provider tunnels — `pim`, `bier`, `rsvp-te` and `mpls` all exist as their own tags, so rules 1 and 5 both apply). MVPN names a single technology, not a category, so it has no `covers`.
- `naming` -- `naming` is a broad topic tag with no genuine alternate name. Candidates considered and rejected: `identifiers`/`namespace`/`name-service` are generic vocabulary describing the area rather than naming it (rule 3), and full-text search already serves them; `name resolution` is the desc's own phrasing and in any case multi-word, with `resolution` already indexed from the desc. `urn`, `uri`, `dns`, `hostnames`, `handle-system`, `uuid` and the other children are existing tag ids (rule 5) and are where readers typing those terms should land. No `covers` list: nearly every concrete naming system under this tag already has its own child tag, so the tag is not standing in for anything unlabelled.
- `nat` -- Deliberately excluded: NAT64 and NAT-PT (NAT-PT is the deprecated predecessor of NAT64, so it belongs with the existing nat64 / ipv6-transition tags, not here); NAT444 and LSN/CGN (deployment models for the child tag cgn); ALG, binding, endpoint-independent mapping, hairpinning (components/sub-features, rule 2); STUN/TURN/ICE and nat-traversal (separate existing tags). 'address translation' as a phrase is already reachable via the desc words 'address' and 'translation', so no multiword entry is warranted.
- `nat-traversal` -- Deliberately empty otherwise. ICE, STUN and TURN are excluded by rule 5 (they are this tag's own children and existing tag ids). "NAT-T" was considered and rejected: in RFC usage it names the IPsec/IKE UDP-encapsulation mechanism, which is a different technology belonging near `ike`/`ipsec`, not the interactive media NAT traversal this tag covers. "UDP hole punching" is a technique described within these documents (generic/component vocabulary, and multi-word), so it is left to full-text search. Plain "NAT" needs nothing here: it belongs to the `nat` tag, and the desc word "NATs" already makes this tag reachable for that query anyway.
- `nat64` -- NAT64 has essentially one name, so no alias qualifies. DNS64 is a companion technology and already has its own tag id (`dns64`), so rules 1 and 5 both exclude it. 464xlat is a sibling tag, not a variant name. Terms like 'translation', 'translator' and 'address family translation' are generic vocabulary (rule 3). 'NAT64' itself is already the tag id and is the first word of the desc.
- `ncp` -- The tag id 'ncp' is itself the only real name for this protocol, so there is nothing to add. Deliberately excluded: 'host-host' and 'logger protocol' (descriptive phrases from `match`, not alternative names, and generic-vocabulary-adjacent); 'ICP'/'Initial Connection Protocol' (a component/companion protocol, rule 2); 'ARPANET' (the parent tag id, rule 5). Note that 'NCP' is also the name of PPP's family of Network Control Protocols (IPCP, IPV6CP, etc.) — a different technology belonging to the `ppp` tag — which is a reason to keep this alias list tight rather than broaden it.
- `nea` -- PA-TNC, PB-TNC, PT-TLS and PT-EAP are the individual protocols within the NEA architecture (rule 2 components), so they are not listed. NAC (Network Access Control) is a broader, different access-control notion rather than another name for endpoint posture assessment, so it is excluded under rule 1; posture-collection/evaluation work of the later SACM kind belongs to the existing `sacm` tag. 'endpoint', 'assessment' and 'posture' are all already reachable by searching the desc.
- `neighbor-discovery` -- Deliberately excluded: DAD (Duplicate Address Detection), NUD, RA/Router Advertisement, NA/NS — all components or sub-features of ND (rule 2). ARP is a different protocol and already has its own tag `arp`; IPv6 ND's ARP-replacement role should not make ARP searchable here. SEND/SEcure Neighbor Discovery is the existing child tag `send`, and 'neighbor discovery' for 6LoWPAN belongs with `6lowpan`/this tag jointly rather than as a separate alias.
- `nemo` -- NEMO has essentially one name. The desc "NEMO (Network Mobility)" indexes as `nemo`, `network` and `mobility`, so both the acronym and the expansion already land a reader here. Candidate variants were rejected: "Network Mobility Basic Support"/"NEMO BS" is a multi-word phrase whose distinctive words are already reachable via `network`/`mobility`, and its acronym form is not reliably attested in RFC text. Components and related terms of NEMO deployments -- MR (mobile router), MRHA tunnel, prefix delegation, NEMO extended support -- are components or generic vocabulary (rules 2 and 3), not other names for the tag. MONAMI6 is a different work item (multiple interfaces in IPv6), not a synonym for NEMO. Siblings mobile-ipv6 and pmipv6 are different technologies and have their own tags (rules 1 and 5). NEMO names a single protocol, not a category, so it has no `covers`.
- `netbios` -- Rejected: NBNS/NBDD/NBSS (component name, datagram and session services of the tag's subject, rule 2); SMB and CIFS (different file-sharing technology layered above NetBIOS, rule 1 - too thin in the RFC corpus to be worth a tag of its own); WINS (vendor name for a NetBIOS name server implementation, i.e. a component instance rather than another name for NetBIOS itself). 'NetBT' was considered but is a Microsoft driver name unlikely to appear in RFC text, so it is omitted.
- `netblt` -- Correction: the aliases array above should be empty. NETBLT has exactly one name, and the expansion 'NETwork BLock Transfer' is already present in the desc word by word (a reader typing 'network', 'block' or 'transfer' reaches it, and those are generic vocabulary anyway). No superseded name, version variant, vendor name or working-group name applies.
- `netconf` -- NETCONF has one name and the tag id already matches it; the desc spells out "Network Configuration Protocol" so "Network" and "Configuration" are reachable as whole words. RESTCONF is a child tag and YANG, NETCONF-over-SSH/TLS transports and NETCONF notifications are components or separate tags, so none belong here. The NETCONF working group name is identical to the tag id, so no working-group alias is needed.
- `netnews` -- NNTP is excluded: it is an existing tag id (rule 5) and is the child of this tag. Generic terms from `match` such as "news" or "news article" are ordinary vocabulary (rule 3) and multi-word, so they stay with full-text search. The working group name USEFOR was considered under the SPRING->segment-routing pattern but rejected: unlike SPRING, readers do not use "usefor" as a name for the technology itself, only as a WG label.
- `network-graphics` -- No confident aliases. The tag's own name is the only name for it, and a reader typing "graphics" or "graphic" already lands here via the desc word `graphics` (prefix match also catches "graphic"). Considered and rejected: "NGP"/"NGG" (Network Graphics Protocol / Network Graphics Group) — plausible-looking expansions of the ARPANET-era graphics RFCs, but I am not confident either acronym actually appears as a standalone token in RFC text, and the guidance is explicit that an invented acronym only costs a rejection. "raster", "vector", "display", "plotting" are generic vocabulary (rule 3) and belong to full-text search. Later image formats such as PNG, GIF and JPEG were rejected under rule 1: they are different technologies from the ARPANET-era network graphics protocols this tag sits under (path arpanet/network-graphics), and mapping them here would produce a confidently wrong hit for a reader looking for RFC 2083 and friends; if the vocabulary ever wants those, they want their own tag rather than an alias here, so I have deliberately not filed them as missing_tag_candidates for this tag either.
- `network-management` -- Deliberately kept minimal. 'NMS' and 'NOC' were rejected as generic vocabulary (rule 3) — they describe a system or a facility in the area rather than naming it, and full-text search already serves them. 'TMN' (Telecommunications Management Network) was rejected as a different, ITU-T-specific architecture rather than another name for this tag. 'network operations', 'operations and management' and 'OAM&P' are multi-word and in any case already reachable: the desc contains 'operations', 'operational' and 'management' and the search matches word prefixes. 'OAM' is excluded by rule 5 — it is an existing sibling tag. Component terms such as SMI, MIB modules and 'agent' belong to mib/snmp, not here.
- `nfs` -- pNFS (parallel NFS, RFC 5661 ff.) was considered and left out under rule 2: it is a sub-feature/extension of NFSv4.1 rather than another name for NFS. NFILE (RFC 1037) appears in the tag's `match` but is a distinct historical file access protocol, not a name for NFS, so rule 1 keeps it out of both lists; it is too small and dated to warrant its own tag. `onc-rpc` already exists for the underlying RPC/XDR layer, so Sun RPC and related terms belong there, not here. The multiword entry is redundant today and should only be revisited if phrase search is added.
- `nhrp` -- NBMA is deliberately omitted: it appears as a whole word in the desc, so typing it already lands here. NARP (NBMA Address Resolution Protocol, RFC 1735) was considered as a predecessor-name alias but is a separate protocol specification rather than an earlier name for NHRP, so rule 1 governs; it is too small to warrant its own tag. DMVPN is likewise excluded as a distinct vendor solution built on top of NHRP (plus mGRE and IPsec), not another name for it. Components such as NHS (Next Hop Server) are excluded under rule 2.
- `nimrod` -- Nimrod has a single name; the desc word 'Nimrod' already makes the tag findable. Nothing else denotes the same architecture.
- `nntp` -- NNTP has essentially one name, and the desc already makes `nntp` findable. `Usenet` and `netnews` are names for the news system/service rather than for this transfer protocol, and `netnews` is itself a tag id (this tag's parent), so Usenet belongs on `netnews`, not here. `NNRP`/`NNTPS` were considered and dropped: the former is a component/variant reader role, the latter a transport-secured variant that reads as a sub-feature rather than a distinct name for the protocol.
- `nomcom` -- The tag has essentially one name. "NomCom" and "nominating" are both already whole words in the desc, so typing either lands the reader here today (rule 4). "Nominating Committee" as a phrase is not searchable but is fully reachable via either of its words, so it does not need a multiword entry. Related terms that come up in the same RFCs -- recall, confirmation, IESG/IAB selection, ISOC Board of Trustees selection -- name other parts of the leadership-selection process rather than the NomCom itself, and "nominations"/"nominee" are generic vocabulary (rule 3). No abbreviation shorter than NomCom is in real use.
- `norm` -- NORM has no superseded or variant name in common use; the protocol is referred to only as NORM. 'NACK' is not a synonym for the tag anyway (it names a component mechanism, rule 2) and is in any case already reachable, since the desc word 'NACK-Oriented' splits on the hyphen into the indexed words 'nack' and 'oriented'. 'Reliable multicast' is the parent tag reliable-multicast, not an alias here (rule 5).
- `nsis` -- NSIS has a single name; the desc already indexes 'nsis', 'next', 'steps' and 'signaling', so the expansion is reachable. GIST (General Internet Signalling Transport), NTLP, NSLP, QoS NSLP and NATFW NSLP are all components/layers of the NSIS suite rather than other names for it, so they are excluded under rule 2; none seems substantial enough on its own to warrant a separate tag alongside nsis.
- `ntp` -- `ntp` is a single technology, not a category, so it has no `covers`. Deliberately excluded: NTS (extension, listed as a missing tag candidate); Roughtime and the Time/Daytime protocols of RFC 868/867 (different technologies — the latter belong with `small-services`); PTP/IEEE 1588 (sibling tag `ptp`); "time synchronization" and "clock" (generic vocabulary, and the parent tag `time-synchronization` already owns the phrase).
- `nvgre` -- NVGRE has a single name, fully covered by the desc (typing NVGRE, or the expanded words Network/Virtualization/Generic/Routing/Encapsulation, already lands here). The base encapsulation belongs to the existing `gre` tag, and the sibling overlay encapsulations vxlan and geneve are different technologies with their own tags, so neither is an alias here. Nothing to propose.
- `oam` -- Deliberately excluded: the expansion words Operations/Administration/Maintenance are already whole words in the desc, so they are reachable. `LSP ping`, `CFM`, `Y.1731` and `BFD` are specific OAM mechanisms, not other names for OAM (rule 2), and `bfd` is an existing tag; MPLS-specific OAM queries belong to `mpls`/`mpls-tp`. `OA&M` was considered as a second spelling variant but I am not confident enough it occurs in current RFC text to risk the corpus check.
- `oauth` -- Deliberately excluded: PKCE, DPoP, bearer token, token introspection and device flow are extensions/components of OAuth (rule 2), not other names for it. OpenID Connect / OIDC is a distinct identity layer built on top of OAuth (rule 1) and is not an alias; it also has little RFC-series presence, so I am not proposing it as a missing tag. JWT and GNAP are existing tags (rule 5). 'authorization' alone is generic vocabulary and is already its own tag.
- `oblivious-dns` -- OHTTP / Oblivious HTTP is a different technology with its own tag (`oblivious-http`) and belongs there, not here. `oblivious` alone already lands on this tag via the desc, so it is redundant. The earlier Princeton-style "Oblivious DNS" (ODNS) proposal was considered as a predecessor-name alias, but the bare abbreviation ODNS is rare in RFC text and risks colliding with unrelated uses, so it is not proposed.
- `oblivious-http` -- Oblivious DoH / ODoH is the sibling technology and already has the `oblivious-dns` tag, so it must not be listed here (rule 5). Component terms from the OHTTP architecture (relay, gateway, encapsulated request/response, HPKE) are components or generic vocabulary and are excluded; HPKE in particular is a separate cryptographic technology.
- `ocsp` -- OCSP has exactly one name, and the desc already indexes both `ocsp` and the expansion words (`online`, `certificate`, `status`, `protocol`), so nothing further is needed. Candidates considered and rejected: `OCSP stapling` / `TLS Certificate Status Request` is a sub-feature of the tag's subject (rule 2) and also multi-word; `CRL` is a different certificate-revocation technology, not another name for OCSP (rule 1) — if it warrants a home it belongs under `pki`, not here; `revocation` is generic area vocabulary (rule 3); `OCSPv2` / `lightweight OCSP` are not established names in RFC text. Siblings `cmp`, `est`, `acme`, `certificate-transparency` cover distinct protocols and are separate tags (rules 1 and 5).
- `olsr` -- NHDP (MANET Neighborhood Discovery Protocol) and MPR (multipoint relay) were considered and rejected: NHDP is a separate protocol used by OLSRv2 rather than another name for it (rule 1), and MPR is a sub-feature (rule 2). Plain `OLSR` is already reachable via the desc.
- `onc-rpc` -- XDR, RPC and ONC are all already reachable: they appear as whole words in the desc, so a reader typing any of them lands here today. RPCSEC_GSS, rpcbind and portmapper are components/sub-features of ONC RPC (rule 2), and RPCSEC_GSS in particular is better served by the existing `gssapi` tag. TI-RPC was considered as a variant form but I am not confident enough of its occurrence in RFC text to propose it.
- `openpgp` -- Considered and rejected: 'GPG' (same intent as GnuPG but I am less confident it occurs as a standalone token in RFC text — worth adding if a corpus check confirms it); 'PGP/MIME' and 'OpenPGP Web Key Directory'/'WKD' (components/bindings of the subject, rule 2); 'keyserver', 'key', 'signature', 'encryption' (generic vocabulary, rule 3); 'S/MIME' (a different technology with its own tag `s-mime`, rule 1/5). 'Pretty Good Privacy' needs no multiword entry since 'pretty', 'good' and 'privacy' are each already indexed from the desc.
- `operational-security` -- The other listed group, GRIP (Guidelines and Recommendations for Security Incident Processing), names incident-handling work rather than this tag's subject; if it is wanted as a search term its proper home is the existing `incident-response` tag, not here. Deliberately excluded: 'BCP38'/'ingress filtering' (a specific practice/instance, and source-address validation is already covered by `savi`), and generic vocabulary such as 'network security', 'hardening' and 'filtering'.
- `opes` -- OPES has only one name, and every word of its expansion (open, pluggable, edge, services) is already indexed from the desc, so no alias is needed. Deliberately excluded: OCP (the OPES Callout Protocol, RFC 4037) and the OPES processor/callout server roles are components of the architecture, not other names for it (rule 2). ICAP (Internet Content Adaptation Protocol, RFC 3507) is a distinct, separately specified protocol that predates and influenced OPES but is not a former name for it, so it fails rule 1; its RFC footprint is small enough that I would not propose a tag for it either, but a reader typing ICAP correctly falls through to full-text search today.
- `opus` -- Opus has exactly one name, and the desc word `opus` already matches the query `opus`. The obvious candidates SILK and CELT were rejected: they are the two internal coding layers/modes of Opus (RFC 6716) that originated as separate codecs, so they are sub-components of the tag's subject under rule 2 rather than other names for Opus itself — a reader typing CELT wanting the Xiph codec is better served by full-text search. `Ogg` was also rejected: it is a container format (RFC 7845 encapsulation), a different technology from the codec, and closer in spirit to `matroska`.
- `oscore` -- OSCORE has a single name, and the tag id itself plus the expansion in the desc already cover every string a reader would type. Related terms are disqualified: OSCoAP (the pre-standardisation working name) is not reliably present in published RFC text, so it is not proposed; EDHOC, ACE and COSE are different technologies with their own tags (`edhoc`, `ace`, `cose`); Group OSCORE and OSCORE-capable proxies are sub-features, not alternative names.

- `owamp` -- OWAMP has one name. - `paging` -- TPC.INT (from `match`) was considered and left out: it names the remote-printing/fax-delivery domain experiment (RFC 1528/1703/2304), which sits closer to the `fax` tag than to paging, and as a dotted string it is an unlikely lookup query. Radio-side paging air-interface protocols (POCSAG, FLEX) were not proposed because I am not confident they appear in RFC text. `paging` is treated here as a small category ("Radio and network paging protocols"), which is why SNPP is in `covers` rather than `aliases` — it is a different thing the tag stands in for, not another name for it; it is not proposed as a missing tag since it is essentially a single-RFC subject.
- `pake` -- No aliases: PAKE has exactly one name, and the expansion "Password-Authenticated Key Exchange" is already reachable word by word from the desc (`password`, `authenticated`, `key`, `exchange`). The specific protocols above are distinct things the category tag stands in for, so they belong in `covers`, not `aliases`. J-PAKE (RFC 8236) was deliberately omitted: the hyphen means a reader typing "J-PAKE" matches no indexed word either way, so listing it would gain nothing; it would need the multi-word/punctuation search fix first. EAP-PWD and other PAKE-based EAP methods were left out as they belong under `eap`. SRP is also relevant to `tls` (TLS-SRP) if that tag ever grows a covers list.
- `pana` -- PANA has one name; the acronym and its expansion are both in the desc and already searchable. Related terms like EAP, AAA and RADIUS are different technologies with their own tags (rule 1 / rule 5).
- `password-hashing` -- The tag names a family of functions rather than one protocol, so the concrete functions go in `covers`, not `aliases`. `password hashing` and `memory-hard` are already reachable from the desc (the desc word `memory-hard` splits on the hyphen into `memory` and `hard`), so nothing there needs restating. Deliberately excluded: HKDF and generic `KDF`, which are key derivation but not password hashing and belong to `key-management`; and the sibling `pake`, since password-authenticated key exchange is a different technology from password storage hashing. `sha`, `md5` and `hmac` are excluded under rule 1 — they have their own tags.
- `paws` -- PAWS has exactly one name; the expansion is fully spelled out in the desc, where 'Protocol', 'Access' and 'White-Space' are all indexed as prefix-matchable words ('White-Space' splits on the hyphen into 'white' and 'space', so both are reachable). Considered and rejected: 'TVWS' / 'TV white space' names the spectrum resource rather than the database-access protocol (rule 1, and the multi-word form is unsearchable anyway), and confidence that the bare acronym occurs in the PAWS RFCs is not high enough to risk a corpus rejection; 'WSDB' likewise names the database, a component of the system rather than a variant name for the protocol (rule 2), with the same corpus uncertainty; 'whitespace' as one token is generic vocabulary (rule 3) and is not how the RFCs spell it. The 'match' field's white.space pattern governs tagging only and needs no alias counterpart here.
- `pce` -- PCEP itself is already findable: it appears as a whole word in the desc, so typing it lands on this tag today (rule 4). PCC (Path Computation Client), PCE-CC, stateful PCE, LSP-DB/TED and BRPC are components, sub-features or procedures within the PCE architecture, not other names for it (rule 2). This tag names a single technology, so it has no `covers`.
- `pcn` -- PCN has a single name; the tag id and the expansion are both already in desc (`pcn`, plus `pre`/`congestion`/`notification` as hyphen-split words), so nothing survives rule 4. Closely related terms are separate technologies with their own tags (`ecn`, `diffserv`, `intserv`, `rsvp`, `aqm`), and admission-control / flow-termination vocabulary is either generic (rule 3) or a sub-feature of PCN (rule 2).
- `pcp` -- The desc already indexes `pcp`, `port`, `control` and `protocol`, so the tag's own name needs no alias. UPnP IGD is deliberately excluded: it is a separate protocol from a different body, not a predecessor name for PCP, so it would be a confidently wrong hit (rule 1); if it is judged substantial it belongs under `nat` or as its own tag, not here. Note also that `PCP` in RFC text frequently means Priority Code Point (IEEE 802.1Q) as well as Port Control Protocol — that ambiguity is in `match`, not something aliases can fix.
- `pem` -- PEM has essentially one name, and typing "PEM", "privacy", "enhanced" or "mail" already lands on the tag via the desc, so nothing survives rule 4. Two things considered and rejected: (1) "MOSS" (MIME Object Security Services, RFC 1848) is PEM's MIME-based successor but is a distinct technology, not another name for PEM, so rule 1 excludes it; it is too thin a body of work to propose as its own tag. (2) "PEM" is also widely used today for the textual certificate/key encoding (RFC 7468, "PEM format"), which readers may be searching for; that is a naming collision rather than an alias, and such queries arguably belong nearer `x509`/`pki` — worth a human decision but not something to encode in this field.
- `performance-measurement` -- Children owamp, twamp, stamp and lmap are existing tag ids, so they are excluded by rule 5 even though readers searching them want this area; the tag tree already routes them. RTFM (Realtime Traffic Flow Measurement, RFC 2722/2724) is listed among this tag's groups but names flow measurement/accounting rather than performance metrics — the better home is `ipfix`, so it is not claimed here. Likewise XRBLOCK produced RTCP Extended Report block formats and belongs with `rtcp`. Generic terms from the desc (metrics, active, passive, measurement) are either already reachable or plain area vocabulary.
- `pidf` -- PIDF has exactly one name, and the desc word 'pidf' already makes it findable, as do 'presence', 'information', 'data' and 'format'. Considered and rejected: PIDF-LO (the Location Object profile) and RPID (Rich Presence Extensions) are extensions/profiles built on PIDF rather than other names for it (rule 2); PIDF-LO in particular is a location-conveyance format whose readers are better served by the existing `geolocation` tag, so it should not be redirected here. 'presence' alone is generic vocabulary and is in any case already reachable via the desc. CPIM is a different specification (the Common Profile for Instant Messaging) and not a variant name for PIDF.
- `pie` -- The desc already indexes `pie`, `proportional`, `integral`, `controller`, `enhanced`, `queue`, `management` and `algorithm` as whole words, so every ordinary way of typing this tag's name already lands here. PIE has exactly one name; the expansion is in the desc and the acronym is the id. PI2 and DualPI2 were considered and rejected under rule 1: they are separate AQM algorithms (RFC 9332), not other names for PIE, and a reader typing them should fall through to full-text search rather than be sent confidently to `pie`. DOCSIS-PIE was also considered: it is the DOCSIS-specific variant/profile of the same algorithm, but the string is hyphenated with `docsis` leading, so a reader typing it would more plausibly want `docsis`, and typing `PIE` alone already works; not worth claiming here.
- `pim` -- The tag has essentially one name. 'PIM' and 'Protocol', 'Independent', 'Multicast' are already indexed whole words in the desc, so plain PIM already lands here. The only real variant names are the mode qualifiers (PIM-SM, PIM-DM, BIDIR-PIM); all are hyphenated and therefore unfindable as single-token queries today, so they are parked under multiword rather than aliases. BIDIR-PIM is the third such name and would belong in the same list if it is judged a variant name rather than a sub-feature. PIM-SSM is deliberately omitted: readers typing it want the existing 'ssm' tag. Components such as RP, BSR, RPF, Join/Prune and Register are sub-features of PIM and belong to full-text search, not aliases.
- `pki` -- pki names a single technology, so it has no covers. Deliberately excluded: CA, CRL, PKCS, trust anchor, certification path (rule 2, components/sub-features -- PKCS/CA/CRL are the rule's own examples); X.509, OCSP, CMP, EST, SPKI, ACME, certificate-transparency (rule 5 -- each is an existing tag id, and the first is also this tag's child x509); 'certificate' and 'trust' (rule 3, generic vocabulary). LAMPS and WPKOPS were considered as working-group aliases but rejected: LAMPS spans S/MIME as well as PKIX and is not used as a name for the technology itself, and WPKOPS names an operational-practices effort rather than the subject; neither is how a reader would search for PKI. 'PKI4IPSEC' is likewise a WG label, not a term readers use for the technology.
- `pmipv6` -- PMIP is not listed: the desc word `pmipv6` starts with `pmip`, so typing it already lands here. LMA, MAG and LMD are components of the architecture, not other names for it (rule 2). NETEXT is a working group name but denotes extensions to PMIPv6 rather than the technology itself, so it is left out. Proxy Mobile IPv4 is a different technology and is deliberately not aliased here.
- `pmtud` -- PMTU alone is already reachable: the desc word `pmtud` starts with `pmtu`. MTU alone is likewise a desc word and in any case generic vocabulary. Fragmentation, MSS and ICMP 'packet too big' were considered and rejected as generic vocabulary or as belonging to other tags (`icmp`).
- `policy-management` -- Considered and rejected: COPS and COPS-PR (COPS is an existing tag id — rule 5; the right home for those terms is `cops`). PIB (Policy Information Base), PDP and PEP are components/sub-features of policy frameworks, not other names for this tag (rule 2). 'policy', 'policy-based', 'provisioning' and 'information model' are generic vocabulary or already reachable from the desc words 'Policy-based', 'management', 'information', 'models' (rules 3 and 4). The WG names 'policy' and 'snmpconf' were considered under the working-group-name allowance, but 'policy' is generic and prefix-matches the desc word 'Policy-based' already, and 'snmpconf' is a configuration-management WG name that readers are as likely to mean for `snmp`/`netconf`, so neither is proposed. QPIM (QoS Policy Information Model) was considered for `covers` but overlaps `qos` and is too narrow to be worth a confident hit.
- `pop3` -- Bare 'POP' is deliberately omitted: the desc word 'pop3' starts with 'pop', so typing POP already lands on this tag (rule 4). 'Post Office Protocol' is both multi-word and already whole-word indexed in the desc, so it needs no entry. Sub-features such as APOP, UIDL, SASL and STLS are components of the protocol, not other names for it (rule 2); SASL has its own tag.
- `post-quantum` -- Typing 'quantum' or 'post' already lands here because the desc hyphen splits 'Post-Quantum' into two indexed words, so neither needs listing. Specific algorithms went to `covers` rather than `aliases`: they are different things, not other names for this tag, and none has a tag of its own (unlike sha, rsa, elliptic-curve, which keep their algorithms out of both lists under rule 1). 'hybrid' key exchange and 'crypto agility' are generic/adjacent vocabulary and were left to full-text search.
- `ppp` -- PPP has one name, and the desc word `ppp` already lands a reader typing PPP (and `point`/`protocol` cover the expansion), so nothing survives. Deliberately excluded: LCP, IPCP, IPV6CP, CHAP, PAP, EAP-over-PPP, MLPPP/multilink — these are control protocols, sub-features or extensions of PPP, not other names for it (rule 2); CHAP/PAP are also separate authentication mechanisms. PPPoE is the child tag `pppoe` and PPPoA/PPPoATM would route there or to `atm`, not here. Note the id collision hazard: `ncp` in the vocabulary is the ARPANET Network Control Protocol, a different thing from PPP's family of Network Control Protocols — another reason not to reach for that term here (rule 5 would bar it regardless).
- `pppoe` -- PPPoA (PPP over ATM) is a different encapsulation, not another name for PPPoE, so it is excluded under rule 1; the same applies to PPPoEoA-style variants. The PPPoE discovery/session stages (PADI, PADO, PADR, PADS) are components of the protocol and fall under rule 2. `PPP over Ethernet` is in `match` but is multi-word and, being spelled out in the desc, is already reachable by typing `ethernet` or `ppp`, so it is not listed.
- `ppsp` -- `swift` (the protocol PPSPP was derived from, cited in RFC 7574) was considered and rejected: the bare word is far too ambiguous in corpus text to route confidently to this tag. `peer-to-peer` and `p2p` belong to the existing `p2p` tag (rule 5), and `streaming` is the parent tag id, so neither is claimed here. PPSPP/PPSTP are listed as aliases rather than covers because readers use them interchangeably with PPSP for the same body of work, not as distinct technologies standing in for missing tags.
- `precis` -- Expanded form 'Preparation, Enforcement, and Comparison of Internationalized Strings' is already in the desc word by word, so 'preparation', 'enforcement', 'comparison' and 'internationalized' are all reachable. Profile and class names (IdentifierClass, FreeformClass, UsernameCasePreserved, OpaqueString) are components of PRECIS, not other names for it, and nameprep/saslprep/idnaprep are stringprep profiles rather than PRECIS names, so none are listed. IDNA-related queries belong on the existing 'idn' tag, not here. If a 'stringprep' tag is ever added, the alias above should move out of this tag.
- `privacy` -- Deliberately excluded: 'anonymity', 'pseudonymity', 'surveillance', 'tracking', 'confidentiality' — generic area vocabulary that full-text search already finds (rule 3). 'PII', 'data minimization', 'fingerprinting' — components/instances of the subject, not other names for it (rule 2). 'GDPR' and similar regulations name a legal instrument, not this tag, and are thin in RFC text. MADINAS was considered as a second working-group alias but its RFC footprint is too small to be worth a search hit; it is covered by the group mapping already. 'privacy' itself is the tag name and is reachable from the desc.
- `privacy-pass` -- Building blocks of the protocol — VOPRF/OPRF, RSA blind signatures (RFC 9474), token issuance/redemption, the 'Private Access Tokens' deployment naming — are components or separate primitives (rules 1 and 2) and are deliberately not listed. 'anonymous tokens' is already reachable: the desc words 'anonymous' and 'tokens' are indexed. 'privacy' alone should continue to land on the existing `privacy` tag (rule 5 bars it anyway).
- `psamp` -- PSAMP has exactly one name; the expansion (Packet SAMPling) is already covered because the desc words `packet` and `sampling` are both indexed and either would land a reader here. sFlow and NetFlow were considered and rejected under rule 1: sFlow is a separate vendor/Internet-draft sampling technology, not another name for PSAMP, and NetFlow belongs to the parent `ipfix` if anywhere. `sampled`, `sampling rate` and `selection process` are generic vocabulary or sub-features (rules 2-3).
- `pseudowire` -- Rejected: "PW" — the ubiquitous in-text abbreviation, but a two-letter query is too noisy/ambiguous to be a safe search key. "PALS" — the successor WG name (Pseudowire And LDP-enabled Services); it spans both this tag and `ldp`, and readers type it as a WG name rather than as a name for the technology, so it seems better left to full-text search. "Martini" — the informal name from the draft-martini series for pseudowires over MPLS; plausible as an alias but I am not confident enough it occurs as a standalone searchable term in published RFC text. "VPWS"/Virtual Private Wire Service is a service built on pseudowires and belongs with `l2vpn`, not here (rules 1-2). Components such as VCCV, control word, and SS-PW/MS-PW are sub-features and excluded by rule 2.
- `pstn-interop` -- PSTN and ISUP are both already reachable: the desc indexes 'pstn' (parenthesis splits the word) and 'isup', so typing either lands here today and neither needs listing. 'telephone' is likewise in the desc, though note 'telephony' would not match it; I left 'telephony' out as generic area vocabulary rather than a name for this tag. SS7 is the PSTN signalling system itself, not Internet/PSTN interworking — the right home is the child tag sigtran (SS7 transport over IP), not here. SIP-I is a variant form of SIP-T and belongs as an alias on the existing sip-t tag. VoIP/IP telephony is broader than this tag and readers typing it want sip or real-time-communications. PINT and SPIRITS are placed in covers rather than aliases because they name specific protocols this category stands in for, not other names for PSTN interworking as a whole; both are small (a handful of RFCs each) and do not look substantial enough to propose as new tags.
- `ptp` -- Deliberately excluded: gPTP / IEEE 802.1AS, which is a profile (instance) of PTP rather than another name for it — rule 2 — and which is mostly encountered via DetNet/TSN documents; if it were ever considered tag-worthy it would be a TSN-profile matter, not a ptp alias. Also excluded: TICTOC, the working group name in `groups`, because TICTOC chartered work covers both NTP and PTP, so it is not a name for this tag's subject specifically and would mis-route readers who mean NTP. "precision time" from `match` needs no alias entry: "precision" and "time" are already whole words in the desc.
- `qos` -- The tag's own name and expansion are already reachable: the desc indexes 'qos', 'quality', 'service' as whole words, so both the acronym and the spelled-out form land here today. Terms that came up and were rejected: 'ToS'/'DSCP'/'IP precedence' are header fields and marking mechanisms, not other names for QoS (rule 2), and their natural home is the existing child tag `diffserv` rather than this tag; 'CoS' (class of service) is a related but distinct L2/MPLS marking notion rather than a synonym for the QoS architecture topic, and it is also heavily overloaded in the corpus; 'SLA', 'jitter', 'latency', 'bandwidth' and 'admission control' are generic vocabulary or subject matter better served by full-text search (rule 3). This is a single-topic tag whose specific architectures already have their own tags (rsvp, diffserv, intserv, nsis, cops), so it needs no `covers` list.
- `quic` -- QUIC has one name, and the desc word `quic` already matches any prefix query a reader would type (`qui`, `quic`). Considered and rejected: HTTP/3 and MASQUE are separate technologies with their own tags (`http3`, `masque`), rule 1/5; `udp` and `tls` are components/substrate with their own tags; "Quick UDP Internet Connections" is a back-formed expansion the IETF explicitly disclaims and is multi-word, so not worth a `multiword` entry. `gQUIC` (Google's pre-standard version) is the one plausible variant name, but I am not confident enough it occurs in published RFC text rather than only in drafts and academic papers; if a corpus check shows real occurrences, it would be a legitimate alias here.
- `radius` -- Deliberately excluded: `diameter` and `tacacs` are sibling tags (different technologies, rule 1); NASREQ, RADEXT and ROAMOPS are working-group names that readers do not use as names for the protocol itself; CoA, Disconnect-Message, VSA, NAS and AVP are components/sub-features of RADIUS (rule 2). 'Remote Authentication Dial-In User Service' is already word-indexed in the desc, so its component words (remote, authentication, dial-in, user, service) are reachable.
- `randomness` -- Deliberately excluded: 'nonce', 'seed', 'salt' and 'IV' are components or inputs of randomness usage rather than other names for it (rule 2/3); 'one-time pad' belongs with the existing `otp` tag, not here; 'DRBG' was considered but omitted for lack of confidence that it occurs in RFC text. Siblings such as `sha`, `hmac` and `password-hashing` have their own tags, so algorithm names stay out (rule 1).
- `ratp` -- RATP (RFC 916) has one name. The expansion "Reliable Asynchronous Transfer Protocol" is already fully searchable word by word in the desc, and the acronym itself is the tag id. No superseded name, version variant or informal name exists for it. Note that RATP is unrelated to the sibling `irtp` (Internet Reliable Transaction Protocol) and to `netblt`, `rdp` and `tmux`, which are separate early transport protocols with their own tags.
- `rdap` -- Deliberately not proposed: 'WHOIS' — RDAP's predecessor protocol — because `whois` is an existing tag id (rule 5) and is a genuinely different protocol (rule 1); a reader typing WHOIS should land on the sibling tag. Also not proposed: 'regext' (the current WG covers EPP and RDAP both, so it does not name this tag), and components/sub-features such as jCard, RIR, or bootstrap registry (rule 2). 'RDAP', 'registration', 'data', 'access' and 'protocol' are all already reachable via the desc (rule 4).
- `rdma` -- RoCE and InfiniBand-native RDMA are deliberately excluded: RoCE is the InfiniBand Trade Association's link-layer mapping, a different technology from the IETF stack, and the `infiniband` tag is the right home for that family. iSER (iSCSI Extensions for RDMA) is likewise excluded as a different protocol whose natural home is `iscsi`. MPA (Marker PDU Aligned framing) is a sub-layer of the iWARP stack, so it falls under rule 2. SDP (Sockets Direct Protocol) is excluded by rule 5, since `sdp` is an existing tag id for the Session Description Protocol.
- `rdp` -- RDP has exactly one name; both 'RDP' and the words 'Reliable', 'Data' and 'Protocol' are already indexed from the desc, so a reader typing either the acronym or the expansion lands here today. 'RDPv2' (RFC 1151 defines version 2) would survive rule 4 since 'rdp' does not start with 'rdpv2', but I am not confident the single token 'RDPv2' actually occurs in RFC text — RFC 1151's title spells it 'Version 2 of the Reliable Data Protocol (RDP)' — so I am not proposing it. Worth flagging for whoever reviews search results: the string 'RDP' also denotes Microsoft's Remote Desktop Protocol and, in BGP/VPN contexts, 'Route Distinguisher'; those are different things, not aliases, and the \bRDP\b match pattern may pull in unrelated documents, but that is a `match` concern, not an alias one.
- `real-time-communications` -- VoIP legitimately overlaps with `sip` and `pstn-interop`, but this topic tag is the broadest correct landing place for the bare term, so it is claimed here rather than under a child. 'RTC' is mildly ambiguous with 'real-time clock', but that sense is essentially absent from the RFC series outside hardware asides, so the risk of a wrong hit is low. Deliberately excluded: 'RTCWEB' (the working group name for WebRTC — belongs to the `webrtc` tag, not here); 'telephony', 'multimedia', 'audio' and 'video' (generic area vocabulary under rule 3); 'AVT' (the working group behind RTP — belongs to `rtp`). No `covers` entries proposed: although this is a category tag, its instances (voice/video signalling, transport, conferencing, streaming, codecs) already have their own child tags, so rule 6's second condition fails for each of them.
- `reliable-multicast` -- NACK-oriented reliable multicast terms (e.g. NORM) already belong to the existing `norm` child tag, and file-delivery terms to `flute`, so they are not claimed here. FEC-related terms belong to the existing `fec`/`fecframe` tags. Generic words such as 'reliable', 'multicast' and 'transport' are already in the desc (and 'multicast', 'transport' are tag ids), so nothing of that kind is proposed.
- `remote-attestation` -- Deliberately excluded: EAT (Entity Attestation Token), CoRIM, CoSWID, CoAP-based attestation evidence formats and the Verifier/Relying Party role names are components or sub-artifacts of remote attestation (rule 2), not other names for it. TPM, DICE and TEE/TrustZone are distinct technologies (rule 1); TEEs already have the sibling tag `teep` for the protocol work. Plain 'attestation' and 'evidence' are already reachable via the desc word 'attestation' or are generic vocabulary. No `covers` list: this tag names one technology area, not a category standing in for untagged instances.
- `renumbering` -- The other group, PIER (Procedures for Internet/Enterprise Renumbering), was considered but not proposed: 'pier' is a common English word and a weak, ambiguous query term. 'renumber' is already reachable because the desc word 'renumbering' starts with it. Related but distinct concepts such as prefix delegation, ULA or provider-independent addressing belong to other tags (dhcpv6, addressing), not here.
- `restconf` -- RESTCONF has a single name, already the first word of the desc and findable by typing it. The expansion "RESTful Network Configuration Protocol" is in the desc and not a term readers type. YANG, NETCONF, and YANG Patch are separate technologies or have their own tags (yang, netconf), so they are excluded by rules 1 and 5.
- `rfc-series` -- Rejected as rule-2 components/sub-entities of the series rather than other names for it: RSE (RFC Series Editor), RPC (RFC Production Center), RSWG/RSAB/RSOC, and the sub-series labels STD, BCP and FYI — none is a synonym for 'the RFC Series', and STD/BCP questions are usually really about `ietf-process`. `xml2rfc` and `v3` belong to the child tag `rfcxml`, not here. Bare `RFC`, `editor`, `style`, `format` and `publication` are already reachable by searching the desc; 'Request for Comments' is reachable word by word, so no multiword entry is needed. `internet-draft`/`I-D` denote a different document class and would be a matter for `ietf-process`.
- `rfcxml` -- No aliases proposed. The obvious candidate, `xml2rfc`, is already a whole word in the desc ("processed by xml2rfc"), so typing it lands a reader on this tag today — redundant under rule 4. Likewise `xml` and `rfcxml` are indexed desc words. Version forms like "v3" or "RFC XML v3" are not single-token names a reader would type on their own ("v3" alone is generic and would be a bad hit), and document-number forms like "RFC 2629"/"RFC 7991" are references to the defining documents rather than names of the vocabulary, and do not occur as single tokens in RFC text. Related tooling terms (kramdown-rfc, bibxml, xml2rfc-processed output formats) are different technologies or components and are excluded by rules 1-2; `xml` and `rfc-series` are separate existing tags (rule 5).
- `rift` -- RIFT has exactly one name; the acronym and its expansion are both in the desc, whose indexed words (rift, routing, fat, trees) already catch "RIFT", "fat" and "tree"-prefixed queries. Considered and rejected: "Clos" and "spine-leaf" — these name the data-center topology RIFT is designed for, not the protocol, so they fail rule 1/3 and are better served by full-text search or the existing `data-center-networking` tag; "ZTP" (zero-touch provisioning) and "TIE"/"TIDE"/"TIRE" are sub-features of the protocol (rule 2). The working-group name is also "rift", so it adds nothing.
- `rip` -- RIPv2 and RIPng are both already indexed as whole words from the desc ("(RIP, RIPv2, RIPng)" -> rip, ripv2, ripng), so they are redundant under rule 4 despite being genuine variant names. IGRP is deliberately excluded: it is a different Cisco protocol and its successor already has the sibling tag `eigrp`. Hyphenated spellings such as RIP-1/RIP-2 are not proposed because the hyphen splits at index time, leaving only `rip` and a digit.
- `rje` -- The tag id `rje` itself is already the obvious query, and `remote`/`job`/`entry` are reachable as whole words in the desc. Considered and rejected: HASP (an IBM subsystem, a different technology under rule 1); RJS (appears in early RFCs only as a particular host's service name, e.g. UCLA CCN's, so too weak and site-specific to be a variant name for the tag); NETRJT (uncertain it occurs in real RFC text, so not proposed).
- `rlogin` -- rlogin has exactly one name, already the tag id and present as a whole word in the desc, so typing it lands the reader here today. Related BSD r-commands (rsh, rcp, rexec) are different protocols, not other names for rlogin, so rule 1 excludes them; they are also too slight and too sparsely documented in the RFC series to propose as tags of their own. `rlogin` appears within `telnet`'s neighborhood but belongs to the existing `telnet` tag only for comparison purposes, not as an alias.
- `rmon` -- Considered and rejected: 'remote network monitoring' — already reachable by typing 'remote' or 'monitoring' against the desc, and multi-word anyway. 'SMON' (Switch Monitoring, RFC 2613) and 'DSMON' are RMON extensions/sub-features, so rule 2 excludes them. 'RMON-MIB' is a component name and 'mib' is a sibling tag.
- `robots-txt` -- 'robots' and 'robots.txt' are already reachable: the desc words 'robots' and 'robots.txt' both prefix-match a 'robots' query, and 'robots.txt' matches itself since '.' stays inside a word. Crawler, spider and user-agent are generic vocabulary or components, not other names for the protocol, so they stay with full-text search.
- `rohc` -- Deliberately excluded: CRTP and IPHC (RFC 2507/2508) are different, earlier header-compression schemes, not other names for ROHC — they belong to the parent `header-compression` tag, as does SigComp (which already has its own `sigcomp` tag). ROHC-TCP, ROHC-RTP, ROHC-U/O/R modes and profile names are sub-features of ROHC, excluded under rule 2. 'RObust Header Compression' expanded is already reachable word by word from the desc.
- `route-reflection` -- No aliases proposed. The tag has one name, and the desc words 'route', 'reflection' and 'confederations' already make the obvious queries land here (the prefix rule means 'confederation', 'reflect' and 'route' all match desc words). 'RR' was considered and rejected as too ambiguous to be a safe search target -- in RFC text it far more often means DNS resource record or RTCP receiver report than route reflector, so it would produce confidently wrong hits (rule 1 spirit). 'route reflector' and 'AS confederation' are multi-word and, being prefix-reachable from the desc anyway, gain nothing under a future search fix. 'ORR' (optimal route reflection), 'cluster-id', 'ORIGINATOR_ID' and 'CLUSTER_LIST' are components/sub-features of the subject (rule 2). 'BGP' itself is the parent tag id (rule 5).
- `route-server` -- Single-technology tag with one established name; no genuine synonyms. Deliberately excluded: 'RS' (ambiguous initialism, also route reflector/resource server contexts, and too short to be a reliable search term); 'IXP'/'Internet exchange' (different subject — the exchange, not the server — and 'exchange'/'Internet' are already desc words); 'route reflector' and 'RR' (a different technology with its own tag, route-reflection); 'peering', 'looking glass', 'RPSL'/'IRR' (separate subjects, rpsl already a tag). 'Routing Arbiter' (the historic NSF project whose route servers RFC 1863 describes) is arguably a predecessor name, but it is multi-word, and the single token 'arbiter' alone is too generic and would not be typed by a reader looking for this tag, so it is not proposed even as multiword.
- `router-alert` -- Only one genuine variant name. "Hop-by-Hop option" was considered and rejected under rule 2/3: the IPv6 Hop-by-Hop Options header is the carrier mechanism, not another name for this option, and it also covers options unrelated to Router Alert. Terms like "IP option" and "option type 148" are generic vocabulary or an instance value, not names for the tag.
- `routing` -- Routing has exactly one name; there is no superseded or variant designation for the general subject. Candidates considered and rejected: FIB and RIB (forwarding/routing information base) are components of a router, not other names for routing (rule 2) -- FIB already appears in `match`, which is the right home for it; 'routing protocol', 'router', 'forwarding', 'route' are generic vocabulary for the area (rule 3), and 'router'/'routing' are in any case already reachable via the desc words 'routers' and 'routing'. The IETF 'Routing Area' / 'RTG' abbreviation is an organisational label rather than a technology name readers would type for the subject. Specific routing technologies (BGP, OSPF, IS-IS, RIP, Babel, EIGRP, MPLS, LISP, segment-routing, ...) all have their own child tags, so rule 1 keeps them out of both lists and this tag is not a stand-in category needing `covers`.
- `routing-architecture` -- This is a topic tag with a single descriptive name; readers reach it by typing 'routing' or 'architecture', both already whole words in the desc. Terms the `match` field pulls in are either subtopics ('policy routing', 'router requirements', 'multi-provider') which are generic vocabulary or sub-features rather than variant names, or named protocols that already have their own tags (nimrod, idpr) and so are excluded by rule 5. The group abbreviation 'sdr' is a working-group/area code rather than a name readers use for this subject, and it collides with unrelated common usage, so it is not proposed. Empty is the right answer here.
- `routing-security` -- S-BGP and soBGP are distinct proposed technologies rather than other names for this topic, so they are not listed here; if anything, they sit near the existing `bgpsec` tag. RPKI and BGPsec terms belong to the existing `rpki` and `bgpsec` child tags, not here. Generic terms such as 'route hijack', 'origin validation' or 'authentication' are area vocabulary (rule 3) or belong to other tags.
- `rpki` -- Deliberately excluded: ROA (Route Origin Authorization) and RTR / RPKI-to-Router are components and sub-protocols of RPKI, not other names for it, so rule 2 keeps them out even though ROA appears in `match`. BGPsec is an existing sibling tag (rule 5/1) and RPSL is its own tag, so neither is claimed here. 'Resource Public Key Infrastructure' spelled out is already reachable via the desc words.
- `rpl` -- LLN (low-power and lossy network) was considered and rejected: it names the network class RPL runs over, not RPL itself, and applies equally to 6lowpan and 6tisch — generic area vocabulary best left to full-text search. DODAG, MRHOF, OF0, RPL Instance and storing/non-storing modes are components of the protocol and are excluded under rule 2. MPL (Multicast Protocol for Low-Power and Lossy Networks), also a ROLL work item, is a different technology and must not be aliased here; if it ever warrants coverage it would be a separate tag, but I did not see enough volume to propose one.
- `rpsl` -- RPSS (Routing Policy System Security, RFC 2725) was considered and rejected as a sub-feature/security extension of the routing policy system rather than another name for RPSL itself; if it ever warrants coverage it is closer to routing-security. Object types such as aut-num, route, and as-set, and tools such as RtConfig, are components or instances and belong to full-text search.
- `rsa` -- RSA has essentially one name, and the desc already indexes rivest, shamir and adleman as separate words (punctuation splits), so the expanded name is reachable. Considered and rejected: PKCS#1 (the specification defining RSA schemes, a component/standard rather than another name for the algorithm — parallel to the PKCS -> pki example in rule 2); RSASSA-PSS, RSAES-OAEP, RSA-PSS, RSA-OAEP (padding/signature schemes within RSA, sub-features under rule 2 — and since '-' splits words, their leading 'RSA' token is matched by the tag name anyway); 'public-key' (generic vocabulary, rule 3, and better served by the existing pki and cryptography tags).
- `rserpool` -- RSerPool has a single name; the tag id and the expansion in the desc (Reliable, Server, Pooling) are all already indexed as whole words, so a reader typing rserpool, reliable, server or pooling already lands here. The two constituent protocols, ASAP (Aggregate Server Access Protocol) and ENRP (Endpoint Handlespace Redundancy Protocol), are sub-protocols/components of the architecture rather than other names for it, so rule 2 excludes them; neither seems substantial enough on its own to warrant a separate tag, since every RSerPool RFC carries both.
- `rsvp` -- RSVP has one name, and the desc "RSVP (Resource Reservation Protocol)" already indexes rsvp, resource, reservation and protocol, so the expansion and the acronym are both reachable today. The obvious variant form RSVP-TE is its own tag id (rsvp-te), so listing it here would shadow a real tag; likewise rsvp is not claimed by intserv, nsis or cops even though those siblings are closely tied to it. RSVP extensions and components readers might type (Path, Resv, RESV, FILTERSPEC, FLOWSPEC, RRO, ERO, refresh reduction, RSVP-DCLASS, CRLDP) are sub-features of the protocol rather than other names for it, and RSVPv1 is not a form that appears in real RFC text. Nothing qualifies.
- `rsvp-te` -- RSVP-TE has only one name in RFC text. The desc splits on the hyphen into the indexed words `rsvp` and `te`, so typing RSVP-TE, RSVP or TE already lands here; nothing needs adding for those. `RSVP` is also an existing tag id (rule 5), so it could not be claimed here in any case. Deliberately excluded: CR-LDP (a different signalling protocol for TE LSPs — it belongs with `ldp`, not here); MPLS-TE and TE-LSP (the former names the broader subject covered by `traffic-engineering`/`mpls`, the latter is the object signalled rather than another name for the protocol); GMPLS (a distinct technology with its own `gmpls` tag, even though it reuses RSVP-TE signalling); FRR / fast reroute (belongs to `ip-fast-reroute`); LSP, ERO, RRO, label (components or generic vocabulary, rule 2/3).
- `rtcp` -- RTCP has exactly one name; the expansion "RTP Control Protocol" is already in the desc (and is multi-word anyway, with each of its words indexed there). Rejected candidates: RTCP XR / XR (extended reports are a sub-feature of RTCP, rule 2, and "extended" and "reports" are already desc words); AVPF, RTP/AVPF, RTCP-FB (feedback profile/message components, rule 2, and "feedback" is a desc word); XRBLOCK (the WG name, but readers do not use it as a name for RTCP itself, unlike SPRING for segment-routing); RTP, SRTP and SR/RR/SDES are either other tags (rule 5) or components. No category role here, so no covers.
- `rtp` -- RTP has essentially one name; 'Real-time Transport Protocol' is already in the desc, where the indexed words 'real-time' (split to 'real'/'time'), 'transport' and 'protocol' are either generic or lead elsewhere, so no expansion alias is worth adding. Considered and rejected: RTCP, SRTP and RTP payload formats are existing child tags (rule 5); RTP/AVP, RTP/SAVP, rtpmap and SSRC are profiles/components of RTP (rule 2); RTSP, SIP, SDP and WebRTC are different technologies with their own tags (rule 1). The WG names AVT/avtcore/avtext are RTP's home groups but are not used in RFC text as a name for the protocol itself, so they do not meet the SPRING->segment-routing bar.
- `rtp-congestion-control` -- NADA, SCReAM and GCC are all already whole words in the desc, so typing any of them lands here today; listing them would be redundant under rule 4. Congestion-control feedback mechanics (RTCP CCFB, TMMBR, transport-wide-cc) are components/message formats, not other names for the subject, so they are excluded under rule 2; the RTCP feedback machinery itself belongs to the existing `rtcp` tag.
- `rtp-payload-format` -- This tag has only one name. Candidates considered and rejected: 'payload format' and 'payload' are generic vocabulary (rule 3) and multi-word/already in `match` anyway; RTP profile names such as AVP, AVPF and SAVP name profiles, not payload formats, so they are a different thing (rule 1) and in any case AVPF/SAVP concerns belong with `rtp` or `srtp`. Specific media names (H.264, Opus, VP8, VP9, AMR, FFV1, Matroska) are instances whose payload formats this tag covers editorially, but each already has its own tag (h264, opus, vp8, vp9, amr, ffv1, matroska), so rule 1 keeps them out of both lists and rule 6's second condition fails — this is not a category tag needing `covers`. 'RTP' itself is the parent tag id (rule 5).
- `rtsp` -- RTSP has exactly one name, and both it and the expansion (Real Time Streaming Protocol) are already whole words in the desc, so typing either lands the reader here today. Version forms like RTSP/2.0 or RTSP 2.0 are not distinct protocol names readers substitute for the tag, and RTSP/2.0 would be an odd single-token query; they add nothing over typing RTSP. Related terms a reader might expect nearby belong elsewhere: RTP/RTCP/SDP have their own tags (rtp, rtcp, sdp), as do streaming (parent) and ppsp (sibling); HTTP adaptive streaming forms (HLS, DASH) are different technologies, not other names for RTSP, so rule 1 keeps them out, and they are better considered against the streaming tag than this one.
- `s-http` -- "http" is rejected under rule 5 (it is another tag's id) even though the hyphen split in the desc makes the bare token reachable there rather than here. "HTTPS" is deliberately not listed: it is a different technology (HTTP over TLS, the scheme that won out over S-HTTP), and a reader typing it should land on tls/http/web-security, not on this historic protocol. "Secure" and "historic" are already whole words in the desc.
- `s-mime` -- "S/MIME" itself is already reachable via the desc word s/mime, so it is redundant. Predecessor/competitor mail-security schemes (PEM, MOSS, PGP/OpenPGP) are different technologies, not other names for S/MIME, and PEM and openpgp already have their own tags. Components such as SignedData, EnvelopedData and triple-wrapping are sub-features and belong to full-text search; the underlying syntax layer is the parent tag cms.
- `sacm` -- SACM has only one name: the acronym is the tag id and the expansion 'security automation and continuous monitoring' is fully in the desc, where 'security', 'automation', 'continuous' and 'monitoring' are each independently searchable whole words. Candidates considered and rejected: SCAP (Security Content Automation Protocol) is a separate NIST specification suite that SACM documents reference, not another name for SACM — rule 1; it appears in too few RFCs to suggest as its own tag. EPCP / Endpoint Posture Collection Protocol and the SACM information model/architecture pieces are components of the work, not synonyms — rule 2. 'endpoint posture assessment' and 'posture' belong with the existing `nea` tag (Network Endpoint Assessment), which is a sibling here, rather than with SACM. 'continuous monitoring' alone is already reachable via the desc and is multi-word besides. SACM names a single work area, not a category, so it has no `covers`.
- `sasl` -- SASL has exactly one name, and its expansion (Simple Authentication and Security Layer) is already in the desc as ordinary whole words, so 'simple', 'authentication' and 'security' all reach the tag today. Named SASL mechanisms (PLAIN, ANONYMOUS, EXTERNAL, CRAM-MD5, DIGEST-MD5, SCRAM, OAUTHBEARER, GS2) are components/instances of the framework, not other names for it, so rule 2 excludes them from aliases; SASL is a single framework rather than a category standing in for missing tags, so it takes no covers either. GS2 and the GSSAPI bridge mechanisms belong with the existing `gssapi` tag; SCRAM is the only mechanism with enough standalone RFC presence to ever merit its own tag, but it is not substantial enough to propose here.
- `satellite` -- Deliberately minimal. Considered and rejected: HAP / "Host Access Protocol" (in `match`, but it is one protocol used over the SATNET satellite network, i.e. a component of the subject, not another name for it -- rule 2); VSAT (a terminal/ground-segment equipment class, an instance rather than a synonym, and this tag names one technology rather than a category, so it gets no `covers`); LEO, MEO, GEO, NGSO (orbit classes -- generic vocabulary describing the area, and "LEO"/"GEO" are too ambiguous to search on); DVB-S and DVB-RCS (the `dvb` tag exists, so rule 1/5 governs); SATNET and the Atlantic Packet Satellite Network (a specific historical network; readers looking for it are better served by `arpanet` or `internet-history`, so it is claimed here neither as alias nor as covers); TCPSAT (the group name, but readers use it for the working group's TCP-over-satellite work rather than as a name for satellite links generally, and `tcp` is the other natural landing spot). Note also that typing the plural "satellites" matches nothing today because matching is directional, but a plural form is not a variant name and I have not listed it as an alias.
- `savi` -- uRPF / unicast Reverse Path Forwarding and BCP 38 ingress filtering were considered and rejected under rule 1: they are different mechanisms (router-level ingress filtering) rather than other names for SAVI, even though they share the general problem area; ingress filtering terms are better served by full-text search or, if ever wanted, their own tag. 'source address validation' itself is already whole-word searchable via the desc, so it needs no multiword entry. SAVNET (the later Source Address Validation in Intra-domain and Inter-domain Networks work) was omitted because I am not confident it appears in published RFC text yet; it would be worth revisiting once SAVNET RFCs exist.
- `schc` -- The tag name SCHC and its expansion are both already reachable: the desc contains the words `schc`, `static`, `context`, `header`, `compression`. SCHC has no superseded or variant name, and the terms surrounding it in RFC text (fragmentation, rule ID, Compression/Decompression, SCHC-over-LoRaWAN, SCHC-over-Sigfox) are components or other technologies rather than alternative names for SCHC itself. `lpwan` (the parent) is the right home for the radio technologies SCHC is profiled over.
- `scim` -- SCIM has one name, and the desc already indexes `scim`, so typing it lands correctly today. The original expansion "Simple Cloud Identity Management" (pre-2.0) is a genuine predecessor name but is multi-word, has no distinctive single token to search on, and appears rarely in RFC text; not worth queueing. Provisioning-adjacent terms were considered and rejected: SPML (OASIS Service Provisioning Markup Language) is a different technology, not a former name for SCIM (rule 1), and `provisioning` is generic vocabulary better served by full-text search (rule 3). Filter/PATCH/ServiceProviderConfig-style terms are components of the protocol (rule 2). Readers arriving from the identity side are served by the existing `federated-authentication`, `oauth` and `directory-services` tags.
- `sctp` -- SCTP has one name; the expansion 'Stream Control Transmission Protocol' is already in the desc word by word, so 'stream', 'control' and 'transmission' are reachable (and generic anyway). Related terms belong elsewhere: SIGTRAN (M2UA/M3UA/SUA adaptation layers carried over SCTP) has its own tag `sigtran`; RSerPool has `rserpool`; DTLS-over-SCTP belongs to `dtls`. Sub-features such as PR-SCTP, CMT, chunk bundling, multi-streaming and the SCTP Partial Reliability extension are components (rule 2), not alternate names. 'SCTP/UDP encapsulation' is likewise a feature, not a synonym.
- `sdf` -- Single-technology tag, so no `covers`. Candidates deliberately rejected: 'Thing Description'/'TD' (W3C WoT — a different technology, rule 1); 'sdf-mapping', 'sdfObject', 'sdfThing' (components of the format, rule 2); 'data model', 'semantic interoperability' (generic vocabulary, rule 3). 'iot' is the parent tag id (rule 5).
- `sdn` -- The desc already indexes `SDN`, `software`, `defined`, `networking`, `programmable`, `control` and `planes`, so the obvious expansions of the acronym are all reachable today. Adjacent southbound/control-plane technologies that might be typed by readers already have their own tags and are therefore excluded by rule 5: ForCES (`forces`), I2RS (`i2rs`), OVSDB (`ovsdb`), NETCONF/RESTCONF/YANG. `sdn` names a family of architectures rather than one protocol, which is why OpenFlow is placed in `covers` rather than `aliases`; it is a different thing the tag currently stands in for.
- `sdp` -- SDP has exactly one name, and both its expansion words ("session", "description") plus the string "offer/answer" are already prefix-reachable in the desc, so nothing survives rule 4. Candidates considered and rejected: "answer" (rule 3, generic vocabulary, and only half of the offer/answer model name); "SDPCapNeg"/"capability negotiation", "ICE", "SDES", "BUNDLE", "trickle" (rule 2, sub-features or extensions of SDP — and `ice` is its own tag, rule 5); "SDPng" (a never-standardised next-generation proposal, too sparse in RFC text to be worth a rejection). Note also that the bare acronym SDP is used in non-IETF contexts (e.g. service delivery platform, software-defined perimeter), but nothing about that argues for adding aliases here.
- `secevent` -- Considered and rejected: SSE (Shared Signals and Events), CAEP and RISC are OpenID Foundation profiles built on SETs rather than other names for this tag's subject, and are unlikely to appear in RFC text; 'seceventtoken' is a WG/list handle, not a term a reader would type. 'token' and 'delivery' are already reachable via the desc. JWT-related terms belong to the existing `jwt` tag.
- `security` -- Generic topic tag for the security area root; its only name is "security", already findable in the desc. Terms like "threat model", "attack", "vulnerability" are generic vocabulary (rule 3) and are covered by `match` and full-text search. "INFOSEC"/"COMSEC" are not names readers would use for this tag. Every specific mechanism has its own child tag, so nothing qualifies for `covers` either.
- `security-labels` -- CIPSO and CALIPSO are both whole words in the desc, so typing either already lands here; they are redundant as aliases even though `match` is never searched. `MLS` (multi-level security) is the other term readers associate with this subject, but it is the id of an existing tag (Messaging Layer Security), so rule 5 forbids claiming it here. `FIPS-188` (the standard behind CIPSO's label format) was considered and dropped: it names a specification component rather than the subject. Generic terms such as sensitivity, classification and label are left to full-text search.
- `segment-routing` -- SR-MPLS and SRv6 are excluded under rule 5 — they are the existing child tags sr-mpls and srv6. SID, SRH, SRv6 SIDs, SR Policy and SR-TE are components or sub-features of the subject (rule 2), not other names for it. MPLS and traffic-engineering are separate sibling tags and different technologies (rule 1).
- `send` -- The tag's own id 'send' and the desc words 'secure', 'neighbor' and 'discovery' already cover every plausible query form, so no alias survives rule 4. 'SeND' and 'SEcure Neighbor Discovery' are only case/expansion variants of terms already indexed. Component pieces of the protocol (RSA Signature option, Nonce/Timestamp options, Trust Anchor, certification path solicitation/advertisement) are sub-features and excluded by rule 2. 'csi' (Cert-based Secure Infrastructure) is the later working group name, but it is not used in RFC text as a name for the technology and is far too ambiguous a three-letter string to be a safe search term, so it is not proposed. SEND is a single technology, not a category, so it has no covers.
- `senml` -- The desc already makes 'SenML', 'Sensor', 'Measurement' and 'Lists' individually findable as whole-word prefixes, so no alias is needed for those. Neighbouring IoT data-model work (SDF, CoRE Link Format, CBOR) is a different technology or already has its own tag and is deliberately excluded.
- `service-discovery` -- Deliberately excluded: DNS-SD, mDNS and SLP are specific discovery protocols that already have their own tags (`dns-sd`, `mdns`, `slp`), so rules 1/5 keep them out of both lists. SRV belongs with `dns` (record type), not here. SSDP/UPnP was considered for `covers`, but SSDP is specified outside the RFC series and only incidentally referenced in RFC text, so I did not propose it; if the corpus shows real usage it would be the one plausible `covers` entry and a weak missing-tag candidate. `service discovery`/`resource discovery` themselves are already findable via the desc words `service`, `discovering` is not a prefix match for `discovery`, but `Discovery:` is indexed as `discovery`, so the bare phrase words are covered.
- `sfc` -- Deliberately excluded: SFF, SF, SFP, classifier and metadata (components of the SFC architecture, rule 2); NFV and NSC/service graph terminology (different technology or generic vocabulary, rules 1 and 3); segment-routing, which is a sibling tag and would shadow it under rule 5. NSH is the one borderline call — it is arguably the header component rather than the chaining mechanism, but the desc treats it as co-equal scope for this tag, so a reader typing NSH wants exactly this tag.
- `sframe` -- SFrame has a single name; the expansion "Secure Frame" is already in the desc as separate indexed words (`secure`, `frame`), so both are reachable and neither is needed here. PERC (Privacy Enhanced RTP Conferencing) is sometimes mentioned alongside SFrame as the earlier SRTP-based approach to end-to-end media security in conferences, but it is a different mechanism, not another name for SFrame, so rule 1 excludes it; if it warrants coverage it would be its own tag or belong near `srtp`/`conferencing`. Generic phrases like "end-to-end encryption"/"e2ee" describe the area rather than name the tag (rule 3) and are multi-word besides.
- `sgml` -- SGML has essentially one name. DTD, document type definition, entity and element are components of SGML, not other names for it (rule 2). HTML and XML are SGML-derived but are distinct technologies with their own tags (rules 1 and 5). 'markup' and 'document interchange' are generic vocabulary (rule 3), and 'Standard Generalized Markup Language' is already spelled out word-by-word in the desc (rule 4). The working-group name mimesgml is not a term readers use for the technology itself.
- `sha` -- Siblings md5 and hmac already own their terms, so MD5, HMAC and HMAC-SHA are deliberately excluded. BLAKE2, BLAKE3, Whirlpool, RIPEMD, Streebog and SM3 are different hash functions (rule 1) and were not proposed here; if any warrants vocabulary work it belongs to cryptography, not sha. FIPS 180 / FIPS 202 are document citations rather than names of the technology, so they are left out. Note that unhyphenated spellings (SHA1, SHA256, SHA3) are common in RFC text and in reader queries; whether the hyphenated covers entries above are findable when typed that way depends on how the indexer tokenises the alias strings themselves — if aliases are split on `-`, both the hyphenated and unhyphenated forms would need to be stored to be reachable.
- `shim6` -- Shim6 is a single named technology, so it has no `covers`. Candidates considered and rejected: HBA (Hash Based Addresses) and ULID/locator-identifier terms are components of the protocol, not other names for it (rule 2); CGA is a different technology belonging to `send` (rule 1); 'shim' alone is already reachable because the desc word 'shim6' starts with it (rule 4), and is generic besides; 'multihoming' is the parent tag id (rule 5).
- `sieve` -- Sieve has exactly one name, and the desc word 'sieve' already makes it findable. Considered and rejected: 'ManageSieve' (RFC 5804) is a separate remote script-management protocol, not another name for the filtering language, so rule 1/2 keeps it out; it is also not a category instance, since 'sieve' names a single technology and therefore has no covers list. Readers typing 'managesieve' fall through to full-text search, which finds RFC 5804 correctly. Also rejected: 'filtering', 'filter', 'vacation', 'notify', 'sieve extension' — generic vocabulary (rule 3) or named Sieve extensions, i.e. sub-features (rule 2). 'Sieve' the working group name is identical to the tag id, so nothing is gained there.
- `sigcomp` -- SigComp has essentially one name, and both words of its expansion ('signaling', 'compression') already appear as separately indexed whole words in the desc, so a reader typing either lands here today. UDVM (Universal Decompressor Virtual Machine) and the SIP/SDP static dictionary are components/sub-features of SigComp (rule 2), not other names for it. The British spelling 'signalling' would not match the desc word 'signaling', but on its own it is generic vocabulary (rule 3) rather than a name for this tag. DEFLATE and other general-purpose compression algorithms are different technologies and have their own tags (deflate, compression).
- `sigtran` -- No aliases proposed. SIGTRAN has one name, and the obvious search terms are already reachable from the desc as whole indexed words: SS7, M2PA, M2UA, M3UA, SUA, IUA and V5UA all appear in the desc split on spaces, commas and parentheses, so typing any of them lands here today (they are also sub-protocols of the suite, i.e. rule 2 material regardless). 'Signaling Transport' and 'Signalling System' are likewise in the desc or generic vocabulary. MTP, MTP3, SCCP, ISUP and TCAP were considered and rejected as components of SS7 rather than other names for SIGTRAN; ISDN terms such as Q.931 belong to the corpus full-text search, and 'transport adapter layer' from match is a multi-word generic phrase, covered by the TALI entry above. 'C7' (the ITU name for SS7) was dropped for lack of confidence that it appears as a standalone token in RFC text. DASS 2 was dropped for the same reason; it appears only alongside DPNSS in RFC 4129.
- `simple` -- The tag name is the protocol suite's only common name, and its expansion plus the terms readers actually type (SIP, instant, messaging, presence, PIDF, XCAP) are all already whole-word searchable in the desc, so nothing survives rule 4. Considered and rejected: IMPP -- it is the separate, protocol-neutral predecessor working group whose output (CPIM, PIDF) SIMPLE extends, not another name for SIMPLE, so it is a different technology under rule 1; CPIM likewise belongs with instant-messaging rather than here. RPID, watcherinfo, resource lists and event packages are components or sub-features of the suite (rule 2), and 'presence' alone is generic area vocabulary (rule 3) as well as already in the desc. PIDF and MSRP each have their own tags, so they cannot be claimed here (rule 5).
- `sip` -- Deliberately near-empty. SIP has essentially one name, and the desc already makes `sip`, `session`, `initiation` and `protocol` findable. Terms considered and rejected: VoIP (a different, broader subject area rather than another name for SIP; readers typing it are better served by full-text search or by the `real-time-communications`/`pstn-interop` tags, not by a confident hit on `sip`); SIP-I (ISUP-in-SIP interworking — it is the sibling/variant of SIP-T and belongs with the existing `sip-t` tag, not here); the P-headers matched by the `match` regex (P-Asserted-Identity etc.) and 3PCC, B2BUA, UAC/UAS, INVITE, REFER, SUBSCRIBE/NOTIFY, which are all components or sub-features of SIP (rule 2); SIMPLE, STIR, SIPREC, SIGCOMP, CPL, TRIP, P2PSIP, which are existing child tag ids (rule 5).
- `sip-t` -- ISUP is deliberately not proposed: it names a different protocol (the SS7 ISDN User Part) rather than being another name for SIP-T/SIP-I, and it is in any case already a whole word in the desc, so typing it lands here today. SS7/ISUP transport questions belong to the sibling tag `sigtran`. BICC was also considered and rejected as a distinct ITU-T call-control protocol, not a name for this tag.
- `siprec` -- SIPREC has only one name, and it is the tag id. The working group name is also siprec, so it adds nothing. Component terms from the architecture (SRC/session recording client, SRS/session recording server, RS metadata, CS/RS for communication and recording sessions) are sub-parts of the mechanism, not other names for it, so rule 2 excludes them; SRC/SRS are also ambiguous two- or three-letter strings that would produce confident wrong hits. 'recording' and 'session' are generic vocabulary and are in any case already whole words in the desc, so a reader typing either lands here today.
- `slaac` -- The desc already indexes `slaac`, `stateless`, `address` and `autoconfiguration` as whole words, so the acronym and every word of its expansion are reachable today. Candidate variants were rejected: `addrconf` (the group name here) is a Linux/IETF-internal label I am not confident appears in RFC body text; `dhcpv6`, `neighbor-discovery` and `ipv6` are other tags (rule 5) or different technologies (rule 1); temporary/privacy addresses, RA and prefix delegation are components or sub-features (rule 2).
- `slip` -- 'reliable link layer' from the match rule is multi-word generic vocabulary (rule 3) and is not proposed. PPP, the successor technology, has its own tag and stays out under rules 1 and 5. 'serial'/'line' are already indexed from the desc, so no additional form of the expanded name is needed.
- `slp` -- Protocol components and roles — DA (directory agent), SA (service agent), UA (user agent), the `service:` URL scheme and service templates — are sub-features of SLP and were excluded under rule 2. mDNS/DNS-SD and Bonjour are different service-discovery technologies with their own tags (`dns-sd`, `mdns`, `service-discovery`), so they were excluded under rule 1; a reader typing those should land on those tags. `svrloc` carries some risk of a spelling variant (`srvloc` appears in some period material); if the corpus check rejects `svrloc`, it is worth re-testing `srvloc` before dropping the idea entirely. Multi-word 'Service Location' was not proposed: both of its words already appear whole in the desc, so the query is already reachable.
- `small-services` -- The six member protocols named in the desc (Echo, Discard, Chargen, QOTD, Daytime, Active Users) are already whole-word reachable from the desc, so none of them qualifies as an alias. 'Character generator' and 'quote of the day' are the spelled-out forms behind chargen/QOTD, but both are multi-word and the abbreviations already land the reader here, so neither is worth a multiword entry. TCPMUX (RFC 1078) is frequently discussed alongside the small services but is a different protocol, not another name for them, so it is excluded by rule 1; it is too slight to propose as its own tag. 'echo' by itself is not proposed as an alias because the word already appears in the desc, and readers typing it may equally want ICMP echo/ping, which belongs to the icmp tag.
- `smds` -- SMDS has essentially one name, and both it and the expansion 'Switched Multimegabit Data Service' are already word-indexed in the desc, so nothing is needed there. Candidates considered and rejected: DQDB and IEEE 802.6 are the underlying MAC/subnetwork technology, not another name for the SMDS service (rule 1); SIP (SMDS Interface Protocol) and DXI (Data Exchange Interface) are components of SMDS and SIP would additionally shadow the existing `sip` tag (rules 2 and 5); CBDS (the ETSI Connectionless Broadband Data Service) is the closest thing to a variant name but is a distinct European service specification and I am not confident enough it appears in RFC text to propose it.
- `smtp` -- Deliberately excluded: MTA, MSA, DSN, 8BITMIME, BURL, CHUNKING and similar are components or extensions of SMTP (rule 2). 'submission'/'message submission' is generic vocabulary and also a sub-feature, so it is left to full-text search even though the desc's indexed word is 'relaying/submission' and a bare query 'submission' would not hit it today. LMTP (RFC 2033) was considered and rejected: although it is derived from SMTP, it is a separate protocol for final delivery rather than another name for SMTP, so rule 1 governs; it is too small to be worth its own tag, so it is not proposed as a missing tag either. Mail-transport-adjacent siblings (imap, pop3, jmap, eai, spam, email-authentication) already have their own tags and are not claimed here.
- `sna` -- The tag's own name is already findable: the desc contains the whole word `sna`, and the expansion's words (systems, network, architecture) are generic vocabulary, so no alias is needed for the name itself. APPN, DLSw and HPR are listed under `covers` rather than `aliases` because they name different things inside the SNA family, not other names for SNA; SNA is an umbrella architecture, which makes `covers` appropriate here. SDLC, LU6.2/APPC and NAU were considered and dropped as internal components or ambiguous acronyms. TN3270 is excluded because it is already an existing tag (this tag's child).
- `snmp` -- Deliberately excluded: USM, VACM, SMI, SMUX and TRAP/INFORM are components or sub-features of the SNMP framework (rule 2), and SMI/MIB material is already served by the child tag `mib`. SGMP (Simple Gateway Monitoring Protocol) is a distinct predecessor protocol rather than an earlier name for SNMP, so it is left out under rule 1; it does not look substantial enough for its own tag. Working-group names (isms, disman, snmpconf) are not terms readers use for the protocol itself. The version aliases overlap the `match` regex, but `match` is never searched, so they are still needed here.
- `sockets-api` -- On reflection the only candidate I considered, "socket", is redundant: the desc word "sockets" starts with "socket", so a reader typing it already lands here. It should be dropped, leaving an empty aliases list. Other terms I weighed and rejected: BSD sockets / Berkeley sockets are multi-word and their first token "sockets" is already findable; getaddrinfo, setsockopt, sockaddr, SOCK_STREAM are API elements, i.e. components of the subject (rule 2); POSIX and libc are generic platform vocabulary (rule 3); RDMA verbs and TAPS name different technologies with their own tags (rdma, taps). This tag has one name.
- `socks` -- Working group name AFT (Authenticated Firewall Traversal) was considered but rejected: readers do not use it as a name for the protocol, and it is closer to the parent `firewall` area than to SOCKS itself. Components of the protocol (e.g. the CONNECT/BIND/UDP ASSOCIATE commands, the username/password or GSS-API authentication methods) are sub-features, not alternative names, and GSS-API belongs to the existing `gssapi` tag. SOCKS4 was left out as a lower-confidence single-token form; if a corpus check shows real occurrences it would qualify on the same grounds as SOCKS5.
- `softwire` -- No genuine synonym exists for the tag name itself: 'softwire'/'softwires' is both the WG name and the technology name, and the desc word 'softwires' already makes the singular query 'softwire' land here by prefix match. The major softwire mechanisms already have their own tags (ds-lite, map, 6rd, 464xlat), so by rule 1 they belong in neither list; only lw4o6 and 4rd lack a home, and they go in covers rather than aliases because they are distinct mechanisms, not other names for the same thing. Terms like 'mesh', 'hub-and-spoke', 'tunnel' and 'encapsulation' are generic vocabulary (rule 3); 'tunneling' is in any case another tag's id (rule 5). 'AFTR' and 'B4' were considered and rejected as components of a softwire deployment (rule 2), and they are more properly ds-lite terminology.
- `sonet` -- Rate designations (OC-3, OC-48, STM-1, STM-16) are instances/sub-features of the hierarchy, not variant names, so they are left to full-text search under rule 2. 'POS' (Packet over SONET/SDH) was considered and dropped: it names an encapsulation practice rather than SONET itself, and the bare token is too ambiguous to be a confident search landing. OTN/G.709 is a different transport technology (rule 1) and is deliberately not proposed here.
- `spam` -- Deliberately excluded: SPF, DKIM and DMARC are existing tag ids (rule 5) and belong under email-authentication in any case; 'blocklist', 'blacklist', 'junk', 'filtering' and 'reputation' are generic vocabulary or already desc words (rules 3 and 4). DNSBL/RBL/ARF are placed in covers rather than aliases because they are distinct mechanisms the tag stands in for, not other names for spam itself; none looks substantial enough on its own to warrant a new tag today, but ARF is the closest if the MARF/repute output is ever split out.
- `special-use-domain-names` -- No genuine synonyms found: "Special-Use Domain Names" (RFC 6761) is the only name for this subject, so aliases is empty. The desc words "special-use" and "reserved" index as "special", "use" and "reserved" (hyphen splits), which already covers the obvious queries. Instances go in covers rather than aliases because they are different names, not other names for the same thing. Deliberately excluded: "example", "invalid" and "test" are reserved names but are generic vocabulary (rule 3) and would produce noisy hits; ".local" belongs to the existing `mdns` tag (RFC 6762) rather than here; ".internal" is recent enough that I am not confident of its occurrence density in RFC text. I also considered "arpa": it is a legitimate reserved/infrastructure domain (RFC 3172), but a reader typing it is at least as likely to want `arpanet` or in-addr/ip6 reverse DNS under `dns`, so I left it out rather than risk a confidently wrong hit.
- `speermint` -- The desc already makes 'session', 'peering', 'interconnect' and 'multimedia' findable as whole words, so no expansion of the acronym is needed. Border-element terms (SBE, DBE) and ENUM/LUF/LRF were rejected: the first two are components of the SPEERMINT architecture (rule 2) and ENUM is an existing tag id (rule 5). DRINKS is the only candidate I would defend; if a reviewer judges DRINKS to be a distinct technology rather than another name for this tag's scope, the right outcome is a separate tag rather than moving it to covers, since this tag names a single peering architecture and not a category.
- `spf` -- Deliberately short. The tag name, its expansion, and the record version token cover essentially everything a reader would type. Rejected: 'Sender ID'/'senderid' and 'PRA' as rule-1 different technology (routed to missing_tag_candidates); 'DMARC', 'DKIM' as sibling tags (rule 5); 'MAIL FROM', 'HELO', 'envelope sender', 'include', 'macro' as rule-2/3 components and generic vocabulary; 'sender policy framework' is already whole-word reachable from the desc. Caution for corpus checking: the bare string SPF also means 'Shortest Path First' throughout the routing RFCs (OSPF, IS-IS, bgp-spf), so occurrence counts for SPF-prefixed terms in this tag's area should be read carefully — this affects the `match` field more than aliases, but the same ambiguity is why no broader SPF-shaped alias is proposed here.
- `spki` -- The expansion "Simple Public Key Infrastructure" is already in the desc word by word, so those words need no alias. SPKI certificates are sometimes called "authorization certificates", but that is generic vocabulary (rule 3) and multi-word.
- `sr-mpls` -- SR-MPLS has only one name in RFC text. The desc indexes as the words sr, mpls, segment, routing, over (the hyphen splits sr-mpls), so readers typing 'sr' or 'mpls' or 'segment' already reach it, and the tag id itself covers the exact string. Related terms were rejected: SPRING is the working group name for segment routing generally and belongs on the parent tag `segment-routing`, not on this data-plane-specific child; SID, SRH, SRGB, prefix-SID and adjacency-SID are components (rule 2); SRv6 is a different data plane with its own tag `srv6` (rules 1 and 5); MPLS itself is another tag id (rule 5). 'MPLS-SR' and 'SR/MPLS' are occasionally seen in slideware but I am not confident they appear in real RFC text, so I do not propose them.
- `srtp` -- Proposing no aliases. SRTP has exactly one name, and both 'SRTP' and 'secure' are already indexed whole words in the desc, so the obvious queries already land. Deliberate exclusions: SRTCP is the companion control-protocol profile defined in the same specification — a sub-feature/counterpart rather than another name for SRTP (rule 2), and the sibling tag rtcp plus srtp between them cover it; DTLS-SRTP names a keying mechanism (RFC 5764), not SRTP, and tokenises to dtls + srtp anyway, with dtls being the right existing tag; 'SRTP Protection Profile', 'crypto context', 'master key' and similar are components or generic vocabulary (rules 2 and 3). MIKEY appears in the tag's `match` but is a key management protocol, so rule 1 disqualifies it as an alias no matter how frequently it co-occurs; it is listed under missing_tag_candidates instead, and key-management is the nearest existing home if no new tag is created.
- `srv6` -- SRv6 has one name in RFC text, and the desc already indexes `srv6`, `segment`, `routing` and `ipv6` as whole words, so the obvious queries land here today. Considered and rejected: `SRH` (Segment Routing Header) and `uSID`/`micro-SID` are components of SRv6 under rule 2, not other names for it; `SR-MPLS` is the sibling tag `sr-mpls` (rule 5) and a different data plane (rule 1); `SPRING` is the working group name for the parent tag `segment-routing`, not for this narrower data-plane tag, so it belongs there if anywhere.
- `ssh` -- Considered and rejected: OpenSSH and other implementation names (a product, not another name for the protocol); scp, SSHFP, ssh-agent, userauth and the transport/connection layers (rule 2, components or sub-protocols of SSH); rlogin, telnet and tls (rule 1 and rule 5 — different technologies with their own tag ids); 'shell' and 'secure' alone (rule 3 generic vocabulary, and already reachable in the desc). 'SSH-2' is omitted as a spelling because the hyphen splits the query and it cannot be matched as one token today; SSHv2 covers the same reader.
- `ssm` -- SSM has essentially one name. The acronym "SSM" and the words "Source-Specific" / "Multicast" are all already indexed as whole words in the desc, so a reader typing SSM lands here today (and "ssm" is the tag id regardless). The expanded form "source-specific multicast" is multi-word and adds nothing findable. PIM-SSM was considered and rejected: it is the PIM protocol mode used to build SSM trees, i.e. a component/sibling matter, and `pim` exists as its own tag (rules 1/2/5). The historical EXPRESS proposal (Holbrook/Cheriton) that preceded SSM was also considered but "express" is an ordinary English word that would produce confident wrong hits, so it is deliberately left out. "ssm-mapping" and "include/exclude mode" are IGMPv3/MLDv2 mechanisms and belong under `igmp`/`mld`, not here.
- `st2` -- Bare "ST" is already findable via the desc word `st`, so it is omitted as redundant. "Internet Stream Protocol" and "stream protocol" are multi-word and already word-reachable from the desc (`stream`, `protocol`), so nothing goes in multiword.
- `stamp` -- STAMP has one name, and the desc already indexes both 'stamp' and the expanded words. STAMP Optional Extensions (RFC 8972) and 'STAMP Session-Sender/Session-Reflector' are components of the protocol, not alternative names (rule 2). TWAMP and OWAMP are separate measurement protocols with their own tags (rule 1/5), so neither is an alias here even though STAMP is TWAMP-Light-compatible; 'TWAMP Light' belongs under the existing twamp tag if anywhere.
- `stir` -- PASSporT (RFC 8225) was considered and rejected under rule 2: it is the token format defined by STIR, a component of the subject rather than another name for it — it is already in `match` so tagging is unaffected. "STI" was rejected as redundant under rule 4: the desc word "STIR" starts with "sti", so typing it already lands here. Sibling tags (sip, siprec, speermint) are unaffected; no term here belongs to them.
- `storage` -- No aliases: 'storage' has one name and the desc words storage/access/protocols already carry it. Deliberately excluded: SAN and NAS — both are genuinely used for storage networking in RFC text, but SAN is overwhelmingly 'Subject Alternative Name' in the x509/pki corpus and NAS is 'Network Access Server' in the radius/aaa corpus, so either would produce a confidently wrong hit for the more common reading. SCSI is not proposed here: the query 'scsi' does not reach the iscsi tag (prefix matching is directional), but the right home for it is the iscsi tag's own alias list, not this parent. FCIP and iFCP likewise belong under fibre-channel. NVMe/NVMe-oF was considered and dropped for lack of confidence that it appears in published RFC text. SMB/CIFS and AFS are left out of missing_tag_candidates because the RFC-series coverage of each looks too thin to carry a tag; they are listed in covers so a search still lands somewhere sensible.
- `streaming` -- Deliberately excluded: ABR (adaptive bitrate) — the acronym collides with Available Bit Rate (ATM) and Area Border Router (OSPF/IS-IS), so it would produce confidently wrong hits. CMAF and Media over QUIC / MOQT were also considered but dropped for lack of confidence that they occur in published RFC text as of now; MOQ would be the obvious next covers/missing-tag entry once it does. ELEGY (a group listed on this tag) is likewise too new to be confident it appears in RFC text. Generic terms like 'media', 'video', 'live' and 'delivery' are area vocabulary (rule 3) and belong to full-text search. RTSP and PPSP are children with their own tags, and codecs/rtp/rtp-payload-format are siblings, so terms naming those belong there rather than here.
- `stun` -- The acronym STUN is already in the desc and so is findable today, and the current expansion "session traversal utilities" is fully searchable word by word from the desc, so neither needs listing. Deliberately excluded: TURN and ICE are separate existing tags (sibling technologies, rule 1/5); STUNT and ICE-lite are different or derived mechanisms, not other names for STUN; "stuns" is the secure URI scheme registered alongside stun: rather than an alternative name for the protocol, so it is treated as a sub-feature (rule 2) rather than an alias -- if the maintainers disagree it would be the one plausible single-token addition, since the desc word "stun" does not make "stuns" findable.
- `supdup` -- SUPDUP has exactly one name. The expansion "SUPer-DUPer" is already in the desc and is not a term readers would type. Related but distinct protocols (TELNET, Supdup Graphics) belong elsewhere: `telnet` is an existing tag, and the graphics extension is closer to the sibling `network-graphics` tag than to an alias here.
- `supply-chain-integrity` -- Only one genuine variant name found. Deliberately excluded: 'transparency' and 'artifacts' as generic vocabulary (and 'transparency' is already a whole word in the desc); 'certificate transparency' and 'attestation' because certificate-transparency and remote-attestation are existing tags and claiming them here would shadow them; 'receipt', 'transparency service', 'append-only log' as components/sub-features of the subject; 'in-toto' and 'Sigstore' as separate external technologies rather than other names for this tag. 'supply chain' needs no entry: 'supply' is a whole word in the desc and already lands a reader here.
- `sustainability` -- "energy", "energy efficiency" and "environmental" are already whole words in the desc, so typing them lands here today (rule 4); "energy"-typed queries also legitimately point at the sibling tag energy-management (EMAN), which is the better home for device-level energy monitoring and reporting. "carbon" was considered and dropped: it names one metric/aspect of the tag's subject (carbon footprint, carbon-aware computing) rather than being another name for sustainability, so it falls under rule 2/3 and belongs to full-text search. Deliberately no `covers`: this is a single topic, not a category standing in for untagged technologies.
- `syslog` -- syslog has a single universally used name; readers type "syslog" and the tag id already matches. Variants like "syslog-sign", "syslog-tls" or "BSD syslog" are prefix-matched by the id itself or are sub-features rather than alternative names. Related terms such as "logging" and "audit log" are generic vocabulary (rule 3) and belong to full-text search; "reliable delivery of syslog" names a component of the protocol suite, not another name for it. SNMP traps, IPFIX and the like are different technologies with their own tags.
- `tacacs` -- TACACS+ is already reachable: '+' stays inside the indexed word, so the desc word 'tacacs+' matches the query 'tacacs+' (and 'tacacs' matches both desc words), making it redundant under rule 4. 'Terminal Access Controller Access-Control System' and its Plus form are multi-word and each significant word is already in the desc, so nothing is needed under multiword. RADIUS and Diameter are sibling AAA protocols, not other names for TACACS, so they are excluded by rule 1.
- `taps` -- TAPS has essentially one name. The expansion "Transport Services" is already reachable: the desc is indexed as whole words including `transport` and `services`, and both are ordinary prefix hits, so a multiword entry would add nothing (and `transport` is itself a tag id, barred by rule 5). Related-but-distinct items were deliberately excluded: `sockets-api` is an existing sibling tag and the right home for BSD-sockets queries; Post Sockets and NEAT are precursor/research efforts rather than established alternate names for TAPS in RFC text, so I did not risk them. Components of the architecture (Connection, Preconnection, Message, racing) are sub-features or generic vocabulary and belong to full-text search.
- `tcp` -- TCP has exactly one name, and both it and the expansion ("Transmission Control Protocol") are already whole words in the desc, so a reader typing `TCP`, `transmission`, `control` or `protocol` lands here today. `TCP/IP` was considered and rejected: it names the internet protocol suite rather than the transport protocol (the tag's own `match` explicitly excludes it), so it is a different subject, closer to `internet-architecture`/`internet-layer`. Variant/extension forms such as T/TCP, TCP Fast Open, SACK and Reno/NewReno are sub-features or congestion-control algorithms, not other names for TCP (rule 2), and the congestion-control family already has `congestion-control`, `cubic` and `ledbat`. `MPTCP` and `tcpcrypt` are existing child tags, so they are barred by rule 5 as well as being distinct technologies.
- `tcpcrypt` -- Considered and rejected: TCP-ENO / ENO (RFC 8547) is the separate encryption negotiation option that tcpcrypt runs over, i.e. a companion component rather than another name for tcpcrypt (rule 2); it is too narrow to warrant its own tag and readers looking for it are well served by full-text search. 'tcp' and 'mptcp' are existing tag ids (rule 5). Generic terms like 'opportunistic' and 'encryption' are already reachable via the desc or are area vocabulary.
- `teep` -- TEE alone is not proposed: it names the general Trusted Execution Environment concept rather than this provisioning protocol, and it is also generic vocabulary spanning remote-attestation, teep and other security tags. SUIT (the manifest format TEEP carries) is a different technology and belongs with firmware-update, not here. 'Trusted Execution Environment' is already reachable via the desc words trusted/execution/environment, and 'provisioning' likewise.
- `tel-uri` -- The tel URI scheme has essentially one name. A reader typing `tel` already lands here: the desc contains the standalone word `tel` ("The tel URI scheme"), and `telephone`, `number`, `portability` and `trunk` are all indexed desc words too, so the obvious queries are already reachable (rule 4). `uri` is itself a tag id, so it cannot be claimed here (rule 5). The tel URI's parameters -- `tgrp`, `trunk-context`, `npdi`, `rn`, `cic`, `phone-context`, `isub`, `ext` -- are sub-features of the scheme, not other names for it, so they are out under rule 2; they are also the kind of string that would produce confidently wrong hits. Neighbouring technologies that readers sometimes conflate with this one have their own homes and must not be aliased here: ENUM (tel-to-URI mapping in DNS) -> `enum`, SIP URIs and tel-in-SIP -> `sip` / `sip-t`, PSTN number interworking generally -> `pstn-interop`, and E.164 formatting questions land in the ENUM/tel area via those tags. `tel-uri` names a single technology, not a category, so it has no `covers`. Candidate multiword forms ("tel URI", "telephone number", "number portability") are all reachable word-by-word from the desc already, so none is worth queueing on a search fix.
- `telemetry` -- "Network telemetry" has essentially one name, and the desc already indexes `network`, `telemetry`, `streaming` and `operational`, so the obvious reader queries land here today. Candidates considered and rejected: "streaming telemetry" and "model-driven telemetry" are multi-word and in any case already reachable via the desc word `streaming`; YANG-Push and NETCONF event notifications are specific mechanisms belonging to the existing `yang` and `netconf` tags (rules 2 and 5); gNMI/gRPC are distinct management protocols rather than another name for telemetry (rule 1) and appear only sparsely in RFC text, so I am not confident enough to propose either as a covers entry or a missing-tag candidate.
- `telepresence` -- CLUE, the WG/protocol name readers would most likely type for this tag, is already a whole word in the desc ("Telepresence (CLUE) multi-stream conferencing" indexes as ... telepresence, clue, multi-stream ...), so it is reachable today and drops under rule 4. TIP (Telepresence Interoperability Protocol) is a distinct protocol and already has its own tag id, so it is excluded by rules 1 and 5. Terms like immersive, multi-stream, video conferencing and room system are generic vocabulary or component descriptions (rule 3) and belong to full-text search. This tag has one name.
- `telnet` -- Telnet has exactly one name; the tag id already matches what any reader would type, and the desc covers 'options'. Considered and rejected: NVT / 'network virtual terminal' (a component concept of the protocol, rule 2 — and 'virtual terminal' is already in `match` anyway); TN3270 and rlogin (different protocols with their own tags, rules 1 and 5); 'terminal' (generic vocabulary, rule 3).
- `teredo` -- Teredo has a single name; no superseded or variant names exist. The Microsoft implementation name "Teredo" is itself the tag id, and the specification's shorthand terms (Teredo client, Teredo server, Teredo relay, bubble packets) are components per rule 2. "Shipworm" was an early pre-RFC draft name for the technology, but it is unlikely to appear in published RFC text, so it is not proposed. Related transition mechanisms (6to4, ISATAP, ds-lite) are different technologies; 6to4 and ds-lite already have their own sibling tags.
- `terminology` -- Considered and rejected: `RFC2119` and `BCP14` — these name a specific document defining requirements language rather than another name for the topic itself (rule 2, instance of the subject); a reader typing them wants that RFC, and full-text search serves them better than a confident landing on this tag. `keywords` (from the `match` pattern `key ?words`) is generic vocabulary — it is a word from the RFC 2119 title, not a name for this subject (rule 3). `definitions`, `definition`, `terminology` variants such as `terminological`, and `requirements` are all already reachable by prefix-matching the desc words `definitions`, `Terminology:` and `requirements`, so they are redundant under rule 4. `abbreviations` and `acronyms` describe document sections rather than naming this topic, so they belong to full-text search.
- `tftp` -- The desc already contains both "TFTP" and "Trivial File Transfer Protocol", so the acronym and the expanded name are both reachable. TFTP has no predecessor or variant names; extensions like the blocksize/timeout options and MTFTP (Multicast TFTP) are sub-features or a distinct variant rather than alternative names for the protocol itself, and the tftpexts group is already tied to this tag. Sibling `ftp` is a different protocol and must not be aliased here.
- `time-synchronization` -- Almost nothing qualifies here. `clock` and `sync`/`synchronization` are already reachable as whole-word prefixes in the desc ("clock synchronization over networks"), and both are generic area vocabulary anyway. SNTP and NTS (Network Time Security) are variants/extensions of NTP and belong to the `ntp` tag, not here; IEEE 1588, 1588v2 and PTPv2 belong to the `ptp` tag. GPS/GNSS and IRIG are different technologies (time sources, not network synchronization protocols) and are rule-1 rejects. NTP and PTP themselves are existing tag ids, so rule 5 excludes them.
- `time-zones` -- Deliberately excluded: TZif (RFC 8536) is the binary file format for the data rather than another name for the subject, so it is a component under rule 2. DST/daylight saving is a sub-feature and generic vocabulary. UTC and leap seconds are different things and belong with date-time-formats or ntp. The SEDATE working group name is listed in `groups` here, but its output (RFC 9557 extended date/time strings) reads more like `date-time-formats`, so it is better proposed there than claimed as an alias of this tag.
- `tip` -- TIP has exactly one name. The tag id itself is the acronym, and the desc already carries the expansion word by word, so 'Transaction', 'Internet' and 'Protocol' are each individually reachable. No superseded name, version variant or vendor name exists for this protocol (RFC 2371/2372). Note the id 'tip' is a short, ambiguous string that also collides with unrelated ordinary English usage, but that is a search-ranking concern, not an alias one.
- `tls` -- HTTPS deliberately excluded: it names HTTP-over-TLS, a different thing from the TLS protocol itself, and would be a confidently wrong hit for readers wanting the `http` or `web-security` tags. STARTTLS likewise excluded as a sub-feature/upgrade mechanism belonging to the application protocols that use it (`smtp`, `imap`, `pop3`). DTLS is a child tag of its own, so it belongs in neither list here. TLS 1.3 / TLS1.2 and similar version strings are omitted: they are rule-3-adjacent version numbers rather than variant names, and the bare `tls` in the desc already lands readers who type the protocol name.
- `tmux` -- RFC 1692's Transport Multiplexing Protocol has only one name. The desc word `tmux` already lands a reader typing TMux, and `transport`/`multiplexing` are both indexed whole words in the desc, so the expanded name is reachable too. No superseded, versioned or vendor variant exists. (Unrelated: the popular terminal multiplexer also called tmux is not an IETF protocol and is not an alias relationship — it is simply a name collision, and nothing in the RFC corpus should be routed on it.)
- `tn3270` -- `3270` alone is already reachable: the desc "(Telnet 3270)" indexes `3270` as a whole word, so it is redundant. `Telnet` is likewise in the desc and in any case belongs to the existing `telnet` tag.
- `token-binding` -- Single-technology tag, so no covers. Deliberately excluded: 'TLS' (a different technology with its own tag, rule 1/5), 'referred token binding', 'provided token binding', 'TokenBindingID' and 'TB_ProtocolVersion' (components or sub-features, rule 2), and 'token'/'binding' alone (already reachable via the desc, rule 4).
- `token-ring` -- IEEE 802.5 is the same technology as token ring, so it is an alias rather than a `covers` instance. Token ring's companion MIB and source-route bridging material are components, not alternative names, so nothing else qualifies. FDDI, which is sometimes loosely lumped with token ring, is a different link layer with its own `fddi` tag and is deliberately excluded under rule 1. 'Token' and 'ring' are each already findable as whole words in the desc.
- `traceroute` -- Deliberately excluded: 'ping' — a different tool (ICMP echo request/reply), and readers looking for it are better served by the existing `icmp` tag; including it here would be rule 1 error. 'MTR' likewise is a separate tool, and I am not confident it appears in RFC text. 'LSP ping' / 'MPLS traceroute' / 'LSP traceroute' belong to `mpls` (and are multi-word in any case). 'path discovery', 'path MTU', 'hop', 'TTL' are generic vocabulary or belong to `pmtud`/`icmp`. 'traceroute6' was considered — it would not be found today, since the desc word 'traceroute' does not start with the query 'traceroute6' — but it is a rare spelling in RFC text and a reader typing it would almost certainly type 'traceroute' instead, so it was dropped rather than risk a corpus-check rejection.
- `traffic-engineering` -- Considered and rejected: MPLS-TE and RSVP-TE are specific applications/instances of TE (and RSVP-TE is already a child tag, so listing it would shadow a real tag id under rule 5); TEAS/TEWG are working-group names but readers type "TE", not "TEAS", for the technology itself. GMPLS, PCE, segment-routing and detnet are separate existing tags and belong there, not here.
- `transport` -- No aliases proposed. The tag's own name is the standard term for the concept, and the desc word `transport` already makes it findable; `transport-layer` and `transport protocol` are generic vocabulary (rule 3) reachable via the desc anyway (rule 4). The concrete transport protocols under this topic -- TCP, UDP, QUIC, SCTP, DCCP, RSerPool, RDP, NETBLT, RATP, IRTP, TMux, ST2, DTN -- all have their own tags, so under rule 1/rule 6 none belongs in `aliases` or `covers`; this topic tag has no `covers`. Layer shorthands such as `L4`/`layer-4` were considered and rejected: they are generic layer vocabulary rather than a name for this subject, and would compete with per-protocol tags. Readers typing TLS want `tls` (the `match` regex already excludes "transport layer security"), and `taps` covers the transport services API.
- `transport-mapping` -- This tag has no genuine synonym. The plausible candidates are all already reachable by prefix search on the desc: 'mapping' matches the desc word 'mappings', 'binding' matches 'bindings', 'model' matches 'models', and 'transport' matches 'transport' directly, so rule 4 removes them. The named transports themselves (TLS, TCP, UDP, QUIC, DTLS, SCTP, SSH, WebSocket, BEEP, DCCP) are different technologies with their own tag ids (tls, tcp, udp, quic, dtls, sctp, ssh, websocket, beep, dccp), so rules 1 and 5 exclude them from both lists; a reader typing those wants the protocol tag, not this topic. 'X-over-TLS'-style constructions are matching patterns from `match`, not names a reader would type as a lookup. The tag names a topic (the practice of transport bindings) rather than a category standing in for untagged instances, so it has no `covers`.
- `trill` -- Deliberately excluded as components or sub-features of TRILL (rule 2): FGL / fine-grained labeling, TRILL nickname, ESADI, Appointed Forwarder. Excluded as different technologies (rule 1): SPB / 802.1aq (IEEE shortest path bridging, a competing approach, not a name for TRILL), STP/RSTP, VXLAN (has its own tag), and IS-IS (its own tag; TRILL uses it as its control plane but they are not the same thing).
- `trip` -- TGREP is the only other protocol name in scope, and it already appears as a standalone word in the desc, so typing it lands on this tag today (rule 4). The expansion "Telephony Routing over IP" is multi-word and its words are all present in the desc anyway. ITAD, LS (location server) and gateway attributes are components of TRIP (rule 2), and generic terms like "telephony" and "gateway" are area vocabulary best left to full-text search (rule 3). Nothing qualifies.
- `trust-management` -- `KeyNote` is already a whole word in the desc, so typing it lands on this tag today and it is redundant as an alias even though it also appears in `match`. Generic terms such as trust, policy, credential, delegation and authorization are area vocabulary (rule 3); `authorization` is in any case another tag's id (rule 5), and readers looking for policy frameworks more broadly are better served by the existing `policy-management` tag. PolicyMaker is the only sibling system I am confident appears in RFC text; REFEREE and similar academic trust-management systems are not, so I have not proposed them. PolicyMaker seems too small a subject (essentially one historical system, discussed only in passing within the KeyNote RFCs) to warrant its own tag, so it is not listed as a missing tag candidate.
- `tunneling` -- Tunneling has no real synonym. "tunnel"/"tunneling" already hit the desc word `tunneling` (prefix match), and the British spelling `tunnelling` is literally in the desc too, so both are redundant under rule 4. "encapsulation" is generic vocabulary (rule 3) and is in the desc anyway. The concrete tunnel technologies are either their own tags (gre, ip-in-ip, l2tp, teredo, vxlan, geneve, nvgre, softwire, ip-in-ip, amt, lisp, vpn, overlay-networks) — rule 5 / rule 1 — or specific protocols like SEAL (Subnetwork Encapsulation and Adaptation Layer, in `match`) and GUE, which are instances rather than other names for the technique (rule 2). `tunneling` reads as a technique with dedicated child tags rather than an unrepresented category, so I propose no `covers` either.
- `turn` -- TURN has one name, and both the acronym and its expansion are already indexed word-by-word from the desc (turn, traversal, using, relays, around, nat), so a reader typing TURN or any word of the expansion lands here today. Candidates considered and rejected: 'relay'/'relays' — generic vocabulary (rule 3) and already a desc-prefix match anyway; 'TURNS' (TURN over TLS) and 'TURN-TCP' — transport variants/sub-features of the same protocol rather than alternative names (rule 2), and thin enough in corpus text not to be worth the rejection risk; 'STUN' and 'ICE' — different technologies with their own tags (rules 1 and 5); 'TRAM' — the WG name, but readers use it for the WG's charter area rather than as a name for TURN itself, and it also covers STUN/ICE work, so it would be a misleading single-tag landing.
- `tvr` -- TVR is already reachable: the desc word "Time-Variant" indexes as `time-variant` (or splits to `time`/`variant`), and the tag id `tvr` itself is the acronym. The working-group name is also TVR, so it adds nothing. Related terms like DTN (delay-tolerant networking) and scheduled satellite constellation routing are different technologies with their own tags (`dtn`, `satellite`) and must not be aliased here. "Scheduled" and "connectivity" are generic vocabulary already in the desc.
- `twamp` -- TWAMP has one name, and the desc word `twamp` already lands a reader typing TWAMP. Its siblings OWAMP and STAMP are distinct protocols with their own tags (rule 1), so neither is an alias here. TWAMP-Light was considered and rejected as a mode/sub-feature of the protocol rather than another name for it (rule 2); if the taxonomy later wants it findable, the cleanest home is a `match`/desc adjustment on this tag, not an alias.
- `udp` -- UDP has exactly one name. The expansion "User Datagram Protocol" is already in the desc and indexed as the words `user`, `datagram` and `protocol`, so typing any of those already lands here; it is also multi-word and thus unfindable as a single-token alias. UDP-Lite is a child tag (`udp-lite`) and DCCP/SCTP/QUIC are sibling transports, so none of them qualify under rules 1 and 5. `udp` names a single protocol, not a category, so it has no `covers`.
- `udp-lite` -- UDP-Lite has exactly one name. The desc "UDP-Lite (Lightweight User Datagram Protocol)" indexes on hyphen and punctuation boundaries, so a reader typing udp, lite, lightweight, user, datagram or protocol already reaches this tag; the expansion needs no alias. The bare acronym UDP belongs to the parent tag `udp`, not here (rule 5). The unhyphenated spelling UDPLite is the only plausible candidate (it is the spelling used in the Linux socket API as UDPLITE and would not be found today, since the desc words are `udp` and `lite`), but I am not confident it occurs in RFC text — RFCs consistently write UDP-Lite or, in header-compression titles, the spaced form "UDP Lite", which is multi-word and equally unfindable — so I am not proposing it rather than risking a corpus-check rejection.
- `unicode` -- Rejected as rule-1/rule-2 material: UTF-8 and UTF-16/UTF-32/UCS-2 are encodings of Unicode, not other names for it — utf-8 already has its own tag (also rule 5), and UTF-16 is recorded above as a missing tag candidate. Generic terms such as 'charset', 'character set', 'code point', 'BMP' and 'normalization' are either generic vocabulary or belong to the sibling tags character-sets and precis rather than here. 'Unicode' itself and 'internationalization' are already reachable via the desc and the parent tag.
- `uri` -- URN and IRI are existing tags (and children of this one), so neither is listed here — rule 5. 'URI template', 'well-known URI', 'URI scheme' and 'host-meta' are components or sub-features of the subject, not other names for it; 'template' and 'schemes' are in any case already reachable via the desc. CNRP / Common Name Resolution Protocol appears in this tag's match rule but is a distinct protocol rather than another name for URIs, so it is deliberately not proposed as an alias; if it ever warrants discovery it would be a separate vocabulary question, not an alias of uri. 'URL' also plausibly belongs to web or http for some readers, but uri is the correct primary home since the URL/URI distinction is exactly this tag's subject.
- `urn` -- URN has exactly one name, and both 'urn' and 'namespace'/'namespaces' are already reachable in the desc ('URN namespaces' indexes as separate words; typing 'namespace' matches 'namespaces' by prefix). Rejected candidates: NID (Namespace Identifier) and NSS (Namespace Specific String) are components of a URN, not other names for it (rule 2); 'URI' and 'IRI' are the parent and sibling tags respectively (rule 5); 'URC' (Uniform Resource Characteristics) is a different, largely historical concept, not a synonym. 'urn:' prefixed forms like 'urn:oid' or 'urn:ietf:params' are instances, not variant names.
- `user-guides` -- The only real alternative name for this tag is the FYI series, and `fyi` is already an indexed whole word in the desc ("User Guides (FYI series)"), so typing FYI lands here today — redundant under rule 4. The other terms in `match` are either titles of individual documents (hitchhikers guide, what is the internet) rather than names for the subject, or generic vocabulary (primer, handbook) that belongs to full-text search under rule 3. Working-group names here (run, nisi, userdoc, trainmat, usergloss) are administrative group labels that readers do not use as names for the technology/topic, unlike the SPRING->segment-routing case. Nothing qualifies.
- `utf-8` -- 'Unicode', 'UCS' and 'ISO 10646' were considered and rejected: Unicode is another existing tag id (rule 5) and the character-repertoire terms belong with `unicode`/`character-sets`, not with this one encoding form. Sibling encodings (UTF-16, UTF-7, UTF-32, ASCII, Latin-1) are different technologies (rule 1) and belong to `character-sets` if anywhere. 'BOM' and 'surrogate' are sub-features (rule 2).
- `uucp` -- UUCP has exactly one name, and the desc already makes "UUCP", "Unix" and "copy" findable (the hyphens in "Unix-to-Unix" split into separate indexed words). Candidates considered and rejected: UUCICO and UUX are programs/components of the UUCP suite, not other names for it (rule 2); "bang path" is both a component notation and multi-word; Usenet/netnews rode over UUCP but is a different technology with its own tag `netnews` (rules 1 and 5); "Unix" alone is generic and already reachable via the desc.
- `uuid` -- Version forms such as UUIDv4 and UUIDv7 would not be found today (the desc word 'uuid' does not start with 'uuidv7'), so they are technically eligible as variant forms, but listing eight of them is field-filling and a reader who types 'uuid' already lands correctly; left out deliberately. ULID, NSID, KSUID and similar identifiers are different technologies, not other names for UUID, so they are excluded under rule 1 and none looks substantial enough in the RFC corpus to propose as a tag. 'urn:uuid' is a URN namespace registration, an instance of the tag's subject and also reachable via the urn tag, so it is not listed here.
- `vcard` -- jCard/xCard are alternate serializations rather than different technologies, so they are treated as variant forms of the same format; if the taxonomy later prefers them split out, they would be sibling tags under applications rather than covers entries here. CardDAV is deliberately excluded: it is an existing tag id (rule 5) and this tag's child. The WG name vcarddav is skipped as it straddles both vcard and carddav and is not a name for the format.
- `vehicular-networking` -- V2X itself is deliberately omitted: it appears in the desc as "(V2X)", parentheses split words, so the indexed word is `v2x` and typing it already lands the reader here. DSRC and 802.11p (and OCB mode) were considered and rejected under rule 1/2 — they name the underlying radio link layer and an 802.11 operating mode, not this tag's subject; neither looks substantial enough on its own to propose as a new tag, but if one were wanted DSRC would be the candidate. ITS (Intelligent Transportation Systems) was rejected as too generic a query string and a broader domain than "IP in vehicular environments".
- `vp8` -- VP8 has exactly one name, and the desc word `vp8` already makes it findable. No superseded or variant forms exist: VP9 is a different codec with its own tag, and WebM/Matroska is a container covered by `matroska`. `libvpx` is an implementation rather than another name for the codec, so it is out under rule 3/2. Empty lists are the correct answer here.
- `vp9` -- VP9 has exactly one name and the desc word `vp9` already matches a reader typing VP9 (or the prefix `vp`), so no alias is needed. Deliberately excluded: `vp09` (the ISOBMFF/MIME codec-string spelling) as too marginal and doubtfully present as a standalone word in RFC text; `VP8`, `AV1`, `H.264`/`H.265`, `WebM` as different technologies under rule 1 (`vp8` and `h264` are existing tags; WebM belongs with `matroska`). `vp9` names a single codec, not a category, so it has no `covers`.
- `vpim` -- IVM (Internet Voice Messaging, RFC 4239) and AMIS were considered and rejected: they are distinct specifications rather than other names for VPIM (rule 1). Neither looks substantial enough for its own tag today, but IVM is the one to revisit if voice-messaging coverage grows. VPIMv2 was considered as a version form but I am not confident the unspaced token occurs in RFC text (the documents write "VPIM v2"), so it is omitted rather than risk a corpus rejection.
- `vpls` -- VPLS has effectively one name, and the expansion "Virtual Private LAN Service" is already in the desc word by word (virtual, private, lan, service), so nothing there needs restating. The historical marketing name "Transparent LAN Service" abbreviates to TLS, which is another tag's id (rule 5) and would badly shadow the transport-security tag; the unabbreviated form is generic vocabulary already reachable via the desc's "LAN" and "service". H-VPLS (hierarchical VPLS) is a deployment variant/sub-feature rather than another name for the tag, and its "vpls" token is reachable anyway. VPWS/pseudowire-based point-to-point service is a different thing and belongs to the existing pseudowire tag; EVPN, l2vpn and vpls are distinct siblings with their own tags, so no cross-listing.
- `vpn` -- "virtual private network" is multi-word and its component words are already indexed from the desc, so it is not proposed. VPN type names such as VPRN, VPWS and VLL were considered and rejected: they name particular service types belonging under the existing l3vpn/l2vpn children rather than being other names for this tag. The children l3vpn, l2vpn, vpls, evpn, mvpn and l1vpn all have their own tag ids, so nothing qualifies for covers here.
- `vrrp` -- HSRP and other first-hop redundancy protocols are different technologies and HSRP already has its own tag, so they are deliberately excluded. `Virtual Router Redundancy Protocol` itself is already reachable word-by-word from the desc (virtual/router/redundancy/protocol), so no multiword entry is needed.
- `vxlan` -- VXLAN has only one name, and both the acronym and the expansion ("Virtual eXtensible Local Area Network") appear as indexed whole words in the desc, so `vxlan`, `virtual`, `extensible`, `local`, `area` and `network` all already land a reader here. Considered and rejected: VXLAN-GPE (Generic Protocol Extension) — it is a distinct extension/encapsulation variant rather than another name for VXLAN itself (rule 2), and readers typing it are usually after the NSH/SFC-adjacent work; Geneve and NVGRE are sibling tags, not variants of this one (rules 1 and 5); VTEP, VNI and VNID are components of the encapsulation, not names for it (rule 2); "overlay" and "tunnel" are generic vocabulary and belong to the parent tag `overlay-networks` and to `tunneling` respectively (rules 3 and 5).
- `wais` -- WAIS has only one name, and both it and the expansion (Wide Area Information Servers) are already indexed word-by-word from the desc: typing 'WAIS', 'wide', 'area', 'information' or 'server(s)' all land here today. Z39.50 was considered and rejected under rule 1 — WAIS used a variant/profile of it, but Z39.50 is a separate ANSI/NISO information-retrieval standard, not another name for WAIS, and a confident hit here would be wrong; it is also too thin in the RFC corpus to propose as its own tag.
- `web` -- Nearly everything a reader might associate with "the web" is a different technology with its own tag (http, uri, html, websocket, cdn, web-security, ...), so it is excluded by rules 1 and 5 rather than being an alias here. "W3C" was considered and rejected: it names the standards organisation, not the web itself. "hypertext" and "browser" were rejected as generic vocabulary (rule 3) that full-text search already covers. This tag names a single subject area rather than a category standing in for untagged instances, so it has no `covers`.
- `web-linking` -- Web Linking has essentially one name. The obvious reader queries are already reachable from the desc: 'link' prefix-matches the desc words 'linking', 'links' and 'link', and 'web' matches 'web'. 'Link header' / 'Link relation' are multi-word and redundant anyway under that same prefix match, so they are not worth queueing. 'Linkset' (RFC 9264) and 'relation type registry' were considered and rejected: the former is a distinct media-type/format specification rather than another name for web linking, and the latter is generic vocabulary plus a registry reference. No category behaviour here — this is a single technology, so no `covers`.
- `web-push` -- VAPID (RFC 8292) was considered and rejected under rule 2: it is a sub-feature (an application-server authentication scheme) within web push, not another name for it. "Push API" is a W3C specification name rather than a synonym for the IETF technology, and is multi-word besides. Message encryption for web push (RFC 8291) sits under this tag but its terms are components, not aliases.
- `web-security` -- Rejected as components/instances already better placed: HSTS, token-binding and S-HTTP are children of this tag; cookies, webauthn, http-authentication, hsts, dane and tls are existing tags and must not be shadowed (rule 5). 'origin', 'same-origin', 'mixed content' and 'browser' are generic vocabulary or multi-word and left to full-text search. Sec-Fetch and X-Frame-Options are header names (components), not alternative names for the tag.
- `webauthn` -- Deliberately excluded: 'passkey'/'passkeys' — the consumer-facing name for discoverable WebAuthn credentials and a plausible alias, but I am not confident it occurs in published RFC text yet; worth re-checking against the corpus and adding if it does. Also excluded: 'U2F' (predecessor FIDO protocol, arguably a superseded-name alias but technically a different, pre-WebAuthn protocol — rule 1), and 'attestation', 'authenticator', 'credential' as generic vocabulary (rule 3). Note that remote-attestation is a separate existing tag and is unrelated to WebAuthn attestation statements.
- `webdav` -- CalDAV and CardDAV are separate existing tags and are deliberately not listed here. Sub-features such as ACL, LOCK, DASL/SEARCH and the PROPFIND/PROPPATCH methods are components of WebDAV, not other names for it, so they are left to full-text search.
- `webfinger` -- WebFinger has one name, and the desc word `webfinger` already makes it findable. The predecessor `finger` protocol is a different technology with its own tag (`finger`), so it is excluded by rules 1 and 5. `host-meta` and `.well-known` are components/mechanisms used by WebFinger rather than other names for it (rule 2); `.well-known` also spans many specs beyond this tag.
- `webrtc` -- ORTC (Object Real-Time Communication) was deliberately excluded: it is a distinct W3C API effort rather than another name for WebRTC, so rule 1 applies. Component/sub-feature terms (DataChannel, JSEP, ICE, DTLS-SRTP, SCTP-over-DTLS) are excluded under rule 2, and several of them already have their own tags (ice, dtls, srtp, sctp, nat-traversal) under rule 5. The children sframe and whip are separate tags, so their names must not be claimed here.
- `websocket` -- 'hybi' (the working group) was considered and dropped: unlike SPRING for segment-routing, readers do not use 'hybi' as a name for the technology. Sub-features and extensions such as permessage-deflate, Sec-WebSocket-Key, and the WebSocket subprotocol registry are components (rule 2), not aliases; compression readers want 'deflate'/'compression', and the HTTP/2 bootstrapping of WebSocket belongs to 'http2'.
- `whip` -- WHIP has exactly one name; 'WebRTC-HTTP Ingestion Protocol' and its expansion are already in the desc and word-prefix reachable ('ingest' matches 'ingestion', 'webrtc-http' matches 'webrtc'). Components and related concepts (ICE, STUN, TURN, SDP, HTTP POST endpoint) are either separate existing tags or sub-features and belong in neither list. WISH is proposed as an alias rather than covers because in practice readers type it as the name of this work, though it nominally spans WHIP and WHEP; if a whep tag is ever added, WISH should be listed on both.
- `whois` -- RDAP, the modern replacement for WHOIS registration lookup, is an existing tag (`rdap`) and so is excluded by rules 1 and 5; likewise `epp`. Generic terms from the desc area (registration data, directory services, port 43) are ordinary vocabulary or already reachable in the desc. WHOIS++ is only a handful of RFCs, so I have not proposed it as a separate tag, but if the corpus count justifies it later it is the obvious candidate to split out of `covers`.
- `wifi` -- '802.11' and '802' already hit the desc word '802.11' (the dot stays inside the indexed word), and 'wireless'/'lan' already prefix-match 'wireless' and 'lans', so none of those are proposed. WPA, WPA2, WPA3, SAE and 802.11i are security mechanisms used within 802.11 rather than other names for it (rule 2), and 802.1X is a separate port-authentication technology closer to eap — none are claimed here. The 802.11a/b/g/n/ac/ax amendment letters were considered as version forms but read as sub-parts of the one standard rather than alternate names for it, so they are left out. CAPWAP and PAWS are existing sibling tags.
- `wimax` -- `802.16` and `WiMAX` themselves are already reachable: `.` stays inside a word, so the desc indexes `802.16` whole, and `(WiMAX)` indexes as `wimax`. IEEE's own marketing name `WirelessMAN` would be a legitimate variant name, but I am not confident it occurs in RFC body text often enough to survive corpus checking, so I left it out; add it if the corpus check shows occurrences. `WiBro` (the Korean mobile-WiMAX profile) was considered and dropped for the same reason. Sub-features of 802.16 such as CS, MAC or the convergence sublayer are components (rule 2) and excluded; `cellular` remains the right home for 3GPP-side terms.
- `workshop-reports` -- "Workshop" is the tag's only real name and is already reachable: the desc contains the word "workshops", which starts with the query "workshop", so typing it lands the reader here today. Related terms like IAB and IRTF are organizational bodies, not other names for workshop reports, and both already appear as whole words in the desc anyway. Terms such as "report", "minutes" or "proceedings" are generic vocabulary (rule 3) and would wrongly pull in non-workshop documents.
- `x-window-system` -- XDMCP (X Display Manager Control Protocol) and the X authorization mechanisms are components/sub-protocols of the subject, so they are excluded under rule 2. The bare letter 'X' is already reachable via the desc and is far too generic to propose. 'X Window System' itself is reachable by typing 'window' or 'system'.
- `x25` -- X.25 has one name, and the desc indexes `x.25` as a whole word (the `.` stays inside the word), so a reader typing X.25 already lands here. Terms considered and rejected: X.121 — the numbering/addressing plan used by X.25 networks, a component (rule 2), not another name for X.25, even though it appears in `match`; LAPB and X.3/X.28/X.29 (the PAD 'triple X' recommendations) — sub-layer and sub-protocol components (rule 2); X.75 — a different protocol (inter-network gateway between X.25 networks), rule 1, and too narrow to warrant its own tag; PAD and PDN — generic/category vocabulary (rule 3), with 'public data networks' already in the desc for full-text purposes; DDN — the Defense Data Network is a specific network deployment, not a synonym for the X.25 protocol (rule 1), and it is in `match` only because the DDN X.25 profile RFCs belong to this tag.
- `x400` -- `X.400` itself is not listed: `.` stays inside a word, so the desc word `x.400` already matches a reader typing X.400, and `x400` is the tag id. MIXER, X.435 and the P1/P2/P7/P22 protocols, plus ADMD/PRMD, are interworking specs or components of X.400 rather than other names for it (rule 2), so they are omitted. X.500 has its own tag.
- `x500` -- Nothing survives as a single-token alias. 'X500' (dotless) is not needed: the tag id itself is x500, so that query already lands here, and 'X.500' is present in the desc as the indexed word 'x.500'. DAP, DSP, DISP, DOP, DSA and DUA are all components or sub-protocols of the X.500 directory (rule 2), not other names for it. 'Directory' and 'white pages' are generic vocabulary for the area and belong to full-text search or to the parent tag directory-services (rule 3). LDAP is a separate existing tag and a distinct protocol, so it is excluded by rules 1 and 5. X.509 is likewise its own tag and a different thing (the certificate format defined in the X.500 series), not a synonym for the directory service.
- `x509` -- The desc indexes 'X.509' as the single word `x.509`, so a reader typing 'x509' (no dot) would not match the desc — but `x509` is the tag id itself, so it is already reachable and is not listed. Terms like CA, CRL, certificate policy, key identifier and attribute certificate are components or sub-features of X.509 (rule 2) or generic vocabulary (rule 3); CRL/revocation queries are better served by the sibling `ocsp` or the parent `pki`. ASN.1 and X.500 are different technologies with their own tags (`asn1`, `x500`, and `spki` for the competing SPKI certificate format), so they are excluded by rules 1 and 5.
- `xacml` -- The tag name XACML is the universally used name; the expansion is already in the desc as individual indexed words (extensible/access/control/markup/language). The variant spelling "eXtensible" is found by case-insensitive prefix match on "extensible". Version forms like XACML 3.0 are multi-word and the bare token XACML already reaches the tag. Related terms such as PDP, PEP and PAP are components of the XACML architecture (rule 2), and OASIS is the standards body rather than a name for the technology.
- `xcon` -- No single-token aliases survive. CCMP (Centralized Conferencing Manipulation Protocol, RFC 6503) and the XCON data model elements (conference object, conference blueprint) are components/sub-protocols of the framework, not other names for it, so rule 2 excludes them; CCMP is also ambiguous with the 802.11i cipher of the same acronym, which argues against a confident search landing. BFCP, the floor-control protocol developed alongside XCON, is a different technology with its own tag (`bfcp`), so it belongs to neither list. The desc word `conferencing` already covers queries like `conferenc` for readers heading to the parent tag `conferencing`.
- `xml` -- XML has exactly one name, and it is the tag id. The expansion "Extensible Markup Language" is already reachable: the desc indexes `extensible`, `markup` and `language` as separate whole words, so typing any of them lands the reader here; the full phrase is not worth a `multiword` entry on top of that. Related XML-family terms were considered and rejected: XSLT, XPath, XQuery and XLink are distinct technologies (rule 1), and DTD, XSD/XML Schema, xmlns and SOAP are sub-features, schema languages or formats layered on XML rather than other names for XML itself (rules 1-2) -- a reader typing any of them should fall through to full-text search rather than be told confidently that they mean XML. This is a single technology, not a category, so it takes no `covers`: it does not stand in for those things, it is the substrate they are built on. Note also that `sgml`, `rfcxml` and `xml-signatures` are existing sibling/related tags, so SGML, RFCXML/xml2rfc and XMLDSIG must not be claimed here (rule 5 for the ids themselves, rule 1 for the rest).
- `xml-signatures` -- Canonicalization / c14n (RFC 3076, Exclusive C14N) is a component of XML signature processing, not another name for it, so it is excluded under rule 2; the same goes for KeyInfo and the XML Signature transforms. XAdES is a distinct profile layered on XMLDSIG rather than a synonym, and is too thin to propose as its own tag. SAML and XKMS are different technologies that happen to use XML signatures and must not be aliased here. Generic 'xml' belongs to the existing `xml` tag (rule 5).
- `xmpp` -- Expansions of the acronym (Extensible, Messaging, Presence) are already reachable via the desc. Component/sub-feature terms such as BOSH, MUC, PubSub, Stanza and Jingle are rule-2 components of XMPP, not other names for it, so they are excluded; Jingle in particular is a signalling sub-protocol, not a synonym. STOX and xmpp-old are group names that duplicate the tag id or are not reader-typed technology names.
- `y2k` -- "2000" and "year" are already reachable as whole words in the desc, and "Y2K" is the tag name itself, so neither is proposed. The Year 2038 / time_t rollover is a different problem and is not proposed as an alias here.
- `yang` -- YANG has a single name and the desc already indexes 'yang'. Expansions like 'Yet Another Next Generation' are multi-word and never typed by readers, and the expansion words are already in the desc. Related terms are either other tags (netconf, restconf, yang is modelled by) or components/sub-features: YANG-Push, YANG Library, SMIv2, and the encodings YIN, JSON, XML are not other names for YANG itself. 'NMDA' (Network Management Datastore Architecture) is an adjacent architecture, not a synonym. Nothing qualifies.
- `zstd` -- Zstandard has exactly one name plus its canonical short form. The short form is the tag id itself, and the full name "Zstandard" is the first word of the desc, so typing either already lands the reader here. Sibling algorithms (deflate, gzip, brotli) are different technologies with their own tags, and the RFC 8478 internals (frames, blocks, FSE/Huffman entropy stages, dictionaries) are components, so none qualify.
